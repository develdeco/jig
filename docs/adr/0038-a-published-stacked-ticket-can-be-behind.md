# A published stacked ticket can be behind, and a head is reviewed through merges git would make

[ADR 0010](0010-ticket-dependencies-live-on-the-ticket.md) made a stacked child start from its parent's branch and told the child's session to restack or retarget when the parent moved or merged. [ADR 0037](0037-a-chart-is-run-from-the-main-session.md) made a chart run end when every ticket is published. The two met badly. A child published into its parent's branch is published, so its standing was done. Once the parent merged, the child still owed a merge of the target and a publish that pointed its pull request at the target, and nothing said so: the correction notes reach only a session working on the child's branch, and a chart run has no such session. The chart read `CHART_DONE` with a pull request that went into a branch about to be deleted.

Finishing that work showed three more gaps. The merge of the target changes the head, and publish refuses a head no clean round reviewed, so a merge git made on its own cost a whole new gate round that asked the reviewer for nothing. A merge resolved by hand got a delta round, but the delta from the reviewed head carried every file the target brought in. And publish looked for the open pull request into the base it was about to use, so when the host did not retarget a child's pull request it found none and opened a second one.

## Decision

**The ticket's own standing carries a restack or a retarget.** A published ticket whose stack plan asks for either is not done: it is *behind*. Its brief, build and review stay done and its publish is current again, ready, with the prompt "Publish T". `phase.Facts` gains `Restacks`, one entry for each repo that asks for a merge, and `Ticket.Behind` says the ticket is owed. `jig next <T>` says `state: behind`, names the merge (`git merge origin/main`) and the publish that follows (`jig publish T`) on each `stack` row, and ends the restack and retarget notes with that publish. A closed ticket is never behind. A built ticket that has not published keeps its phase: the merge is part of its work, and its review and publish follow by phase.

**The chart gets it from the ticket.** A chart entry that names a stacked blocker and has published is read with its stack plan, like `jig next <T>`. A behind ticket is a row at the publish, reachable here, in the run, so the chart is ready under "Continue <chart>" and `CHART_DONE` waits for it. The chart has no rule of its own for a behind ticket. Before the parent merges, while its pull request is open, the published child is done, and its stacked need names that pull request: the run ends at it (an entry of `ends`), so the chart is `CHART_WAITS_MERGE` with "Continue <chart>", not `CHART_DONE`. The TUI reads a chart that waits on a merge again every two minutes, so it sees the parent merge and the child turn behind. A child whose own work merged, or whose parent is closed or has no pull request on record, waits for nothing. The `chart` skill says such a ticket needs no build subagent: the main session runs the merge in a checkout of the ticket's branch, then publishes.

**jig does not make the merge, and `jig here` and the hooks do not read it.** The session merges. `jig here` and the hooks run on every tool call and keep a stack-blind standing, so the person-facing verbs (`jig next`, `jig status`, a chart's standing) agree with one another and the per-call readers stay cheap. The TUI's ticket screens derive a ticket from the status text and the journal, which carry no stack plan, so they show a behind ticket as published until `jig status` has a form they can read; the chart screen takes each listed ticket's steps from `jig next <chart> --json` and shows it behind. One stack-aware derivation for every reader is a follow-up.

**A ticket whose own work merged is not behind.** `stack.Facts.Landed` says the ticket's own work has merged in the repo, from the merge reader's fact for the ticket itself. Without it, once the child's own pull request merged its branch would never hold the target's head again and it would read as behind for good.

**A head is reviewed through merges git itself would make.** A head is reviewed when it is the reviewed head, or when every commit between them along first parents is a two-parent merge whose tree equals `git merge-tree --write-tree` of its parents (`gitx.MergeTree`, git 2.38 or later; an older git is `GIT_TOO_OLD`). The gate and the three publish checks (`checkReviewedHead`, `checkBodyHead`, `PublishRecordPR`) share this one rule. Any other commit, an octopus included, is still refused with `PUBLISH_UNREVIEWED_HEAD`.

**A hand-resolved merge's delta round reviews its resolution.** When the tip is a merge a person resolved by hand and every merge before it is clean, the delta round's base is a tree: git's own merge of the tip's parents. The diff is the hand edits, and `must_review` lists their files and none of what the target brought in. When the head is the reviewed head or only clean merges lie past it, the base is the head and the round asks for nothing. Any other line, with an ordinary commit or a hand-resolved merge that is not the tip, is the plain delta from the reviewed head, so the reviewer sees more, never less. The scope stays `delta` in every case.

**Publish finds the pull request by its branch and points it at its base.** `FindOpenPR` takes the branch alone and returns the pull request's URL and base. `UpdatePR` adds `--base` to the same `gh pr edit` that writes the body when the base differs from the one the plan names. A stacked child's pull request that the host did not retarget is updated and pointed at the target, never doubled; the table says `updated, retargeted to main`. More than one open pull request from a branch is still an error. A branch with no open pull request opens one into the plan's base. Only this full publish retargets: the hand-off (`--body`, then `--pr`) records a pull request somebody opened and leaves its base alone, so the retarget notes and a behind ticket's help also give the edit for that path, `gh pr edit <pr> --base <target>`.

## Rejected alternatives

- **A chart-only rule** (the chart treats a published child whose parent merged as unfinished). The ticket's own verbs would still say it is done, and `jig next <T>` would disagree with `jig next <chart>`. The standing belongs to the ticket and the chart reads it.
- **Recording the owed merge** (a journal line when the parent merges, cleared by the publish). It is a second place that says what the stack plan already derives, and it goes stale when the session merges before anything reads it. The plan is read on demand and nothing is written.
- **Reviewing every merge.** A merge git made on its own adds nothing of the author's; a round that asks the reviewer for nothing costs a session and teaches people to skip the gate. Only a resolution is new work.
- **Parsing `git merge-tree` text without `--write-tree`.** The older form prints a patch to read back, and comparing a merge commit with it means rebuilding a tree from text. `--write-tree` gives the tree to compare, and the tree of a conflicted merge is the base a hand-resolved merge's delta needs.
- **Reading the pull request's base from the host to hold the standing until it is retargeted.** It would make `jig next` ask the host about the ticket's own pull request every time. A session that merges and stops before publishing leaves the standing at done while the pull request still points at the parent's branch, and the next `jig publish` fixes it.

## Consequences

- Amends [ADR 0037](0037-a-chart-is-run-from-the-main-session.md): a chart's standing is no longer done for a published ticket that is behind, or one stacked on a parent whose pull request is open, and the run ends when none is.
- Amends [ADR 0010](0010-ticket-dependencies-live-on-the-ticket.md): restack and retarget are the ticket's standing as well as a note to a session.
- `CONTEXT.md` gains *Behind* and *Reviewed head* and amends *Stacked start point* and *Correction*. `ARCHITECTURE.md` changes in the `internal/stack`, `internal/phase`, `internal/gitx`, `internal/repohost` and `internal/verifydeliver` rows and the stack and publish paragraphs.
- `base_sha` in a delta round's `review.json` and open record can be a tree id. Every reader passes it to `git diff`, which takes a tree.
- jig needs git 2.38 or later to compare a merge with git's own. On an older git, a publish or a gate of a head that only merges lie past the reviewed head stops with `GIT_TOO_OLD`; a line with any other commit is judged as before, on any git, without asking git to merge.
- A parent merged by squash has commits that are not in the target. The child's merge of the target may conflict and is then resolved by hand, which the delta round reviews. jig does nothing special for it.
