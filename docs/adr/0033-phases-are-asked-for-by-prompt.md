# Phases are asked for by prompt, and a fresh session reviews

ADR 0032 left the person in the harness session and gave jig the job of listening. A ticket still goes through four phases, brief, build, review and publish, and each has a skill. What nothing gave a session or a person was one answer to "where does this ticket stand, and what do I ask next". `jig status`, `jig next`, the claim refusals and the TUI's steps each worked it out their own way, so they could disagree. A session told "review SHOP-1" had no way to learn that it had built SHOP-1 itself, which makes it a reviewer whose round publish will refuse. The first run of a whole ticket, brief to pull request, in one session, found the rest: a reviewer started in the background so the turn ended, a planner that made a ticket's folder by hand, a reviewer that edited the clone it was reading.

The owner asked for four things: phases that run when the person asks for them, one at a time by default; a run of several phases when the prompt names them; advice to review in a subagent when the session is not a fresh one; and screens and hints that all say the same thing about where a ticket is. This ADR records the five decisions that give them.

## Decision

**One pure derivation says where a ticket stands (decision 35).** `internal/phase` takes a ticket's journal lines and a small struct of facts (its slices and their states, whether the brief's approval is current, changed or missing, the outstanding asks, the rounds and the open one, the unpublished blockers) and returns the four phases, each done, current or pending with its sub-steps, which phase is current, whether it can start now, the code and sentence that say why not, and the prompt that starts it: "Plan SHOP-1", "Build SHOP-1", "Review SHOP-1", "Publish SHOP-1". It imports neither the store nor the gate package, so the TUI, which reads no store, calls the same function as `jig next`, `jig status`, `jig here` and the refusals do. There is no phase verb and there are no start or end records: a claim, a gate round opening, a reviewer taking it, a rendered pull request body, a publish approval, a recorded pull request and the approval line already mark every phase boundary, and the phase is read from them.

**Every skill checks the phase, and ends by naming the next prompt (decision 36).** A phase skill begins with `jig next <T>`. If the phase it names is not the skill's own, the session tells the person what the ticket needs and the prompt that does it, and stops; it does not run an earlier phase on its own. A skill ends by relaying `jig next`'s `prompt:` and stopping. `jig next <T>` gained `phase`, `ready` and `prompt` (and, when the phase cannot start, `code` and `reason`), and `--for <phase>` answers for a phase the caller names. The refusals that already existed stay (`CLAIM_*`, `GATE_NOT_GREEN`, `PUBLISH_*`), and their help ends with the prompt that meets them. Running a phase that is already done is a warning, never a refusal. An attended claim on a brief nobody approved still warns and goes through, as it did, and the build skill stops on any claim warning and asks.

**A run of several phases is the person's prompt (decision 37).** "Build and review SHOP-1" and "Take SHOP-1 from brief to PR" name phases in order, and a skill whose prompt named later phases goes on to the next skill instead of stopping. A refusal ends the run. Nothing records that a run began. The Stop hook's publish note became a next-phase note: it keeps its old rule (a clean round, a person's approval of the reviewed head, not yet published) and gained a review note, and the review note is for an unattended session only. A session that claimed with `--unattended`, whose slices are all green with no round open, is told once to open the gate and have the change reviewed. An attended session is never held at Stop.

**The person's moments stay theirs unless the prompt gives them away (decision 38).** The brief's approval and the publish approval are the person's. "Go with your recommendations" delegates the first; a prompt that ends at the pull request, or says "and publish it", delegates the second. A delegated approval is recorded with agent provenance, as `jig validate` off a terminal already records it, and an agent's `jig publish --approve` never stands for a person's. This is skill text and needs no code.

**A fresh session reviews directly; one that is not spawns a subagent (decision 39).** A session is *fresh* for a ticket when its id carries no journal line of that ticket but the gate's, triage and publish lines, and no ledger line of it changed a file, made a commit or claimed. `jig gate` and `jig next <T>` say whether the calling session is fresh, not fresh or unknown. A fresh session reviews in its own context. Otherwise they advise a subagent: in Claude Code the Agent tool with `subagent_type: general-purpose`, `model: opus` unless the person named another, run in the foreground with no worktree isolation, and handed a prompt that says it did not build the ticket and is to run the review skill and reply with the verdict line. The main session never runs `jig review context` itself. This is advice: `jig review done` still judges independence from who built, as before.

## Consequences

- The skills carry the hand-off text, and each stays within the 6000 bytes and 100 lines the lint allows. The intake skill had to be trimmed to make room.
- A hint, a refusal and the TUI's Steps panel can no longer disagree about the phase, because there is one function. `TestTUIAndNextAgree` walks a ticket from a drafted brief to a published pull request and compares the screens' standing with `jig next --json` at each state.
- A subagent shares its parent's session id, since the commands it runs carry no agent id, so freshness is a fact about the whole session. If the main session and a subagent both read a round, the ledger cannot say which of them closed it; the rule that the main session never reads the round is what keeps the round independent.
- A reviewer subagent that runs `jig next` before any round is open is shown the advice to spawn a subagent, because jig sees it as its parent. Its prompt and the review skill say to ignore the advice. A way for the harness to tell jig the caller is a subagent would remove the case.
- `jig status`, `jig here` and the Stop hook derive the phase without asking a repo host about a blocker's pull request, so they can say "Build T" for a ticket that `jig next T` holds for an unmerged blocker. `jig next <T>` is the exact answer, and every skill starts with it.
- The MCP `next` tool takes `for` but no session, so over MCP the freshness advice follows the session the server's environment names, and is absent when it names none.

## Rejected alternatives

- **A phase verb with start and end records.** A `jig phase start` and `jig phase end` would be a second record of facts the journal already holds, one that a crashed or forgetful session leaves open and that could disagree with the lines it duplicates. The phase is derived from the lines, and nothing needs to be told to jig.
- **A record of a run's span.** Writing down that an automatic run began, and which phases it covers, would give jig a second place that says what the person asked for, one that outlives the prompt and has to be cleaned up. The span is the prompt, and the skills read it there.
- **Enforcing a fresh reviewer.** Refusing `jig review context` or `jig review done` from a session that is not fresh would refuse the legitimate subagent too, since jig cannot tell it from its parent. The independence check at `jig review done` already refuses a round the reviewer built part of, and the advice only keeps the person from reaching that refusal.
