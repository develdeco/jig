# A chart is made and checked by verbs

[ADR 0037](0037-a-chart-is-run-from-the-main-session.md) gave a chart a run and a standing, and left the chart itself as it was: a folder, `charts/<name>/`, that a person or the intake skill wrote by hand, `map.md` and `tickets.yaml`. Three things followed from that. A hand-made folder could have the wrong shape (a `tickets.yaml` with no `tickets:` list is refused by `WriteChart` as an invalid chart file), and the chart's GitHub issue came only with some later checkpoint, after tickets had graduated under it. Next, the one check of a chart's entries was `jig graduate`, which refuses one problem at a time while it mints entry by entry: to see every problem a person ran it again and again, and a run that got past the first entries minted tickets before the later entries' problems showed. Last, `jig next <chart>` refused the whole chart on one bad ref of an entry that had no ticket yet, so a chart under construction could not be read at all, and a chart just made (no entries) was told to "run `jig graduate`", which refuses a chart with no entries.

## Decision

**`jig chart new <name> --title <t>` makes the chart, the way `jig ticket new` makes a ticket.** It syncs the store, lands `charts/<name>/` with `Store.Claim` (one commit, "chart <name>: new chart", pushed on a store with an origin) and runs the checkpoint hook. It writes nothing to the session ledger: a chart is not a ticket. `chart` is a verb with the one subcommand `new`; any other is a `VALIDATION_ERROR`.

**The skeleton is written once, and the map is read after.** `Store.CreateChart` writes `map.md` (the title as its heading and the five empty sections of the chart template: Destination, Notes, Decisions so far, Not yet specified (fog), Out of scope) and a `tickets.yaml` with a comment that says how an entry is written and an empty `tickets: []` list, which `ReadChart` reads as no entries and `WriteChart` accepts once entries are added. The map has no placeholder prose, because a paragraph under a heading is an item to `jig recall` and to the mirror. jig never writes the map again: it reads its sections, and people and sessions fill it.

**A name is a word a chart can be reached by.** It is lower case letters, digits, `-` and `_`, starts and ends with a letter or digit, at most 64 characters: two folders that differ in case are one folder on some volumes. The name is refused when it is taken, which is when `charts/<name>` exists in any form or differs from an existing chart folder only in case, and when it reads as a ticket, because a ticket id or alias wins over a chart name (`chartNamed`) and the chart could then never be reached by its name. A name that ends in a ticket lease suffix (`-gate`, `-publish`) is refused for the same reason. The taken checks run again inside the claim's write, so a chart another clone pushed meanwhile is refused after the retry's pull.

**The chart's issue exists at once.** The checkpoint hook runs the GitHub mirror, which opens an issue for every chart with no record, titled by the map's first heading. Running it after the claim means the chart's issue exists before any ticket graduates under it.

**`jig validate <chart>` lists every problem of a chart's entries and mints nothing.** `cmdValidate` asks `chartNamed` after it resolves the store and before it resolves the word as a ticket, so a ticket id or alias still wins. It reads the store and writes nothing: no sync, no commit, no mirror. `--check` is accepted and changes nothing, since a chart has no approval to record. The checks are `jig graduate`'s, from one function, `checkChart`, that both call: a title on every entry, a declared key on every entry with no id, no duplicate ids, a ticket folder for every id, a kind of merged or stacked, and every `blocked_by` ref (in range, not its own entry, an earlier entry for an entry with no id, a ticket the store has, no ref twice). It collects all of them instead of stopping at the first, and lists a chart with no entries and a `tickets.yaml` that cannot be read. `validateChartEntries` and `resolveChartEntryRefs` stay as thin wrappers that return the first problem's error, so `jig graduate` refuses with the error, code and help it always gave. A failure is a `VALIDATION_ERROR` whose help is the problem lines in graduate's order and a closing line to fix the file and run `jig validate` again; a pass says `valid: yes` with the counts of the entries and the step that follows.

**A bad ref is a row's problem, not a refusal of the chart.** `chartFacts` resolves the refs of entries with no ticket with the collecting resolver. An entry whose refs have problems gets the problem on its row (its reasons joined, then a pointer to `jig validate <chart>`) and the refs that did resolve as its needs; it is blocked, and the entries behind it with it. The other entries are read as before. `jig next <chart>` and `jig status <chart>` print it as a `problems` table after the tickets, the JSON already carries it as the row's `problem`, and the TUI shows it as a stalled row with no change. While an entry with no ticket has a problem, the verdict's reason and the help say to run `jig validate <chart>` before `jig graduate <chart>`. `jig graduate` still refuses such a chart, with the same error as before, and mints nothing until the entries are fixed.

**A chart with no entries is told right.** `phase.DeriveChart` keeps `CHART_NOT_GRADUATED` for it (the TUI reads the code) with no prompt, and the reason says to add the entries to `charts/<name>/tickets.yaml` and check them with `jig validate <name>`.

**Intake makes the chart with the verb.** The `intake` skill's chart output is `jig chart new <name> --title "<t>"` instead of writing the folder by hand, and it checks the entries with `jig validate <name>` before `jig graduate <name>`.

## Rejected alternatives

- **A `jig graduate --check`.** It would tie the check of a chart to the verb that mints, and `jig validate` is already where a person asks whether what they wrote is right. A chart's check is the same verb as a ticket's, told apart by the word.
- **A `jig chart` family that renames `graduate`** (`jig chart graduate`, `jig chart validate`, and more subcommands). The owner dropped it: the verbs people already use keep their names, and `jig chart new` is the one that was missing.
- **A skeleton with placeholder prose.** `jig recall` and the mirror read a paragraph under a heading as an item or as the issue's body, so a line saying "describe the destination here" would be shown as content. The sections are empty.
- **jig writing the map again on later commands.** jig would then own text people and sessions edit, with the conflicts that brings. It writes the skeleton once.
- **A mixed-case chart name.** It would be two folders on a case-sensitive volume and one on another.

## Consequences

- Amends [ADR 0037](0037-a-chart-is-run-from-the-main-session.md): "`map.md` is read, never written" becomes "jig writes its skeleton once, when the chart is made, and reads it after". The chart's standing is still derived, and the verdict, the rows and the run are unchanged.
- `jig next <chart>` and `jig status <chart>` no longer fail on a bad ref of an entry with no ticket: they exit 0 with the row's problem. A script that read that failure reads the problem now.
- `Store.RunCheckpointHook` is called by one more verb after its own `Claim`: `jig chart new`. The one chain that cannot run end to end is the mirror's: the real binary would reach api.github.com, so `TestChartNewRunsItsOwnCheckpointSync` runs it in process with the stub client.
- `CONTEXT.md` changes in *Chart*, *Intake* and *Chart standing*. `ARCHITECTURE.md` changes in the store tree comment on `map.md`, the paragraph on what `jig graduate` checks, the list of verbs that call `Store.RunCheckpointHook`, the paragraph on `phase.DeriveChart` and `chart_facts.go`, the paragraph on `jig validate`, and the `internal/store/` row. The `intake` skill's chart paragraph is replaced, not added to, to stay under the 6000 bytes and 100 lines the lint allows.
- A chart folder made by hand before this still works: a chart is a folder with a `tickets.yaml`, and `jig validate <chart>` checks it.
