# T-17 (REPO-4): publish opens one pull request per repo, each linked to the others

Notes for the DOCS-1 ticket. Nothing in README.md, ARCHITECTURE.md, CONTEXT.md,
DECISIONS.md or docs/adr was edited; the text they need is at the end. Issue
develdeco/jig#55. Branch `ph/T-17`.

A ticket whose slices build in several repos publishes one pull request for each
repo, all from the one branch name, and each body names the others. Every form of
`jig publish` covers the repos the gate reviewed (`gateRepos`, T-16) or the one
`--repo` names. `MULTI_REPO_NOT_YET` is gone, and so is `selectRepo`'s `Repos[0]`
default: a ticket that builds in one repo that is not the first publishes from that
repo. No new verb, no new flag (`--repo` already existed; it now narrows instead of
choosing), one new journal key, no schema bump. A project of one repo, and a ticket
in one repo of a project of several, publish as they always did.

## Which repos a publish covers

`readyToPublish` returns a `publishTarget` for each repo (`internal/verifydeliver/publish.go`):

| Project | `jig publish T` covers |
|---|---|
| one repo (or none known) | that repo, whatever the slices say. Nothing changes |
| several repos | the repos the ticket's slices build in (`gateRepos`, so `ready.Place`), in the project's order. A ticket in one repo that is not the first is covered by that repo alone |

`--repo r` narrows any form to repo r (`publishRepos`). A name the project lacks is
`VALIDATION_ERROR` `the project has no repo "docs" (it has api, web)`; a repo the
ticket does not build in is `VALIDATION_ERROR` `JIG-1 builds in api and web, not in
docs`, help `Name one of its repos with --repo (api, web), or leave --repo out to
cover them all`. The refusals of `readyToPublish` are in this order: the slices are
not built (`GATE_NOT_GREEN`), then no slice places in a repo (T-16's
`VALIDATION_ERROR`), then the `--repo` name, then the branch, the round
(`PUBLISH_NOT_CLEAN`, `PUBLISH_NOT_INDEPENDENT`), the intent. A failure in one repo
says which: `repo web: ...` (`inRepo`, T-16's).

The ticket's branch has one name in every repo (`publishBranch` resolves it against
the target of each repo it covers).

## The forms

- **`jig publish T --body [--repo r]`** renders `pr/<repo>.md` and the review notes
  for each covered repo's reviewed head and journals a `pr-body` line for each (it
  names the repo). Each body is that repo's slices, the round's findings for that
  repo, and a `## Part of T` section. It changes no lease and no branch.
  Output: for one repo the `publish_body` block as before (`ticket`, `repo`,
  `branch`, `base`, `head`, `title`, `pr_body`, `review_notes`, the picks rows); for
  several a `publish_body` block with the ticket and the branch, and a table
  `bodies[N]{repo,base,head,title,pr_body,review_notes}:` with a row for each repo.
  The help for one repo of a ticket in several says to record its pull request with
  `jig publish T --pr <url> --repo r`.
- **`jig publish T --pr <url> --repo r`** records repo r's pull request after the
  host says it is from the ticket's branch and at r's reviewed head. Without
  `--repo`, a ticket that builds in several repos is `VALIDATION_ERROR` `JIG-1 builds
  in api and web: say which repo the pull request is for`. It journals a `pr` line
  naming the repo. When it is the last repo without a pull request it writes what a
  publish leaves in the store (changelogs, ledger entry, contract index, evidence)
  and `publish-done`; otherwise the output's help says `web still needs its pull
  request: jig publish T --pr <url> --repo web`. `RecordReport.Pending` lists the
  repos still waiting.
- **`jig publish T --approve [--repo r]`** journals a `publish-approved` line for
  each covered repo, with that repo's reviewed head and the repo. The output has the
  ticket, the branch and the provenance, and for several repos an
  `approved[N]{repo,head}:` table (for one repo, the `repo` and `head` rows as
  before). A bare publish asks nothing only when a person approved the head of
  every repo it ships (`allApproved`).
- **Bare `jig publish [--yes] [--repo r]`** (`Publish`):
  1. `readyToPublish`, then **every repo is prepared before anything is written**
     (`prepareShipment`: lease, the reviewed head, the fast-forward check, the host
     and the open pull request, the divergence check). A repo that refuses leaves
     the others, and the store, as they were.
  2. Each body is rendered, naming the pull requests the branch already has open
     and the ones the journal recorded for repos this publish leaves alone, else
     `pending`.
  3. One confirmation for all (`confirmation`: `Push jig/JIG-1 in api and web and open
     a PR for JIG-1?`; one repo asks what it always asked), or `--yes`, or a person's
     approval of every head.
  4. For each repo in order: the body is re-rendered if a pull request opened since it
     was rendered changed its links, the branch is pushed, the pull request is opened
     or updated, a `pr` line naming the repo is journaled, the review notes are posted
     as the first comment.
  5. **Each body is updated with the others' urls once all are known**: a repo opened
     before the last has its body rendered again and its pull request updated
     (`gh pr edit`), and the media references are checked again. With two repos that
     is one `gh pr edit` for the first.
  6. When every covered repo has a `pr` line since the last `publish-done`
     (`pendingRepos`), the store docs are written and `publish-done` follows. A
     publish narrowed to one repo of two stops short: the report names the pending
     repo (`pending: web` row, help `web still needs its pull request: jig publish T
     --repo web`).
  Output: the `publish` block (ticket, tier, picks rows, and `pending` when a repo
  waits) then the `pushed`, `pr_body` and `pr_url` tables, which already had a row for
  each repo.

A repo with no pull-request host is pushed and gets a `pr` line with no url
(`none:no-host`), which counts for the publish-done rule as it did.

## The body section

```
## Part of JIG-1

- also web: https://github.com/acme/web/pull/4
- also docs: pending

```

After `## Intent` and before `## What changed`, in the pull request of a ticket that
publishes in several repos only: one line for each other repo it builds in, in the
project's order, with the url of that repo's pull request (the journal's latest `pr`
line with a url, or the open pull request the branch has) or `pending`. Nothing else
in the body changes, so a ticket in one repo has the body it had
(the golden renders in `publish_pr_golden_test.go` pass unchanged).

In a project of several repos a body for a ticket that publishes in several repos
tells the slices of its repo (`## What changed`), the findings whose file begins with
its repo (`<repo>/<path>`, T-16; a bare path an older jig recorded goes to the first
repo) and the review notes' coverage as repo-relative paths. The notes file is
`pr/review-notes-<repo>.md` there (`review-notes.md` otherwise), since each pull
request carries its own first comment. `## Verification` names the oracles its own
manifest declares among the round's.

## Journal shapes

`journal.Line` gains `repo` (omitted when empty), the repo a `pr-body`,
`publish-approved` or `pr` line is about, by its name in the project. It is set only
in a project of several repos (`publishTarget.lineRepo`); a project of one repo writes
the lines it always wrote.

```
{"event":"pr-body","commit":"<head>","branch":"jig/JIG-1","ref":"tickets/JIG-1/pr/web.md","repo":"web"}
{"event":"publish-approved","commit":"<head>","branch":"jig/JIG-1","provenance":"person","repo":"web"}
{"event":"pr","outcome":"opened","commit":"<head>","url":"https://github.com/acme/web/pull/4","branch":"jig/JIG-1","repo":"web"}
{"event":"publish-done"}
```

`outcome` of a `pr` line is as before (`opened`, `updated`, `recorded`,
`recorded:unverified`, `none:no-host`). `publish-done` has no repo.

## Decisions I took

1. **`--repo` narrows, it does not choose.** The default is every repo the ticket
   builds in; the old default (`Repos[0]`) is gone. A name the ticket does not build
   in is refused rather than shipped.
2. **Every repo is checked before the first is pushed**, and one confirmation covers
   all. A failure while pushing the second leaves the first pushed with its pull
   request open and `pending` in its body: running `jig publish T` again updates it
   (the branch is already on origin and a fast-forward of itself; the open pull
   request is found).
3. **The journal names the repo only in a project of several repos**, so the lines of
   a project of one repo (and every golden, ledger and mirror test) are what they were,
   and a ticket in one repo of a project of several still names it.
4. **publish-done is a rule over the lines since the last publish-done**, not a flag:
   every covered repo has a `pr` line. It is the same for `--pr` (the last one written
   finishes it) and for a bare publish, and a re-publish after a fix writes a new
   publish-done.
5. **The link line is `also <repo>: <url or pending>`** under `## Part of <T>`; the
   brief's wording ("also <repo b> <PR url or 'pending'>") has no colon. The colon keeps
   the repo name and the url apart.
6. **`BodyReport` and `ApproveReport` list the repos** (`Repos []RepoBody`,
   `[]RepoHead`) in place of the one repo's fields; `RecordReport` gains `Pending`,
   `PublishReport` gains `Pending`. Callers: `cmd/jig/publish.go` and the tests.
7. **The TUI sub-steps come from the journal's lines**, as the rest of the phase does:
   the repos of a publish are the ones its lines name. During a bare publish the first
   `pr` line arrives alone, so the step list has one `pull request` until the second
   repo's line arrives (a moment, then two). `--body` and `--approve` (which name
   every repo at once) show two from the start.
