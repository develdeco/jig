# T-18 (GRAPH-4): a blocker is met when its work merged

Notes for the DOCS-1 ticket. Nothing in README.md, ARCHITECTURE.md, CONTEXT.md,
DECISIONS.md or docs/adr was edited; the text they need is at the end.

Digester decision 43, issue develdeco/jig#56. A merged blocker used to be met by a
`publish-done` line (and by `gh` saying its recorded pull request was not unmerged,
when `gh` could tell). It is met now when its work has merged, and `jig claim` and
`jig next` say what is missing when the facts are not there. No new verb, no new flag,
no journal line, no schema bump.

## The merge fact

For a blocker of kind `merged`, per repo it builds in, in this order
(`ready.JudgeRepo`, internal/ready/merge.go):

| Evidence | Fact |
|---|---|
| the ticket has not published (no `publish-done` line) | not met, `it has not published`. Nothing else is read: no host is asked and no clone is touched |
| the recorded pull request (`publish --pr`, the latest `pr` line for the repo), and the host says `MERGED` | **met**, by `pr` |
| the host says `CLOSED` | not met, `its PR was closed without merging (<url>)` |
| the host says `OPEN` | not met, `its PR is open (<url>)` |
| no recorded pull request, or one the host could not be asked about, and the ticket's branch tip is an ancestor of `origin/<target>` in the repo's mapped clone | **met**, by `ancestry` |
| a recorded pull request the host could not be asked about, and no ancestry | not met, `its PR could not be read from the host (<url>)` |
| nothing recorded, no ancestry | not met, `no merge on record: record its PR with `jig publish <B> --pr <url>`` |

- A readable pull request decides: open or closed beats the branch being in the target.
- Ancestry is positive evidence only. A squash or a rebase gives a tip the target does not
  hold, and equal content is never taken for a merge: such a blocker stays blocked until its
  pull request is recorded. Nothing is fetched: `origin/<target>` is the clone's, as of its
  last fetch. The branch is looked for as `refs/remotes/origin/<branch>` and
  `refs/heads/<branch>`; either one in the target is enough. `<branch>` is
  `Store.ResolveTicketBranch`'s.
- A multi-repo blocker is met when every repo it builds in is. The repos are the ones its
  slices are placed in (`ready.Place`, in the project's order); with one repo, or none placed,
  every repo of the project. A project of several repos names the repo before each missing
  fact (`web: its PR is open (...)`); a ticket that builds in one repo names none.
- Which repo a recorded pull request is: when the ticket builds in one repo, every `pr` line
  is that repo's. Otherwise the latest `pr` line **on that repo**: for a GitHub remote the
  URL's owner and repository must be the remote's; for another remote (a local path, another
  server) the URL's repository must be the repo's name or the last part of its remote's path.
  A pull request on no repo is nobody's, and its repo reads as `no merge on record`.
- `ready.Merge` (`Published`, `Repos`) is a ticket's fact: `Met`, `Why`, `Via` (`pr`,
  `ancestry`, or `pr+ancestry`), `AsOf`.

## Where it is used

- **`internal/ready` `Tickets`**: `Ticket.Merge *Merge` is the fact a caller read for a ticket.
  A merged blocker is met by it. `Status.Why` (new) says what each blocker in `Blocked` is
  missing, keyed by the blocking ticket. A stacked blocker is met by publishing (T-19 owns
  stacked), and so is a merged one whose `Merge` is nil, which is the rule `jig recall` still
  runs on (below).
- **`jig next <ticket>`**: the `blocked_by` table gains a column, `blocked_by[n]{ticket,kind,fact}`,
  and the JSON `blocked_by` rows gain `fact` and `as_of` (RFC 3339, only when the host's
  answer is not from this run). The `phase` block (`reason`) and the help line name the same
  fact: `JIG-2 waits for JIG-1: its PR is open (<url>); run `jig next` to see a ticket that is
  ready`. The phase is derived with the same merge facts (`derivePhaseWith`), so `state`,
  `phase.ready` and `reason` agree.
- **`jig next` (the store)**: the `tickets` table is as it was; a new table follows it when
  something is blocked, `waiting[n]{ticket,blocker,fact}`, one row per blocker not met. The
  JSON rows' `blocked_by` carry `fact` and `as_of` too. Facts are read only for blockers of
  tickets that have not published, and only for blockers that have published and are not stacked.
- **`jig claim`**: `CLAIM_BLOCKED_MERGED` for a published blocker whose work has not merged.
  Message: `JIG-2 waits for JIG-1: <fact>`. Help, by the fact: `Merge <url>, then try again`
  (open); `Its pull request <url> was closed without merging: open the one that lands JIG-1 and
  record it with `jig publish JIG-1 --pr <url>`` (closed); `Check `gh auth status` and the
  network so <url> can be read, then try again` (unreadable); `Merge the pull request of JIG-1
  and record it with `jig publish JIG-1 --pr <url>`; if it merged already, fetch the repo so its
  origin has the merge` (nothing on record). A blocker that has not published keeps its message
  (`JIG-2 waits for JIG-1, which has not published`). Unattended: refused; attended: warned, as
  before. The blocker's phase prompt is appended as before.

## Cost: what is cached

`jig next` and the claim ask the host through `repohost.PRState` (one `gh pr view <url> --json
state`, the call the claim already made, 30 s limit) behind `mergefacts.PRCache`:

- **Per run**: a ticket's fact is read once (`mergefacts.Reader` memo), a pull request is asked
  about once.
- **On this machine**: `<jig home>/cache/pull-requests.json` (`home.PullRequestStatesPath`),
  `{"pull_requests": {"<url>": {"state": "MERGED", "at": "<time>"}}}`, written atomically
  (`store.AtomicWrite`), read again before each write so another jig's answers are kept. It is a
  cache, never a store record: deleting it costs the next reads; a file that does not parse
  holds nothing.
  - **`MERGED` is final**: kept for good, never asked again.
  - **Open or closed** stands for the run's `MaxAge` and is then asked again. A claim and
    `jig next <ticket>` use 0 (always ask: they are about one ticket and must be right). The
    listing `jig next` uses `listingMergeAge` = 2 minutes, so a listing of many tickets does not
    wait on the network for each blocker, and the answer it takes is dated: the fact ends
    `(as of 2026-10-25 14:05 UTC)` and the JSON row has `as_of`.
  - **Host cannot be asked**: the last answer is given, dated `(the host did not answer; as of
    ...)`; none kept means no state (then ancestry, then `could not be read`).
  - **A dead network is paid for once**: once asks that failed have taken 15 s in all, the host
    is taken as down for the rest of the run (a quick failure, such as a pull request the host
    does not hold, costs nothing).

A command that does not read merge facts (nil `mergeSource`) judges a blocker by `publish-done`
alone.

## Decisions I took

1. **A ticket that has not published is never met**, whatever its branch holds. It also keeps a
   branch cut from the target with no commit (an ancestor trivially) from reading as merged.
2. **The recorded pull request decides ahead of the branch** when the host can say; ancestry is
   the way left when there is no pull request or the host cannot be asked.
3. **Unreadable is not met.** A published blocker whose recorded pull request cannot be read
   (no `gh`, no network, nothing cached) and whose branch is not in the target is held, where
   the claim used to let it pass ("a host that cannot tell blocks nothing"). The brief's rule is
   positive evidence only. An unattended claim is refused on it; the help says what to check.
4. **The listing may be stale, a ticket may not.** 2 minutes for the store listing, 0 for a claim
   and `jig next <ticket>`.
5. **Repo attribution of a pull request is by the repository it is on** (owner and repository for
   GitHub; the repository's name for any other remote), since a `pr` line carries a URL and no
   repo. T-17 can write the repo into its `pr` lines and this reads that first.
6. **`repohost.PRMerged` is replaced by `repohost.PRState`** (the state, not just merged). Nothing
   else called it.
7. **The fake gh answers `pr view <url> --json state`** from `GH_STUB_PULLS` by the row's
   `html_url` (a row with none: its number). `fixture.GhPull.Repo` (new, default `repo`) names
   the repository in the URL, so a test can hold the pull requests of two repos.

## Findings outside the brief (not fixed)

- **`jig status`, `jig here`, the Stop hook's notes and the `GATE_NOT_GREEN` refusal's prompt**
  derive the phase with `derivePhase` (no merge facts), so they judge a blocker by `publish-done`
  alone and can say "Build JIG-2" while `jig next JIG-2` and the claim hold it for a merge.
  `jig next <ticket>` is exact, and every skill starts with it (decision 36). A follow-up can
  wire an offline reader into them: `newMergeReader` with `Ask` nil gives cached answers and
  ancestry with no network, and `derivePhaseWith` takes it.
- **`jig recall`** classes tickets with `ready.Tickets` and no merge facts: a ticket whose blocker
  published reads as ready there.
- **Ancestry is as fresh as the last fetch.** A blocker merged without a recorded pull request
  stays blocked until the clone fetches (`git fetch`); the claim's help says so. `jig next` does
  not fetch.
- **`skills/here/SKILL.md` line 42** says a ticket is ready "when it has a slice that is queued
  with every blocker green and nothing blocks the ticket"; the text could add that a blocker is
  met when its work has merged. (`lint/skills_test.go` limits skill sizes.)
- **The TUI** reads only `state` from `jig next`; `fact`, `as_of` and the `waiting` table are
  additive, and it could show the fact on a blocked ticket.
- **The mirror's checkpoint** (out of scope): `mergefacts.Reader.Of(ticket)` is what a checkpoint
  hook calls to learn a merge at the moment it syncs; the mirror already reads a ticket's pull
  requests from GitHub, and could record the merge it sees in the same place the PR cache keeps
  it, or in the store, so every command reads it with no network. `mergefacts` imports
  `internal/store`, `internal/journal`, `internal/ready`, `internal/repohost`, `internal/gitx`
  and `internal/project`, and not `internal/mirror`.
- `TestDigesterFlow` compares `git status` of the jig checkout before and after the flow, so a
  commit made in the checkout while the e2e suite runs fails it.
