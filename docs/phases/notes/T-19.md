# T-19 (GRAPH-5): stacked tickets start from the parent's branch, as advice

Notes for the DOCS-1 ticket. Nothing in README.md, ARCHITECTURE.md, CONTEXT.md,
DECISIONS.md or docs/adr was edited; the text they need is at the end. Issue
develdeco/jig#57, the digester chart's row "ticket-graph 4, A3". Branch `ph/T-19`.

A ticket stacked on another (`blocked_by: [{ticket: P, kind: stacked}]` in
ticket.yaml, ADR 0010) is built on the parent's branch before that work merges.
jig now says, for each repo the child builds in, where its branch starts and where
its pull request goes, writes that target into the pull request, and tells the
child's session when the parent's branch moved past it (a restack the session
makes with `git merge`) or the parent merged (a retarget). jig rebases nothing and
merges nothing. No new verb, no new flag, no schema bump; one new refusal code,
two new correction kinds, one new package.

## The rules (`internal/stack`)

For a ticket with a `stacked` blocker, per repo it builds in (`ready.BuiltIn`: the
repos its slices are placed in, in the project's order; the one repo of a project of
one; every repo when no slice is placed):

| Repo | start_from | pr_target |
|---|---|---|
| shared with a parent that has not merged there | the parent's branch as the clone holds it: `<branch>`, or `origin/<branch>` when only the origin has it or the origin's is ahead | the parent's branch |
| shared, the parent merged there | `origin/<target>` | `<target>` |
| the child's alone | `origin/<target>` | `<target>` |

- **Shared** is a repo the parent's own slices build in too (`ready.BuiltIn` of the
  parent's slices). With several stacked parents in one repo, the first in
  ticket.yaml order that has not merged there is built on; when all merged, the
  first, merged.
- **The parent's branch** is `Store.ResolveTicketBranch` of the parent against the
  repo's target. Its head in the clone: `refs/heads/<b>` and
  `refs/remotes/origin/<b>`; the local one wins when the origin's is in its history
  or they diverged, the origin's when it is ahead or there is no local one. When the
  clone holds neither, `start_from` is `origin/<b>` and the head is unknown.
- **Merged** is the parent's merge fact (T-18's `mergefacts.Reader`) for that repo:
  published, and the recorded pull request merged or, with none, the parent's branch
  tip in `origin/<target>`. `jig next <T>` and the publish ask the host (max age 0);
  `jig here` and the hook take what this machine kept (`cachedMergeReader`: the PR
  cache file, ancestry, no network).
- **Behind** (a restack): shared, not merged, the child has a branch, the parent's
  head is known, and the parent's head is not in the child's branch (their merge
  base is not the parent's head).
- **Retarget**: the parent merged in a shared repo, the child has a branch, and the
  child's branch does not hold `origin/<target>`'s head.
- A parent that is closed is not built on (its closure decides whether the child
  still waits); a ticket with no stacked blocker has an empty plan, read from its
  ticket.yaml alone (no slices, no git).

API: `stack.Read(Input{Store, Cfg, Clones, Merges}, ticket) (Plan, error)`,
`stack.Judge(Facts) Repo` (pure), `Plan{Ticket, Branch, Repos []Repo}` with
`Stacked()` and `In(repo)`, `Repo{Repo, Target, StartFrom, PRTarget, Parent,
ParentBranch, ParentRef, ParentHead, Merged, Head, Behind, Retarget}` with
`Shared()`, `stack.Merges` (`Of(ticket) (ready.Merge, error)`). It imports
`internal/gitx`, `internal/project`, `internal/ready` and `internal/store`.

## Where it is shown

- **`jig next <T>`**: a table after `blocked_by` and before `ready`, only for a
  stacked ticket:

  ```
  stack[2]{repo,parent,start_from,pr_target}:
    fixture-repo,JIG-2,JIG-2-parent,JIG-2-parent
    second-repo,-,origin/main,main
  note: the branch of JIG-2 moved past JIG-1 in fixture-repo: restack onto `JIG-2-parent` at `7242634157e3`: `git merge JIG-2-parent`; jig never rebases
  ```

  A merged parent's cell is `JIG-2 (merged)`. The notes: the restack above; `note:
  JIG-2 merged in fixture-repo: retarget the PR of JIG-1 to main and merge main
  (`git merge origin/main`)`; and `note: the clone of <repo> holds no copy of <b>, the
  branch of <P>: fetch it (`git fetch origin`) before <T> starts from it`. The
  `ready` table's `start` column is the plan's `start_from`, so the help's `git
  switch -c <branch> <start>` names the parent's branch. JSON: `stack` (absent when
  not stacked), rows `{repo, parent, parent_branch, parent_head, merged, start_from,
  pr_target, restack, retarget}` (`parent*`, `merged`, `restack`, `retarget` omitted
  when empty).
- **`jig here`**: a section `stack` (order 310, before verify) with the same table and
  notes; `--json` puts the rows under `sections.stack`. Best-effort: a plan that
  cannot be read shows nothing (`jig next <T>` says why).
- **`jig publish <T> --body`**: the `base` row (and the `bodies` table's `base`
  column, and the `gh pr create --base` of the help) is the pull request's target;
  the body of a repo whose pull request goes into the parent's branch has, after `##
  Intent` and before `## Part of`:

  ```
  ## Stacked on JIG-2

  JIG-1 builds on JIG-2: this pull request goes into `JIG-2-parent`, the branch of JIG-2. Once JIG-2 merges, retarget it to `main`.

  ```

  No section once the parent merged, or in the child's own repo.
- **Bare `jig publish`**: looks for the open pull request into that base
  (`FindOpenPR(branch, base)`) and opens one into it (`CreatePR(branch, base, ...)`).
  New refusal, before anything is pushed or written: `PUBLISH_PARENT_NOT_PUSHED`,
  `JIG-1 is stacked on JIG-2, whose branch JIG-2-parent is not on the origin of
  fixture-repo, so no pull request can go into it`, help `Publish JIG-2 first (its
  branch goes to the origin), then publish JIG-1 again`.
- **`verifydeliver.Deps.Stack`** (new seam, `func(ticket) (stack.Plan, error)`): set by
  `verifydeliverDeps` (cmd/jig/main.go) with the host-asking reader; nil (tests)
  reads none and every pull request goes into its repo's target.
  `publishTarget.base()` is the parent's branch for a shared repo whose parent has
  not merged, else the target. `RepoBody.Target` is that base.

## The correction notes (`internal/correct/restack.go`)

`correct.Input.Stack` (new, `func() (stack.Plan, error)`; cmd/jig/observe_correct.go
sets it with `locatedStack`, no network). Two kinds:

| Kind (correction line `outcome`) | Ref | Found | Told |
|---|---|---|---|
| `restack` | `restack:<parent>:<repo>:<parent head 12>` | each event, while the repo is Behind | while it holds; the line is written once per ref, so once per parent head; the core delivers a ref to a session once |
| `retarget` | `retarget:<parent>:<repo>` | each event, while the repo asks for a Retarget | once: offered again only to the session whose line it is (since its start), never to a later session |

Texts:

- `JIG-1 is stacked on JIG-2, whose branch moved past it: restack onto `JIG-2-parent`
  at `7242634157e3`: `git merge JIG-2-parent` in fixture-repo. jig never rebases: the
  merge is yours to make.` (the merge names the ref the head was read from, so
  `origin/<b>` when the origin's copy is the newer)
- `JIG-1 is stacked on JIG-2, and the parent merged in fixture-repo: retarget the PR
  to main and merge main (`git merge origin/main`).`

Both are `Enforce` notes like every correction: told to an attended session, a hold at
Stop (once each) for an unattended one. Journal line, as the other corrections:

```
{"event":"correction","outcome":"restack","ref":"restack:JIG-2:fixture-repo:7242634157e3","commit":"<parent head>","summary":"<text>","provenance":"jig","session":"...","harness":"claude"}
{"event":"correction","outcome":"retarget","ref":"retarget:JIG-2:fixture-repo","summary":"<text>","provenance":"jig","session":"..."}
```

A stack that cannot be read is an error of that detector only: the other notes still
come back (the cmd/jig source logs it).

**A merge is no scope drift** (`correct.Scope`): a commit with more than one parent is
not judged, as `Unsliced` already did not judge it. Without it, the `git merge` the
restack note asks for drew a scope-drift note for each parent file outside the child's
workspaces.

## Decisions I took

1. **Advice, computed on read, no record.** The plan is derived each time from
   ticket.yaml, the slices, the clones' refs and the parent's merge fact. Nothing is
   written but the correction lines.
2. **A new package, `internal/stack`**, read by `jig next`, `jig here`, the publish
   (through `Deps.Stack`, so `verifydeliver` asks no host itself) and the correction
   check (through `Input.Stack`, so `correct` knows nothing of projects or hosts).
   `ready.BuiltIn` is the one rule for the repos a ticket builds in;
   `mergefacts.builtIn` now uses it.
3. **The start point is a ref a person can pass to git**: the local branch when the
   clone has it and it is not behind the origin's, else `origin/<b>`; `origin/<b>` also
   when the clone holds neither (that is where it will be once fetched, and a note
   says to fetch).
4. **The restack is a state, the retarget an event.** "Behind" is true until the child
   merges the parent's head, so each session that works the child while it holds is
   told once (and a new head is a new note). A parent merges once: the retarget is
   told to the session it was found in and not repeated to later ones, which `jig next`
   and `jig here` (target `main`, the note) still show. The retarget asks only while
   the child's branch lacks the target's head, so a child that already merged the
   target is not told.
5. **Shown only for a stacked ticket.** The table and the JSON `stack` key are absent
   otherwise, so every existing output and golden is unchanged (the `ready` table
   already names `origin/<target>`).
6. **The publish asks the host about the parent** (max age 0), as the claim does: a pull
   request opened into a branch that merged goes nowhere useful. A stack that cannot be
   read refuses the publish.
7. **No pull request into a branch the origin lacks**: refused with
   `PUBLISH_PARENT_NOT_PUSHED` before the push, since jig pushes only the ticket's own
   branch.
8. **`skills/publish/SKILL.md`**: the hand-off's `gh pr create` said `--base main`; it
   says `--base <base>` now, and one sentence says the base is the parent's branch for a
   stacked ticket (4632 of 6000 bytes).

## Findings outside the brief (not fixed)

- **`ready.Tickets` meets a stacked blocker by publishing** (ready.go `unmet`), while the
  claim (`CLAIM_STACKED_PARENT_NOT_CLEAN`) and `internal/phase` meet it by a clean gate
  round. A child whose parent has a clean round but has not published is `blocked` in
  `jig next` and claimable (warned or not) at the claim. ADR 0010's rule is the clean
  round.
- **`jig here` and the observe hook open the store without `BranchesFrom`**
  (`openLocatedStore`, the observe core; only `resolveStoreChecked` sets it). In a
  project whose branches the tracker ids lead, their branch names (the stack section, the
  restack notes, the phase) can differ from `jig next`'s.
- **The gate and the body diff against `origin/<target>`**: a stacked child's review
  scope, its review notes' file coverage and `PUBLISH_NO_DIVERGENCE` include the parent's
  changes, while its pull request into the parent's branch shows only its own. A
  follow-up can diff against the base.
- **The observe core takes any HEAD move as the session's commit** (handlers.go `tool`):
  a restack that is a fast-forward (a child with no commit of its own) brings the
  parent's commits under the slice-missing check ("names no slice", or "carries
  `Jig-Slice: p`, but JIG-1 has no slice p"). A merge commit is exempt.
- **After the parent merges, a bare publish looks for the open pull request into the
  target**, so one that still goes into the parent's branch is not found and a second is
  opened. GitHub retargets such pull requests itself when the parent's branch is deleted
  on merge; the retarget note asks the session to. A follow-up could find the open pull
  request by its head alone.
- **Cost not measured**: for a stacked ticket the hook reads the plan at every tool call,
  prompt and stop (per shared repo about four `rev-parse` and two `merge-base
  --is-ancestor`, and the parent's merge fact from the cache and the clone); a ticket
  stacked on nothing pays one ticket.yaml read.

## CONTEXT.md

A candidate term, for DOCS-1 to judge: **restack** - the child of a stacked pair merges
its parent's branch at the parent's new head (`git merge <parent branch>`); jig asks for it
in a correction note and never performs it.
