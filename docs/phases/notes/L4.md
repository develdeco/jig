# L4 (T-24): the tracker tree, refreshed for the digester

Notes for the DOCS-1 ticket. Nothing in README.md, ARCHITECTURE.md, CONTEXT.md,
DECISIONS.md or docs/adr was edited; the text they need is at the end.

## What was built

The tracker tree: one record and one link per remote item, in the store root.

    trackers/<provider>/<scope>/<remote id>.yaml    the record
    trackers/<provider>/<scope>/<remote id>         a relative symlink to tickets/<id> or charts/<name>

GitHub's provider folder is `github`, its scope is the lower-case `<owner>/<repo>`
and its remote id is the bare issue number: issue 65 of develdeco/jig is
`trackers/github/develdeco/jig/65.yaml` and `trackers/github/develdeco/jig/65`.

- Paths are named once, in `internal/store/store.go` next to `TicketRelDir`:
  `TrackerRelPath`, `TrackerRecordRelPath`, `TrackerPath`, `TrackerRecordPath`.
- The tree code is `internal/store/trackertree.go` (records, index, write,
  remove), `trackerlinks.go` (links), `trackercheck.go` (the check) and
  `trackerlegacy.go` (the old places).
- The mirror (`internal/mirror`) reads and writes its records only through the
  store's tree. `internal/store/trackerids.go` (D18's branch binding) reads the
  tree too, and falls back to the old place.
- No new verb, no new flag, no journal line, no schema bump. A v2 store
  (`project.yaml`) and a v3 store (`store.yaml`) both work: the tree lives in the
  store root and neither config file is read by it.

## The record

    # This file is written by jig's GitHub mirror; edits here are overwritten.
    ticket: JIG-12          (or  chart: demo)
    repo: develdeco/jig
    issue: 65
    node_id: I_kwDO...
    item: PVTI_...
    prs: ...
    synced: ...

- The tree owns `ticket:` / `chart:` and the link, and nothing else. It decodes a
  record into those two keys and a YAML mapping node holding every other key in
  file order (`TrackerRecord.Fields`), and writes them back as they were. The
  mirror decodes `Fields` into its `githubRecord` and encodes it back.
- `ticket:` is resolved through `Store.ResolveTicket`: a record written under an
  old id belongs to the ticket that id is now an alias of. The mirror writes the
  current id.
- The header comment is the provider's: the tree takes it as an argument and
  drops the comment above the first key when it reads.
- An entry is checked before any write (`TRACKER_ENTRY_INVALID`): provider, scope
  parts and id are plain names (letters, digits, `.`, `-`, `_`), so an id read out
  of a file can never lead a write out of `trackers/`.
- Writing a record over another owner's record is refused
  (`TRACKER_ENTRY_TAKEN`): one remote item is one ticket's or chart's.

## The links

`Store.RebuildTrackerLinks` makes every link from the records alone, with no
provider and no network: each record that names a ticket or chart the store has
gets a relative symlink to its folder; a link that points elsewhere (or a plain
file where a link goes) is replaced; a link with no record beside it is removed;
a second run finds nothing to do.

- Every sync that is not a dry run runs it after it writes records, including a
  sync of a store with no `trackers:` github entry (the report is `NoTracker`,
  and the links are still made). So `jig trackers sync` is also the command that
  mends links on a store with no provider.
- The claim of a new issue puts the record and its link in the same commit
  (`Store.Claim`'s paths), so the committed tree is whole at every step.
- `core.symlinks` (git's setting for this clone, default on) decides whether a
  clone makes links (`Store.SymlinksOn`). With it off the rebuild touches
  nothing, the plain stand-in files git leaves are left as they are, and the
  Store warns once ("this clone makes no links in the tracker tree ..."), once
  per `Store` value, so once per command. A symlink the file system itself
  refuses (Windows without Developer Mode) counts as off. Every record is still
  there and the sync works the same.
- No directory junction is used (git would see a type change).

## The old places (fallback and move)

A6's mirror kept `<ticket>/tracker/github.yaml` and `charts/<name>/github.yaml`.

- Reading: `TrackerIDs` (branch names and bindings) uses the ticket's tree
  records first and the old place only for a ticket with no GitHub record in the
  tree, so an unmigrated store still binds. The mirror reads an old-place record
  too, for a dry run and for a record that arrives mid-sync from another clone.
- Writing: the mirror writes only the tree. The first thing a sync does (not a
  dry run) is `moveLegacyRecords`: each old-place record is moved into the tree
  (the `ticket:` / `chart:` key added, every other key kept, the old file and its
  empty `tracker/` folder removed), after the repo check
  (`MIRROR_REPO_CHANGED`) has passed for every one of them, so a refused sync
  moves nothing. The issue is then found by its record and updated in place.
- The move is a working-tree change. It goes in with the next checkpoint's commit
  like every record change but a creation (T-22's rule), not in a commit of its
  own. `SyncReport.MovedRecords` lists what moved and `jig trackers sync` and the
  checkpoint print it as a `moved` table (what, from, to).
- `jig store migrate` (internal/migrate) is untouched: it still keeps
  `tracker/github.yaml` inside the moved ticket folder, and the first sync of the
  migrated store moves it into the tree.

## What the sync does differently

- `collectItems` finds each item's record in the tree (`findRecord`): the record
  in the configured repository's folder, else the first the item has elsewhere
  (so `MIRROR_REPO_CHANGED` still fires), else the old place, else none. An item
  holds its `recordRef` by pointer, so a record created, moved or recreated
  mid-sync is the one every later step finds.
- A record that cannot be decoded makes the sync refuse (`MIRROR_RECORD_INVALID`,
  naming the file) before anything is written: it names no ticket, so the ticket
  would look like one with no issue and get a second. (Before, an unreadable
  record failed the sync the same way.)
- An issue gone from GitHub is opened again under a new number: the record
  moves to `<new number>.yaml` and the old record and link are removed.
- A record is named for the issue it holds: `writeRecord` writes
  `githubEntry(rec.Repo, rec.Issue)`. A spelling of the same place in another
  case is kept as it is (on a case-folding file system a move would delete it).

## jig validate

`jig validate <ticket>` (with or without `--check`) checks the whole tree through
`Store.CheckTrackerTree`, with or without a provider configured, and prints what
it finds in the `advisories` table under the verdict. The tree is a view of the
store around the ticket and not part of the brief, so it never refuses a brief
and never touches approval recording (`recordApproval` is unchanged).

| code | what is wrong | help |
|---|---|---|
| `TRACKER_RECORD_INVALID` | a record that cannot be read or decoded | restore it or remove it |
| `TRACKER_RECORD_ORPHAN` | a record naming no ticket or chart: neither key, both keys, or an id the store lacks | fix the key or remove the record |
| `TRACKER_RECORD_DUPLICATE` | two records in one scope for the same ticket or chart | keep the real one |
| `TRACKER_RECORD_MISPLACED` | a GitHub record whose file name is not its `issue:` or whose folder is not its `repo:`; a record in no scope folder | move it |
| `TRACKER_LINK_WRONG` | where the clone has symlinks: a link that is missing, is a plain file, or points anywhere but its record's ticket or chart | run `jig trackers sync` |
| `TRACKER_RECORD_UNMOVED` | a record still in a ticket or chart folder | run `jig trackers sync` |

- More than three of a kind print the first three and one row "and N more of the
  same kind" (`trackerTreeAdvisoryMax`), so an unmoved store is not a row per
  ticket.
- If the tree cannot be listed, one `TRACKER_TREE_UNREADABLE` advisory says so.
- Code: `trackerTreeAdvisories` in `cmd/jig/validate_store.go`, called by
  `validateAdvisories`. The problems and codes are the store's
  (`Tracker...` constants in `internal/store/trackercheck.go`).

## Decisions taken (and why)

1. Tree findings are advisories, not problems. A refusal would stop a planner
   approving an unrelated ticket's brief over a stale view; the brief's list says
   "reports", and the task allowed either.
2. The tree index is memoized per `Store` value (`trackerIndex`), kept in step by
   the tree's own writes (`putTrackerRecord`, `dropTrackerRecord`) and dropped by
   a pull, a change of aliases, an undone claim and `ReloadTrackerTree`. Without
   it `TicketBranch` (called per ticket in the sync) would read every record per
   ticket. `remoteLeads` (branch binding) and `CheckTrackerTree` read the tree
   afresh, as `remoteLeads` always read the records afresh.
3. `jig trackers sync` / the checkpoint rebuild links even with no provider (the
   brief: "the rebuild needs no provider"), which is also what makes the validate
   help ("run `jig trackers sync`") true for a store with no tracker.
4. A scope is lower-cased (`githubEntry`): GitHub names are case-insensitive.
5. Several GitHub records for one ticket in different scopes are allowed;
   `TrackerIDs` uses the first by path, the mirror uses the configured repo's.
6. The `moved` table in the sync report is new output, not asked for.

## Findings (not fixed, outside the brief)

- ADR 0011 (the store runs git in process): `gitx`'s in-process stage and commit
  declines any store whose index holds a non-regular entry or whose work tree has
  a symlink (`newScan`, `scan.walk` return `ErrUseCLI`), so once the tree has
  links every checkpoint stages and commits with the git program again. Correct
  but it gives back the Windows speed ADR 0011 bought, on a store with a tracker
  tree and symlinks on. A symlink-aware scan in `internal/gitx` would fix it.
- `cmd/jig/next.go` (`TicketForBranch` per branch) reads the whole tree for each
  branch it binds (as it always read every ticket's record): O(branches x
  records). PH-1 owns next.go; nothing to change there for this ticket.
- `TrackerIDs` has no config, so for a ticket mirrored in two repositories it
  takes the first record by path, not the `trackers: github: repo:` one. One repo
  per store is the only case today.
- `.claude/retrieval/T-22.md` still describes the old record places (history, not
  edited).
- The checkpoint warning "this clone makes no links" prints in every command that
  checkpoints on a store with records, when symlinks are off (as the brief asks:
  once per command). A Windows machine without Developer Mode sees it everywhere.

### CONTEXT.md

- **Tracker tree**: the folder `trackers/<provider>/<scope>/<remote id>` of a
  store: one record and one link for each remote item a tracker holds of the
  store's tickets and charts. _Avoid_: tracker folder, mirror folder.
- **Record**: the file `<remote id>.yaml` in the tracker tree. The tree owns its
  `ticket:` or `chart:` key and the link beside it; every other key belongs to the
  provider and is kept as the provider wrote it. The link is a view of the
  record, made again from the records on every sync.
