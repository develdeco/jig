# T-16 (REPO-3): a gate that covers every repo the ticket touched

Notes for the DOCS-1 ticket. Nothing in README.md, ARCHITECTURE.md, CONTEXT.md,
DECISIONS.md or docs/adr was edited; the text they need is at the end. Issue
develdeco/jig#54. Branch `ph/T-16`.

A gate round in a project of several repos reviews every repo the ticket's slices
build in: one lease, base, head and scope diff for each. A reviewer names its
files by repo, a finding's fix slice builds in the repo of the finding, and
independence is judged against the builders of every repo. No new verb, no new
flag, no journal line, no schema bump. `jig publish` still refuses a ticket that
builds in more than one repo (`MULTI_REPO_NOT_YET`, T-17); the gate no longer does.

## Which repos a round covers

`gateRepos` (internal/verifydeliver/roundrepos.go):

| Project | The round covers |
|---|---|
| one repo (or none that this machine knows: `primaryRepo`) | that repo, whatever the slices say. Nothing changes |
| several repos | the repos the ticket's slices build in (`ready.Place`), in the project's order, and no other. A ticket whose slices are all in one repo that is not the first is covered by that repo: the T-14 finding is fixed |
| several repos, no slice places in a repo | `VALIDATION_ERROR`: "none of T's slices builds in a repo of the project, so there is no repo to review". It is told after `GATE_NOT_GREEN`, so a ticket that is not built is turned away for that first |

A fix slice names its workspace as `<repo>/<id>`, so it places like any slice.

`gatePrepare` then does for each covered repo what it did for the one: restores
and acquires the repo's gate lease, points it at the copy of the branch to review,
resolves the manifest and runs the repo's oracles for the slices that build in it
(`runGateOracles`, the reuse of a recorded pass included: a pass is reused only
where its commit's tree is the lease head's tree, and a commit of another repo is
not in this one). The ticket's branch has one name in every repo, so it is
resolved once and held against the target branch of every covered repo
(`checkBranchAgainstTargets`). The commits jig built that a repo's copy of the
branch must hold are the verified lines of the slices that build there
(`builtIn`), not every verified line of the ticket. An adoption (`--branch`)
records the start sha of each repo. A failure in one repo says which: an
`*axi.Error` keeps its code and help and has `repo web: ` in front of its message
(`inRepo`). `GATE_NOT_GREEN` names the repo of the slice it stops at.

## The file name rule (what a finding's path is)

In a project of one repo a file is a path in the repo, as it always was.

**In a project of several repos a round names a file `<repo>/<path>`**, everywhere
it names one: a finding's `file` (`jig finding --file web/ui/page.go`, and `file`
in a `--result` file), `reviewed_paths` / `--reviewed`, `must_review`, the `open`
and `dismissed` lists, `findings.yaml`. The repo is the text before the first `/`
and must be one of the round's repos. A path of no repo (`ui/page.go`,
`docs/x.md`) is `REVIEW_INVALID`: `finding 0 file "ui/page.go" names no repo of
this round (api, web): write it as <repo>/<path>` (`jig finding` says the same
without the finding number). No `repo` field: one string says both, and every
list that holds files (coverage, clearing, `findings.yaml`) stays a list of files.

- The file is read at the head of its repo (`FileExistsAtRev` in that repo's
  lease), so "present at head or deleted in the scope diff" and the clearing of a
  finding whose file is gone are per repo.
- Its **workspace** is the one of that repo's manifest whose path holds it, named
  as a slice names it: `web/ui/page.go` is in `web/ui`; a root workspace `.` of
  `api` is `api/<id>`. A file in no workspace of its repo is an ask with no build
  target, as before.
- Its **oracle** must be one of that repo's manifest (`oracle "lint" is not a
  manifest oracle` where only the other repo declares it), and is required when
  that repo declares more than one. `TriageInput.Repos` (new) holds each repo's
  manifest, so `DefaultTriage`'s build-target check reads the finding's own.
  `GATE_NO_ORACLE` is per repo: "the manifest of repo web has no oracles".
- The **fix slice** is `fix-<round>-<workspace>-<oracle>` with the workspace
  `<repo>/<id>`: `fix-1-web-ui-test` builds in `web/ui` with web's oracle `test`.
  `jig next` lists it under `web`, and `jig verify` accepts its commit in web's
  clone only.
- An absolute path inside one repo's lease (what an agent reports for a file it
  read) is that repo's file (`roundFiles.relativize`).

The rule depends on the **project**, not on the ticket: a ticket whose slices are
all in one repo of a project of several repos still has its files named
`<repo>/<path>`. A ticket can gain a slice in another repo between rounds (a
person re-plans); the findings of the earlier rounds keep their names and the
round that follows reads them, which a rule per ticket would break.

## The request (review.json)

The request lists the repos, and keeps the old top-level fields for a round over
one repo. Chosen shape, and why: neither duplicates the other. A top-level
`head_sha` of a request that lists several repos would name one of them, so a
reader of the old fields would be handed the wrong repo; a request of a project of
one repo has no list, and is byte for byte what it was (`TestReviewRequestOfOneRepoMatchesItsGolden`
pins its bytes; `scope`, `base_sha` and `head_sha` gained `omitempty`, which only
leaves them out when empty, and they never are in that request).

A project of several repos (the store's copy; `worktree` is in the reviewer's copy
under the jig home and is left out of the store's, as the top-level one is):

```json
{
  "ticket": "JIG-1",
  "round": 1,
  "repos": [
    {"repo": "api", "branch": "jig/JIG-1", "scope": "full", "base_sha": "...", "head_sha": "...",
     "oracles": ["test"], "must_review": ["api/server/handler.go"]},
    {"repo": "web", "branch": "jig/JIG-1", "scope": "delta", "base_sha": "...", "head_sha": "...",
     "oracles": ["test"], "must_review": ["web/ui/page.go"]}
  ],
  "intent": {"source": "brief", "path": "..."},
  "slices_path": "...", "journal_path": "...",
  "oracles": ["test"],
  "oracles_passed": [{"oracle": "test", "workspace": "api/server", "command": "...", "reused_from": "..."}, ...],
  "open": [], "dismissed": [],
  "must_review": ["api/server/handler.go", "web/ui/page.go"]
}
```

- `repos` has an entry for each covered repo, in the project's order, also when the
  ticket builds in one repo of the project (a list of one). Its `scope`, `base_sha`
  and `head_sha` are those of that repo; a repo with nothing new in a delta round
  has `base_sha == head_sha` and `"must_review": []`. Its `must_review` names files
  as the round does (`<repo>/<path>`), so it is what the reviewer reports.
- The top-level `must_review` is the union (sorted), `oracles` the union of the
  repos' names (sorted, once each), and `oracles_passed` has every repo's runs with
  `workspace` as a slice names it (`api/server`).
- `scope`, `base_sha`, `head_sha` and `worktree` are not at the top of such a
  request.
- `recordings.json` has `heads` (repo -> head) in place of `head_sha`, and lists the
  recordings of every repo's history in one list.

`gate.round-N.open.yaml`: a project of one repo keeps `repo`, `copy`, `head`,
`base`, `scope`, `target`, `target_sha` and `lease` at the top (they gained
`omitempty`; the bytes of that record are pinned by
`TestOpenRoundFileKeepsItsTopForOneRepoAndListsSeveral`). A project of several
leaves them out and has `repos:`, an entry with those eight keys for each repo.
`report.yaml` is unchanged in shape: `target_sha` and `reviewed_sha` were already
maps by repo and now hold every covered repo (publish's `checkReviewedHead` already
read `reviewed_sha[repo]`). `GateReport.Scope` of a round over several repos is the
scope all had, else `mixed`; `GateReport.Copy` is the copy all had, else
`api: the clone's; web: origin's`.

## The commands

  `base`, `scope` and `worktree` rows for a project of several repos; a
  `repos[n]{repo,copy,head,base,scope,worktree,must_review}` table has them for
  each repo. The `stale` row names the repos that moved. The help adds: "This round
  covers the repos api, web: read each in its own worktree (the repos table), and
  name every file as <repo>/<path> ...". `target_sha` is sorted by repo.
- `jig finding --file`: usage text now says `<repo>/<path>` in a project of several
  repos; `jig review done --reviewed` the same.
- `jig here`: the `review:` block of an open round has `head_<repo>` and
  `copy_<repo>` for each repo (`verifydeliver.OpenStatus.Repos`, new) where it has
  `head` and `copy` for a project of one.

## Builders and freshness

`Builders`, `JudgeIndependence`, `LedgerReviewer*` and `Freshness` read the
journal and the machine ledger by **ticket** (and, for the ledger, the ticket's
branch, which has one name in every repo), and the hooks bind a session's work in
a nested repo to the ticket by that repo's branch (`locate`). So they already span
every repo of the ticket; no code changed. `TestGateJudgesIndependenceAgainstTheBuildersOfEveryRepo`
proves it: the builder of the api alone, the builder of the web alone and a session
that only edited a web file with its tools are each `REVIEW_NOT_INDEPENDENT` as the
reviewer of a round over both repos, `jig next` tells each builder `fresh: no`, and
a session that did none of it closes round 4 clean and independent.

## Decisions I took

1. **The file rule depends on the project** (several repos), not on the ticket's
   touched set - see "The file name rule". The price: a ticket in one repo of such a
   project has a list of one and `<repo>/` in front of its files.
2. **Request shape**: the list in a project of several repos, the old fields in a
   project of one, never both.
3. **One repo of several, not the first**: covered by that repo alone, found by
   `ready.Place` (not by the clone's location: the gate has no working directory).
4. **A fix slice's workspace is `<repo>/<id>` always in a project of several**, even
   when the ticket builds in one repo: a bare id that two repos declare (`lib`) would
   be ambiguous for `ready.Place`, which owns no slice.
5. **`BranchMoved` is `MovedRepos`** (a list of repo and tip): `review done`'s
   `REVIEW_STALE_HEAD` names the repo, `review context`'s `stale` row names the repos.
6. **`validateReviewResult`, `routeRound`, `buildFixSlices` take the round's files**
   (`roundFiles`) in place of one manifest or one lease; `ApplyRound` (exported, used
   by revieweval) keeps its signature and calls `applyRound`.
7. **The launched reviewer reviews one repo**: `NewLaunchedGateSource` refuses a
   round over several repos with a plain error. Only `internal/revieweval` links it
   and its cases are of one repo; `jig gate` and `jig review context` use the
   recorded path.
8. **The intent excerpt** of a round over several repos is matched against the files
   changed in all of them (the ticket's own sessions), and the search of local
   transcripts falls back to the first repo that finds a session.
9. **The recordings** of a round over several repos are listed from each repo's
   history (`gone` commits are per lease), in one `recordings.json`.

## Findings outside the brief (not fixed)

- **`jig publish` on a ticket that builds in one repo that is not the first** ships
  `Repos[0]` unless told `--repo web`; with no flag it is refused
  `PUBLISH_UNREVIEWED_HEAD` ("recorded the head it reviewed for web, but none for
  api"), which names the cause. T-17 owns `selectRepo`.
- **`Builders` misses a session that only committed in a shell**, in either repo: the
  hook's tool line for `git commit` carries no files, and the `git-commit` line comes
  from git's hook, which the e2e harness does not install (design note 39 already
  says so). A session that only ran `git commit` through its Bash tool is judged
  independent when the git hook is not installed. `Freshness` does see it
  (`commitsCode`); `Builders` could read the same way.
- **Findings an older jig recorded in a project of several repos carry bare paths**
  (only a ticket in one repo of an orchestrator could be gated before, on the first
  repo's lease). A round of this version cannot place them: they are left out of
  `must_review`, a `still_present` for one is refused as not present at head, and a
  finding not reported again would clear. It needs a ticket of a project of several
  repos that was gated before T-16 and has findings still open, which is rare: T-14
  refused every gate of a ticket that builds in more than one repo.
- **A fix slice's goal prints the file as the reviewer named it**
  (`web/ui/page.go:4`), while the builder's clone has `ui/page.go`. The slice's
  workspace and `jig context` say the repo; the goal could say it too.
- `jig doctor`, the TUI and the MCP tools read none of this; nothing to change.

## CONTEXT.md

**Repo-qualified file**: in a project of several repos, how a gate round names a file:
`<repo>/<path>`, the repo being one the ticket's slices build in. A finding's file,
`reviewed_paths` and `must_review` are all named so; in a project of one repo a file is a
path in the repo. A finding's workspace is named `<repo>/<id>` the same way, as a slice's
is (T-14). _Avoid_: bare path (in a project of several repos).
