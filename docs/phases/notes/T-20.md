# T-20 (GRAPH-6): priority order and the overlap warning across tickets

Notes for the DOCS-1 ticket. Nothing in README.md, ARCHITECTURE.md, CONTEXT.md,
DECISIONS.md or docs/adr was edited; the text they need is at the end.

Digester decision 42 (the A4 row), issue develdeco/jig#58. A person or a crew's scheduler
asks `jig next`, with no ticket, what to start, and gets the ready tickets in the owner's
priority order, a flag where two hold the same rank, and a warning where two would build in
the same workspace. Nothing launches anything (decision 16). No schema bump: `rank` is an
optional key of ticket.yaml schema 1.

## The field

`rank:` in `<ticket>/ticket.yaml`, an optional integer.

- `store.Ticket.Rank *int` (nil is "no rank"; 0 is a rank). `ticketFile` carries
  `rank,omitempty`, read and written by `ReadTicket`, `writeTicketFile` and so by every
  `mutateTicket` caller: a rewrite for any other field (branch, aliases, the migration) keeps it.
- Reading accepts any integer. `rank: soon` is the same `TICKET_RECORD_INVALID` an unknown key
  gets, so `jig validate` reports it as "ticket.yaml could not be read" and accepts every integer.
  `jig validate` has no rank rule of its own.
- `Store.SetTicketRank(ticket, *int)`: sets or (nil) removes the key through `mutateTicket`.
  Setting creates the record when the ticket has none; clearing a ticket with no record writes
  nothing. `Store.TicketFileRelPath(ticket)` is the record's store-relative path, the one
  `Claim` stages. `WriteTicketBranch`'s doc no longer says it is the only update of a record.

## The verb: `jig rank`

`cmd/jig/rank.go`, registered in its own `init()` (Order 111, after `ticket`).

| Call | Effect |
|---|---|
| `jig rank <T> <n>` | writes `rank: n` into T's ticket.yaml and commits that file alone |
| `jig rank <T> --clear` | removes the key and commits that |
| flags | `--clear`, `--store`, `--project` (the usual two) |

- `<n>` is a whole number from 1. `0`, a negative number (a leading `-` parses as a flag), a
  fraction, a word, a missing rank, a rank with `--clear`, more than two arguments and a
  ticket that is not in the store are `VALIDATION_ERROR`s that write nothing. A hand edit may
  hold any integer (see above); the verb writes 1 and up.
- The ticket may be an alias (`resolveTicketArg`, which prints "OLD is now NEW").
- It runs `st.Sync()`, reads the record, and when the rank is already what was asked says
  `result: unchanged` and makes **no commit**. Otherwise it commits through `Store.Claim`, as
  `jig ticket new` does: `write` calls `SetTicketRank` and returns the one path
  `tickets/<T>/ticket.yaml`, so the commit holds that record alone; with an origin it is pushed
  at once and a rejected push is undone and retried (the write re-reads the record, so it keeps
  what another clone changed). Commit subjects: `JIG-2: rank 4`, `JIG-2: clear rank`. Then
  `st.RunCheckpointHook()`, as `ticket new` does, since `Claim` never runs it.
- Output:

  ```
  rank:
    ticket: JIG-2
    rank: 4            # "none" after --clear
    result: recorded   # or unchanged
  help[1]:
    Run `jig next` to see the ready tickets in priority order
  ```

## The ordering rule: `jig next` with no ticket

The `ready` tickets (state `ready`: not blocked, not published, a slice ready to build) are
ordered by `ready.ByPriority`:

1. ranked tickets by rank ascending (any integer; lower first);
2. then the unranked, after every ranked one;
3. equal ranks, and the unranked among themselves, keep the store's id order
   (`Store.TicketIDs`: by key, then by number, so JIG-2 precedes JIG-10), because the sort is
   stable over the id-ordered list.

A ticket that is blocked, active, green, new, done or invalid is not in the order, and its rank
is nobody's to share. The `tickets` table is unchanged (id order, same columns), so the TUI's
roster and the existing tests read it as before.

### Output (human)

After the `tickets` table:

```
next[3]{ticket,rank,title}:          # the ready tickets in the order to start them; "-" for no rank
  JIG-2,2,Second
  JIG-3,2,Third
  JIG-1,-,
warning: rank 2 is shared by JIG-2 and JIG-3: they are ordered by id      # one line per shared rank
warning: ready tickets build in the same workspace
workspace_overlap[2]{repo,workspace,tickets}:
  second-repo,gamma,JIG-2+JIG-1
  fixture-repo,alpha,JIG-3+JIG-1
```

The `help` block: "Run `jig next <first of next>` ..." (the first ticket in priority order now),
and when there are workspace overlaps "Do not run tickets that share a workspace
(`workspace_overlap`) at once: start the one that comes first in `next`, and the other after it",
and when several tickets are ready and one has no rank "Order the ready tickets with
`jig rank <ticket> <n>`: the lowest rank starts first".

### Output (`--json`), all additive

```
{"tickets":[{"id":"JIG-2","title":"Second","state":"ready","rank":2,"ready":["x1"]}, ...],
 "next":["JIG-2","JIG-3","JIG-1"],
 "shared_ranks":[{"rank":2,"tickets":["JIG-2","JIG-3"]}],
 "workspace_overlaps":[{"repo":"second-repo","workspace":"gamma","tickets":["JIG-2","JIG-1"]}],
 "overlaps":[...]}
```

- `tickets[].rank`: the ticket's rank, absent when it has none (blocked and other tickets carry
  theirs too).
- `next`: the ready ticket ids **in priority order** (it was in id order).
- `shared_ranks`: only among ready tickets, lowest rank first, each with its tickets in the
  order of `next`. Omitted when empty.
- `workspace_overlaps`: omitted when empty. `overlaps` (D3: local branches changing one file) is
  unchanged and independent.

## The overlap warning across tickets

For each pair of **ready** tickets (taken in priority order, so a pair names the one to start
first first) that build in the same workspace of a repo, one entry per pair and workspace.

- A ticket's footprint is **all** its slices' workspaces, not only the ready ones: its later
  slices will build there too. `ready.Sites(slices, placement)`: each slice's workspace placed by
  `ready.Place` over `ready.ProjectRepos(cfg, mp.Clones)` (the same placement `jig next <T>`
  uses), as (repo, the workspace's id in that repo's manifest), each once. `fixture-repo/alpha`
  (the qualified form) and a bare `alpha` that only fixture-repo declares are the same site.
- A workspace that no repo declares, or that several do, is no site (it is not known whose it
  is): it overlaps nothing. `jig next <T>` already notes those.
- In a project of one repo every workspace is that repo's, as `Place` has always had it.
- Same workspace name in different repos is no overlap.
- Pairs are in the order of `next`; for a pair, the sites in the order the earlier ticket's
  slices name them. A workspace shared by three ready tickets gives three entries.
- The manifests are read (`ProjectRepos`) only when two or more tickets are ready.

## Decisions I took

1. **Shared ranks and overlaps are judged among the ready tickets only.** A ranked ticket that
   waits on a blocker cannot be started, so its rank does not make an order ambiguous now.
2. **The `tickets` table is not reordered and gains no column.** The new `next` table carries the
   order; the existing assertions and the TUI roster read `tickets` as before.
3. **Rank values: 1 and up from the verb, any integer on read.** A leading `-` cannot be passed
   as a positional anyway, and 0 reads as "no rank" to most people.
4. **`unchanged` makes no commit.** `Claim` would find nothing to stage; the verb says so first.
5. **Workspace overlap is by (repo, workspace id), not by file.** It is a prediction from the
   brief's slices, where D3's `overlaps` is the fact from branches.
6. **The `here` skill says it** (skills/here/SKILL.md, 4729 of 6000 bytes): the `next` table, the
   shared-rank warning, `workspace_overlap`.

## Findings outside the brief (not fixed)

- **Nested workspace paths are not compared.** `manifest.Workspace` has a `Path`; two workspaces
  of one repo whose paths nest (a `root` workspace at `.` and `web` at `web/`) are different ids
  here, so tickets building in them are not warned of. Comparing paths needs the manifests'
  paths in `ready.Repo` (today only the ids and the oracle names are kept).
- **`jig next <ticket>` and the TUI do not show the rank.** The ticket view's JSON has no `rank`,
  and the TUI roster reads only `state`; both could, additively.
- **`jig recall` lists open tickets without their rank.** The planning context could order or
  mark by it.
- **A rank in a writers store** goes through `Claim` on the writer's branch like a mint, so it is
  committed there; not exercised by a test (the e2e fixture is a single-main store).
- A rank is per store, not per person: two clones ranking the same ticket race, and the second
  `Claim` re-reads and overwrites (last writer wins), as for any ticket.yaml field.
