# Overlap advice is a real conflict, shown where the session looks (GRAPH-24)

Ambiguous: the store-level overlap list named every file two branches both changed, and a project with one workspace listed every pair of ready tickets, so neither said whether two tickets would really collide.

Chosen (all defaulted in the brief):
- Cost: only pairs of tickets that share a changed file are merged, once per pair per repo (`gitx.MergeConflicts`, over `git merge-tree --write-tree --name-only`). A failed call leaves the pair `untested`, never an error. No cap.
- Refs: a ticket's local branch; `origin/<branch>` stands in only when the ticket has no local branch here. Local wins when both exist.
- Store-level `jig next`: the `overlap` table gains a `conflict` column (`conflict`, `clean` or `untested`) and `--json` `overlaps[]` gains `conflict` and `files`. The warning line no longer says "local".
- The ticket in hand: `jig here` and `jig next <T>` print a warning, a `conflict` table (repo, ticket, file, branch) and a help line; a clean sharing pair is one info line there only. `jig gate` and `jig publish` print the conflict block before they do anything else and nothing for a clean pair. The block's help names the ticket of the pair that comes first in next order (rank, then id): the later one is told to stack on it, the first is told which ticket to stack on it.
- JSON: `jig here --json` and `jig next <T> --json` carry a `conflicts` array (omitted when empty). `jig gate` and `jig publish` have no `--json`, so their `conflicts` array is not built; the pull request body carries nothing.
- Never a refusal: exit codes, gate rounds, journal verdicts and publish refusals are unchanged.
- One workspace: `workspaceOverlaps` (and so the chart's `setWorkspaceOverlaps`) returns none when the slices of every ticket of the store, placed as `jig next <T>` places them, build in one site or none (r1-f3). A site is a repo and a workspace id, so two repos' `root` are two; a workspace id that holds a slash stays whole. Declared but unused workspaces do not count: the brief judges by the slices. The chart skill stacks on `conflicts` rows of `jig next <T>` at each wave's start and after its hand-backs, before Publish (r2-f3): a wave's tickets have no commits at its start, so the rows that matter appear once its builders hand back. It stacks with `jig depend --kind stacked`. Cost: before any branch exists, a chart's first wave is not pre-stacked.
- Tests that relied on the old rule give one ticket a second workspace so the project has two.
- Open tickets only (gate rounds 1 and 2, r1-f1): a branch bound to a closed ticket, or to no ticket record, is left out before pairing. A published ticket counts only when its merge reader positively says a pull request is open: a state it cannot tell (no pull request recorded, nothing cached, a squash merge the clone cannot see) leaves it out, the way an untestable pair says nothing. `jig here`, gate and publish use the cached reader, which asks no host. In this project's own clone the round-2 head paired nine merged tickets in 17 s; the fix pairs only the one live ticket in under 3 s.
- For the ticket in hand only its own pairs are merged (r1-f2); the store-level listing still tests every sharing pair.
- Chart skill (r1-f7): the lines the cap had cut are back, and the new instruction replaces the old paragraph within 6000 bytes by tightening the wording of a few other lines.
- Not changed (r1-f8): a ticket with several live branches is merged by its alphabetically first one.
- Left as notes (round 2): the store-level `jig next` filter and the `--json` `conflicts` array of `jig next <T>` have no test of their own (r2-f1, r2-f2); the store-level clean row has a test, but r1-f5's untested row is left as a note with no test.
- Session-start cost (after gate round 5, PR review): `jig here` runs at every session start and the conflict advice made it about six times slower. Timed on the real store from a ticket worktree, three runs each, in one session: the installed jig 305-311 ms; this branch before the fix 2021-2149 ms; after 421-441 ms. Where the time went, in order: a tracker-record read for every branch that leads with an issue number (`TicketsForBranches` now reads them once for all branches); the full journal of each of ~50 bound tickets decoded to learn whether it published (`journal.HasEvent` and `journal.PRURLs` read the file's text and decode only the lines they need); the full merge fact of each published ticket, with its clone and slice reads (the open filter now reads the recorded pull requests and their states alone); and git processes run one after another (one `for-each-ref` for both ref kinds, one `git diff base...branch` for each branch in place of a merge-base and a diff, the diffs started together). A ticket that shares no file with another makes no merge: pinned by a merge counter in the scan test.
- Round 6: a published ticket is judged by the latest recorded pull request of each repo, as the merge fact does (an earlier one that still reads open does not keep it open); the branch diffs run at most min(4, half the processors) at a time. `jig here` re-measured on the real store: 418-517 ms against the installed jig's 301-310 ms.
