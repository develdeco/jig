# Claude Code's global pieces go in CLAUDE_CONFIG_DIR when it is set (RUN-44)

Ambiguous: Claude Code reads its user settings, skills and memory from `$CLAUDE_CONFIG_DIR` in place of `~/.claude` when the variable is set, and jig wrote and checked its global Claude Code pieces in `<home>/.claude` alone. The build of `jig setup` (DECISIONS.md, ADR 0032's build) had chosen not to honor the variable, because a test run on a machine that has it set would write to the real directory, and had `jig doctor` only note it. A person running one Claude Code directory per account then got a doctor that called every global piece missing and a setup that wrote where no session reads.

Chosen:
- D1: Claude Code's user directory is `$CLAUDE_CONFIG_DIR` when it is set and not empty, else `<home>/.claude`. It holds the global skills (`skills/`), the global hook entries (`settings.json`) and the global hint (`CLAUDE.md`), and it is the claude harness's `ConfigDir`; the hidden `jig skills install` defaults to its `skills/` too. `~/.agents/skills` and every other harness's files stay under the home; project files do not change.
- D2: `cmd/jig` reads the variable once per command through `env.getenv` (`env.userDirs`), and a relative value is made absolute against the env's working directory, not the process's. `internal/setup` takes the result as a value, `setup.UserDirs{Home, Claude}`, and reads no environment; a `UserDirs` with no `Claude` falls back to `<Home>/.claude`, so a caller that knows only the home keeps the old paths. `Harness.ConfigDir`, `Harness.GlobalFile` and `HintFile` take a `UserDirs` in place of the home string, and `UserDirs.SkillRoots` is the one list of the global skills roots that the installer and doctor share.
- D3: `jig doctor` keeps one note, only when the variable is set, and it now says which directory was checked: `CLAUDE_CONFIG_DIR is set: Claude Code's skills, hooks and hint are checked in <dir>`. With it unset the report is as before.
- D4: This reverses the earlier call on its own grounds, which a guardrail now removes. `cmd/jig` tests already read only the variables their `env` is given. e2e's `jigEnv.environ()` started from `os.Environ()`, so it now drops `CLAUDE_CONFIG_DIR` unless the test sets it through `with`, as it drops `JIG_GITHOOK_WRAPPED` and the harness session id; that landed as its own slice before jig read the variable anywhere new. `internal/claudetest.Serve` sets it to a temporary directory for the live CLI tests, which build the real `claude`'s environment from `jigEnv.environ()`, so the guard stripped it and the CLI fell back to the host's `~/.claude` (gate round 1, r1-f1); `Serve` now returns that directory and both live tests pass it through `with`.
- D5: No ADR: nothing beyond D1 binds later design. ARCHITECTURE.md's installation table, the README's setup section and the usage strings of `jig setup --global`, `jig skills`, `jig hooks` and `jig hint` name `$CLAUDE_CONFIG_DIR` beside `~/.claude`.

Checked: `internal/setup` tests pin `UserDirs`, the harness files and the hint files with and without a Claude Code directory of its own; a `cmd/jig` test resolves the variable set, unset, empty and relative, and another installs and uninstalls the global skills, hooks and hint with it set, finds nothing in `<home>/.claude`, and has doctor report them, the shared agents skills and the helpers installed with the note (and Claude Code's missing without the variable), with each skills row read from its own root and the helpers row from both (gate note r1-f3); e2e's `TestSetupGlobalFollowsClaudeConfigDir` runs `jig setup --global --artifacts --yes` and `jig doctor` against the built binary with the variable set; `TestJigEnvDropsTheClaudeConfigDir` pins the guardrail.

Follow-up: the intent reader still looks for transcripts in `<home>/.claude/projects` only (ADR 0012's known limit); resolving it from the same `UserDirs` beside `Deps.UserHome` is the natural next step. Other harnesses' relocation variables (`CODEX_HOME` and the like) are not honored.
