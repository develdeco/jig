# D16: `jig tui`

Branch `dg/D16`, from the `digester` tip 28860c8 (S0b, S0a, D15, D8, D10 merged, and
the rest of the first waves), then merged with d46f88b (D2 and D18 landed; the last
digester merge). Five screens (project, ticket, build, review, slice)
over the event stream `jig events` prints, acting only by running verbs. A ticket
built by hand goes from its first commit to a published pull request without the
person leaving them. The package reads no store; a test pins that.

## Verb

```
jig tui [T] [--store P] [--project N]
```

Registered in `cmd/jig/tui.go`, Order 360, help row "browse a store's tickets in the
terminal and drive them: answer, decide asks, gate, publish". `T` (an id or an alias)
opens that ticket's screen first, with the project one step back; at most one. It
resolves the store like every store verb, refuses before drawing anything when the
ticket or the store is not there (`VALIDATION_ERROR`, exit 2), and ends with exit 0
on `q`, Ctrl-C, or an interrupt (`e.ctx`).

Where stdout is a terminal the screens take the alternate screen (bubbletea, raw
keys). Where it is not (a pipe, a file, a test) nothing is drawn over: each screen is
printed whole when it changes, followed by a line holding a form feed (`\f`), and keys
are read from stdin as they arrive. That is the mode the e2e drives. Colors follow the
output: none on a pipe, and `NO_COLOR` is honored by termenv.

## Keys

| Key | Does |
|---|---|
| `↑` `↓` `pgup` `pgdn` `home` `end` | move the cursor |
| `enter`, `→` | open the row: ticket (main), build, review or publish (ticket), slice (build), a question's slice, an ask's review |
| `esc`, `←`, `backspace` | back |
| `a` | answer a question: `jig answer --as person [--store S] T qid -- <text>` |
| `k` / `d` | keep / dismiss an ask: `jig triage T id keep\|dismiss` |
| `g` | `jig gate T` |
| `p` | asks "approve the reviewed head, push it and open the pull request?"; on `y` or enter: `jig publish T --approve`, then `jig publish T --yes` (a refused approval stops it) |
| `t` | a tail pane: the latest stream lines of the screen's scope |
| `r` | read the ticket list and the open ticket's status again |
| `q`, Ctrl-C | quit |

`a`, `k` and `d` act on the row under the cursor when it is a question or an ask; else
on the only open question (undecided ask) of the ticket (of the slice, on the slice
screen); else they say which to pick. The answer is typed on a line at the foot; enter
sends, esc abandons, an empty answer is not sent. Printable keys that arrive in one read
(a script writing `aOK\r`) are pressed one at a time; a paste stays text.

## What the screens read

- **The stream**: `events.Follow` over every journal of the store and the ledger lines
  about them (`cmd/jig/tui.go`'s `eventsSource`). The `Source` interface is just
  `Follow(ctx, emit)`. Per ticket the model keeps the journal whole, sorted by instant
  (a late line from a merge is placed where it belongs), and the latest ledger lines.
  Ticket phase, slice timeline, questions (text from the `question` line, answered by an
  `answer` line), gate rounds (`gate-open`, `gate-round`, `gate-clean`), triage decisions
  and the publish (`pr-body`, `publish-approved`, `pr`, `publish-done`) are read from it.
- **`jig status T`** for the store's word on the ticket: its slices with state, tries
  and blockers, its questions, the outstanding asks (id, risk, file:line, title, why)
  and the help line shown as `next`. Read when a ticket screen opens and again when a
  line for the open ticket arrives or a command of the screens ends. Parsed by
  `internal/tui/axi.go` (a reader of the axi register, tested against what
  `internal/axi` writes).
- **`jig next --json`** for the ticket list: ids, titles and states, in the store's
  order; read at the start and when the stream shows a ticket it does not know.
- A read that fails is made again, 5 times, 300 ms apart, before the screens say so:
  on Windows a read can meet the instant another process renames a store file over
  (the same window D8 documents for the other store readers). Without it the status of
  the open ticket was lost once in a run of the e2e and the screen stayed stale.

## Actions run as the person at the keys

`tuiRunner` runs a verb through `run` in process with `stdinIsTerminal` true for the
reader it hands the verb, so what the verbs record by "person at a terminal" (a triage
line, `publish --approve`, an answer without `--as`) is the person's, whatever the
screens' own stdin is (a pipe in the e2e). The answer passes `--as person` as well, as
the brief says. Every command carries `--store <resolved root>`, so a directory change
cannot move it; the screens show the command without that flag (`jig answer --as person
JIG-1 q-001 -- text`) with its output, a tick or a cross, in a panel above the keys until
the next navigation.

A keep from the screens passes no `--reason`, `--workspace` or `--oracle`; an ask whose
file lies in no workspace still needs `jig triage ... --workspace W --oracle O` from the
command line (the verb's own refusal shows in the panel).

## Journal and ledger lines

None of its own. It writes through the verbs: `answer` (provenance `person`, the typed
text as `summary`), `triage` (`ref` the finding id, `outcome` keep or dismiss, provenance
`person`), `gate-open`, `publish-approved` (provenance `person`, `commit` the reviewed
head), `pr`, `publish-done`. It reads the lines listed above and nothing else of the
journal's schema; an event it does not know is drawn by name and outcome.

## Package

`internal/tui`:

- `model.go`: `Model` (a bubbletea model, `New(Config)`), `Config`, `Source`, the keys,
  the stream plumbing (`Init` starts one goroutine that follows the source into a
  channel; `waitEvents` takes what is there in one update), retry of failed reads.
- `runner.go`: `Runner func(args []string) (string, int)`, `serial` (one command at a
  time), `exec` (a key's command or its two), `refreshStatus`, `loadRoster`.
- `state.go`, `statusinfo.go`, `axi.go`: the world (tickets, journals sorted, ledger
  lines bound to a ticket by session), the derivations (phase, slices, questions,
  rounds, asks, publish), the readers of `jig status`, `jig next --json` and the axi
  register.
- `view.go`, `screens_{main,ticket,build,review,slice}.go`: `View` is plain text of
  exactly the terminal's height: header, body windowed around the cursor, the last
  command's panel, the tail pane, the foot (keys wrapped to the width, the answer
  prompt, the publish question).
- `icons.go`: `Look{Icon, Color}` per state (`StateQueued` ... `StateFail`), `styles`
  over a `lipgloss.Renderer`. Every state has its own glyph; a few states that are one
  thing in two places share one (round findings and the ask in it, published and a
  command that worked, stalled and a command that failed). Colors are ANSI 256 indexes.
- `program.go`: `Run(ctx, cfg, in, out, screen)`; stdin that is not a terminal is hidden
  behind a plain reader, or bubbletea would open the terminal for its keys (and on
  Windows fail to read a pipe as the console).

## Decisions

- **Plain frames on a non-terminal** instead of bubbletea's inline renderer: that
  renderer redraws by moving the cursor, which a pipe shows as noise and a test cannot
  read. The brief's "non-alt-screen output" is met; the golden `View`s are the same text.
- **`p` asks first.** It approves a head for a person and pushes it; one stray key should
  not. The brief lists `p` as approve then `--yes`; the question is the person's
  approval being a person's.
- **Status and roster through verbs**, not a store read: the slice states live in
  `slices/<id>.state` and the asks in `gate/round-N/findings.yaml`, neither in the
  stream. `jig status` is the golden-tested surface for both.
- **Order of keys by screen**: the footer lists only keys that do something there; keys
  that do nothing on a screen are not bound to a message (they say what to pick).
- **Tail** is a pane, not a screen: the five screens are the brief's.
- **What `jig status` adds later is ignored, not broken**: the reader takes the tables it
  names and leaves the rest, so D2's `driver:` block (who drives the ticket) does not
  show on the screens yet. A one-line addition to the ticket screen, for whoever wants it.
- **`--store`/`--project`** are flags (the house ones); `--all` is not offered.

## ADR impact (for D1)

ADR 0032 can say: the terminal screens are a reader of the event stream and of two
verbs and an actor through verbs; they hold no store and no state the journal does not
carry, so a hand-built ticket, a `jig run`-less builder and a person at another machine
all show on the same screens, and every key leaves the lines its command leaves. The
person at the keys is a terminal: provenance `person`.
