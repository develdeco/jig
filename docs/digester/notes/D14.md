# D14: `jig mcp`

Branch `dg/D14`, from the `digester` tip 830b0b4 (S0b, S0a, D7, D8 and the
other digester tickets merged). `jig mcp` is a Model Context Protocol server
on stdio. Nine tools, one per jig command (here, next, context, claim, ask,
answer, note, observe, status), each of which runs that command in the server
process and returns what it printed. `ask` puts the question to the person
through the client when the client can ask them, and falls back to the record.

## Verb

```
jig mcp [--store <path>] [--project <name>]
```

Registered from `cmd/jig/mcp.go`, Order 370, FlagSet `mcp`. It takes no
positional argument (VALIDATION_ERROR, exit 2). With `--store` or `--project`
every tool works on that store whatever directory the server runs in; without
them each tool resolves the store from the server's working directory, as the
command does. Exit 0 when the client closes its input, 130 at the first
interrupt, 1 when the stream breaks (a message over 16 MiB, a read error).
Stdout carries the protocol and nothing else, so an error after the server
starts goes to stderr; a person at a terminal gets one stderr line saying an
MCP client starts this.

Pins. The flags are handed on by what each command declares in its help row:
`--project` to a command that has it, `--store` to one that has that, and a
`--project` given to a command with only `--store` (here) is the store the
machine map holds for it, read at each call. `observe` has neither flag and is
not pinned. The model cannot override a pin: no tool has a store or project
argument.

## Tools

Every tool turns its arguments into the command line the command parses
(positionals, flags, a bare `--`, free text) and runs it through `run`, so a
tool and its command cannot differ. A tool result is the command's stdout as
one text content; `isError` is true when the command exited non-zero, so the
model sees the `error:` / `code:` block of a refusal. A command that printed
nothing returns `(no output)` (`here` outside a project does that). An
argument that is unknown, of the wrong type, missing, or outside an enum, or a
ticket or question id that begins with a dash, is a failed tool with a message
that names the fix, and nothing runs. An unknown tool name or malformed
`tools/call` params is a JSON-RPC error (-32602).

| Tool | Arguments | Command |
|---|---|---|
| `here` | ticket, slice, session, explain, json | `here` |
| `next` | ticket, topology, json | `next` |
| `context` | ticket, slice, json | `context` |
| `claim` | ticket, slice, session, unattended, take, release | `claim` |
| `ask` | ticket, slice, session, **question** | `ask` (see below) |
| `answer` | ticket, **question_id**, **text** | `answer` |
| `note` | ticket, slice, session, **text** | `note` |
| `observe` | **event**, session, agent, cwd, tool, command, exit, files, model, transcript, stop_active | `observe --event ...` (neutral, no harness payload) |
| `status` | **ticket** | `status` |

Bold is required. Free text (question, text) goes after `--`, so it may begin
with a dash. `here`, `next`, `context` and `status` carry `readOnlyHint` (jig's
own bookkeeping aside: `here` records a recognized clone in the machine map,
`context` a ledger line); the rest do not. `observe` returns the neutral JSON
(`context`, `message`, `block`) or `(no output)`. The `answer` tool is an
agent's: it has no `--as`, so its line is `Provenance: agent`; the person's
provenance is reached only by accepting the form (below). `ask` does not offer
`--wait`: a blocked tool call would hold the server's one-command-at-a-time
lock, and the answer is read with `context` (its `questions` block) or arrives
by the hooks.

## `ask` and elicitation

1. Run `ask` (records the question, parks the slice, pushes). A failure is the
   tool result, `isError`, and nobody is asked.
2. If the client declared the form elicitation capability at `initialize`
   (`capabilities.elicitation` present and either empty or listing `form`; a
   client that lists only `url` cannot be asked), send `elicitation/create`
   with the message `<ticket>, slice <slice> asks:` and the question, and a
   schema of one required string field `answer`.
3. `accept` with a non-blank answer: run `answer <ticket> <qid> --as person --
   <text>`, return the `answer:` / `text:` blocks that `ask --wait` prints,
   with `provenance: person`. The refused answer (already answered, say) is a
   failed tool naming the refusal.
4. `decline`, `cancel`, an unknown action, an empty answer: nothing is
   answered. The tool returns the `asked:` block with a help line saying why
   the question `stays open` and that the person answers with `jig answer`;
   not an error.
5. No capability, the client answering the request with an error, or the
   client hanging up while asked: the same record result, with that reason.
6. The client cancelling the `tools/call` while the person decides: the server
   sends `notifications/cancelled` for the elicitation it had out and writes no
   reply; the question stays recorded and open.

The question is recorded before the person is asked, so it is never lost.

## Line shapes

Nothing new is written. The tools write what the commands write: a `question`
journal line (`Provenance: agent`) from `ask`; an `answer` line with
`Provenance: person` when the form was accepted and `agent` from the `answer`
tool; `claim` / `release` / `note` lines; `observe` ledger lines with harness
`neutral`.

Known limit: an answer taken through the form is not written as a ledger
`note-delivered` line (`ask --wait` writes one for a session). Only a question
asked with a session id can matter to D7's `answer` note source, and the model
does not know its session id in most harnesses; where it does and a hook also
delivers answers, the session may hear that answer once more at its next
prompt.

## Protocol (`internal/mcp`)

Hand-rolled newline-delimited JSON-RPC 2.0, no dependency.

- Methods: `initialize`, `ping`, `tools/list`, `tools/call`; notification
  `notifications/cancelled` is acted on, the others are accepted and ignored;
  anything else is -32601. Server to client: `elicitation/create` and
  `notifications/cancelled`.
- Versions: `2025-06-18`, `2025-03-26`, `2024-11-05`. A client asking for one
  gets it; anything else is answered with `2025-06-18`. Capabilities:
  `tools` (no `listChanged`). `instructions` is sent. Elicitation exists from
  `2025-06-18`; the server uses it whatever version was negotiated if the client
  declared it.
- No batching (removed from the protocol in 2025-06-18): an array is -32600.
  A line that is not JSON is -32700 with a null id; the session goes on. No
  lifecycle enforcement: a request before `initialize` is served, without
  elicitation.
- Concurrency: `initialize`, `ping`, `tools/list` and unknown methods run on
  the read loop, in order. `tools/call` runs on a goroutine, so a tool waiting
  on the person does not stop the server reading the answer; replies may come
  out of request order, matched by id. Commands run one at a time (one mutex
  in the toolkit): they are written for separate processes, whose locks do not
  keep two goroutines of one process apart (the checkpoint lock is re-entrant
  per process). `ask` releases the lock while the person decides.
- Shutdown: when the input ends, requests already running finish and are
  answered, the calls they have out to the client fail (so `ask` falls back to
  the record), then Serve returns, exit 0. A piped one-shot (`printf ... |
  jig mcp`) therefore gets every reply. When the context is cancelled, running
  requests are cancelled and Serve returns. A cancelled request gets no reply.
- A message line is capped at 16 MiB; a longer one ends the session.
- Output is encoded without HTML escaping, one line per message.

## Decisions

- **One mutex over command runs**, not per tool: simplest thing that keeps the
  store's in-process semantics as they were; no tool is long (no `--wait`).
- **Tool arguments are the command's own flags**, enforced by
  `TestMCPToolsPassOnlyTheFlagsTheirCommandsHave`, which runs every tool with
  every argument set and checks each `--flag` against the command's help row.
- **Elicitation answer text is the only `--as person` caller.** The tool the
  model calls can never claim to be the person.
- **`observe` is neutral only**: an agent in a harness without hooks reports
  events by flags; the per-harness payload shapes are for the hook installers.

## ADR impact

ADR 0032 can say: a harness that speaks MCP gets jig's verbs as tools, each
the in-process command of the same name (the surface of the CLI, not a second
one); a question to the person goes through the client's own form when it has
one, and only that path writes an answer as the person's; the record is the
fallback and is written first.
