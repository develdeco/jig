# D6: `jig verify`

Branch `dg/D6`, from the `digester` tip 26b5642 (S0b, S0a merged), then merged
with 5c136ac (D4, D5.1). `jig verify` runs a slice's oracle on a commit in a
detached worktree, in a detached process, and journals it the way the frontier
journals a builder's green run, so the gate reuses the pass. No change to the
frontier or the gate.

## Verb

```
jig verify [T] [sha] [--slice S] [--wait] [--rerun] [--session ID] [--store P] [--project N]
           hidden: --worker --agent-id ID --repo-dir DIR
```

- **Positionals** are optional, either order, a ticket id (`store.BranchLeadID(p) == p`) or a
  revision. Ticket default: the ticket `locate` binds to the branch checked out in the working
  directory; none is `VALIDATION_ERROR` with `jig verify T-1` as the help. Commit
  default: `HEAD` of the working directory when it is a checkout of the same repository as the
  clone, else of the clone. A revision may not start with `-`.
- **Slice** is chosen `--slice`, else the commit's `Jig-Slice` trailer, else the slice `locate`
  found: `$JIG_SLICE`, else the slice of the session's latest `claim` line (`--session` or
  `$JIG_SESSION`) not followed by its `release`. A trailer or located slice that names a slice the
  ticket lacks is passed over; a `--slice` that does is refused. None: `VALIDATION_ERROR` listing
  the slices.
- **Clone** (where the worktree is added from) is `--repo-dir` (the worker's), else the clone
  `locate` found the working directory in, else the machine map's clone of the repo, else the git
  repository around the working directory. The repo (for `start.<repo>.sha` and the target branch)
  is the one `locate` found, else the project's first.
- **No `--wait`**: `verify.Spawn`. Looks at the journal and the verification's lock; if a
  verification of (sha, slice) is there in any state, or a worker holds the lock, prints it with
  `existing: true` and starts nothing (exit 0). Else starts `jig verify --worker ...` through
  `e.spawn` (cwd the clone, output to the log) and appends the ledger `verify-spawned` line; prints
  `state: pending` and `pid:` (exit 0). `--rerun` starts one over an existing outcome.
- **`--wait`**: `verify.Run` in this process, the log appended at `log:`; prints the outcome. If
  a worker already holds the commit (pending), it waits for that worker (polls the journal every
  500 ms until the clone manifest's timeout plus 5 minutes, or the interrupt) and prints its
  outcome. Exit 0 for pass, 1 for fail or error; a still-pending result after the bound or an
  interrupt exits 0 saying so.
- **`--worker`** is the same `Run` with stdout as the log, `gitx.ClearRepoEnv()` first. It exits 0
  for pass and fail (the worker did its job) and 1 for `error` or a failure to record.
- Output is a `verify:` block (ticket, slice, commit, state, attempt, existing, pid, seconds,
  command, env, summary, signature, log), a `warning:` block for a failed push or ledger write, and
  one help line.

## Worker command line and the log

`verify.WorkerArgs`: `verify --worker --store <store root> --repo-dir <clone> --slice <S>
[--session ID] [--agent-id ID] [--rerun] <ticket> <full sha>`, program `Deps.Executable`, cwd the clone,
environment inherited (a nil `Spec.Env`), so the worker finds the same jig home. The hidden flags are
`--repo-dir` and `--agent-id`, not `--clone` and `--agent`: `TestHelpContainsCommands` fails when a
hidden flag's name is also a visible flag of any other command (`jig init --clone`, `jig session
start --agent`), so a later ticket that adds a visible `--worker`, `--repo-dir` or `--agent-id` breaks it.

Log: `home.VerifyLogPath` = `<jig home>/logs/verify/<storeID>/<ticket>/<sha12>-<slice>.log`, appended
to by every run of that (commit, slice). It holds the worker's progress lines (`verify: ...`), on a
failed oracle the last 4000 bytes of its output, and the final report. It is never removed.

## Line shapes

`Run`'s order, all appended with `journal.Append` and pushed (3 tries, 0.5 s then 1 s apart; a push
that never goes through is a `warning:` and `Result.PushErr`, and the lines stay local):

1. `verify-pending` {slice, commit: sha, attempt, session?, agent?}, then a push.
2. (env class, if the slice names one) `env-up` {slice}; at the end `env-down` {slice}. If it will
   not come up: `env-unavailable` {slice, outcome: the class's policy, `pause` for none}, the slice
   state `env-blocked` / reason `env-up-failed`, then `verify-error`. The frontier's own handling.
3. `oracle` {slice, outcome: pass|fail, commit: sha, attempt, command, env, seconds (rounded up, at
   least 1), source: `jig`, session?, agent?}; on a fail also `summary` (the flattened last 600 bytes,
   from a line boundary) and `signature` = `outcome.Signature(slice, "code-bug", summary)`.
4. On a pass: `recorded` {slice, commit, attempt, record_run: `<slice>-v<attempt>` (a `-N` suffix if
   taken), recordings, outcome (dropped/over notes or `refused: ...`)} when the scenarios wrote
   anything, exactly the frontier's shape; then `verified` {slice, commit, attempt, session?, agent?}.
5. Slice state (under the store checkpoint lock): a pass is `green` from any state (stalled and
   needs-input included) and clears question, reason, signature and stall summary; a fail is
   `building` from any state except `needs-input`, which stays; `attempts` becomes
   `max(state, attempt)`.
6. A push.

A run that cannot reach the oracle ends in `verify-error` {slice, commit, attempt, outcome: `error`,
summary: the reason (at most 600 bytes), session?, agent?} and a push. That is `Result.State = error`
(exit 1 from `--wait`), not a Go error. Reasons: the worktree cannot be made, the checkout is not
clean, the start sha is not in the clone, the commit is the start sha or does not descend from it, the
manifest does not resolve, the slice has no oracle, an undeclared or unavailable env class.

`Attempt` is per slice: `journal.NextAttempt` is one more than the highest `attempt` any line of the
slice carries (frontier dispatch lines included), so a rerun is the next attempt and a slice the
frontier built continues its numbering.

## Decisions

- **Idempotence and the lock.** `VerificationState(lines, sha, slice)` is the last of the slice's
  `verify-pending`, `oracle` (pass/fail), `verified` and `verify-error` lines at that commit; anything
  there stands unless `--rerun`. A worker holds `store.TryLock` on the worktree path (sidecar
  `<VerifyWorktreeDir>.lock`, never removed) for its whole life; a second worker finds it held and
  reports `pending`, and the pending line is written by the worker under the lock, so two Spawns made
  close together still verify once. A worker that died leaves a pending record that stands until
  `--rerun` (the journal cannot tell dead from running; the ledger `verify-spawned` pids can).
- **The worker writes the pending line**, as the design says; the foreground writes none.
- **`--slice` before the trailer** (the design lists the trailer first): an explicit flag must be
  able to correct a wrong trailer. A trailer for a slice the ticket does not have is passed over.
- **A commit is verified on a fresh checkout of itself**: `git worktree add --detach` from the
  operator clone, the manifest read from that checkout (not the working tree), the oracle command
  `m.OracleCmd(slice.Oracle, workspace)`. The tree is checked clean first, so the oracle line's
  `commit` is evidence of exactly that commit (the gate's reuse rule). Cleanup is
  `worktree remove --force --force`, `RemoveAll` (retried on Windows), `worktree prune`; what a
  killed worker left at the same path is cleared before the next add.
- **Start sha.** The ticket's `start.<repo>.sha` (repo = the one `locate` found, else the first of the project), else the merge
  base of the commit and `refs/remotes/origin/<target>`, else no descent check. `verifyGreen` then
  holds the commit to it: not the start sha itself, a descendant of it. A start sha the clone lacks is
  its own reason. `jig claim` (D8) is meant to write the file.
- **Run bound**: `timeout:` in `.claude/jig.yaml` (`time.Duration` text, `45m`, `1h30m`; a bare number
  or a negative one is a manifest error), else 30 minutes. It kills the oracle's process tree
  (envrun) and counts as a failure. A wedge guard, not a cost cap.
- **Recording**: `JIG_RECORD_DIR` is given to every oracle run, run name `<slice>-v<attempt>`.
- **No change to the oracle line shape**: `source` is the only field not already in use there.

## Deviations from the brief

- **The gate test does not use `--scenario` alone and reads `review.json`, not `report.yaml`.** The
  scripted gate source (`--scenario` without `--backend`) writes no review request, and `report.yaml`
  has no reuse field. `work/gate.round-1.review.json` (`oracles_passed[].reused_from`) is where the
  gate says which runs it reused, and a reviewer round (`--backend fake`) writes it.
- **The gate test edits the store's `slices.yaml`** to drop the `env: rig` of slice d. The gate brings
  up every env class a slice names and reuses a pass only when exactly those were up for it
  (`gateEnvs`, `sameEnvs`), so with the fixture as it is a slice a pass (no env class) is never
  reusable; the test fails at the reuse assertion without the edit (checked). A slice d pass would
  carry `env: rig`, which the gate does reuse.
- **`Deps` has more fields** than the brief's: `Repo`, `Target`, `Log`, `Sleep`, `Executable`,
  `Start`. `Spawn(d Deps, r Request) (Spawned, error)`. `internal/verify/spawn.go` is a sixth file.
- **Uses `locate` (D3)**, which was not in the brief because D3 was in parallel: the ticket the
  branch binds, the session, `JIG_SLICE` and the claimed slice, and the repo and its clone are
  `locate.Locate(..., NoMap: true)`'s, so `verify` and `jig here` agree. The brief's own
  `ClaimedSlice` journal function was dropped for locate's.
- **`--store` and `--project`** are flags as on every verb; `--agent-id` and `--repo-dir` are hidden.
- **`--slice` wins over the trailer** (above).
- The Write and Edit tools refused paths in this worktree; the files were written through the shell.

## For other tickets

- **D7 (`observe`)**: build a `verify.Deps` (`Store`, `JigHome`, `Clone`, `Repo`, `Target` from the
  located project; `Executable` from `os.Executable`; `Start: spawn.Detached`; `Now`) and call
  `verify.Spawn(d, verify.Request{Ticket, Slice, SHA, Session, Agent})` for a commit it sees. It is
  idempotent, so a git `post-commit` and a `PostToolUse` that both see the commit verify it once. The
  `Spawned` result says `Existing`, `PID`, `Log` and a `Warning` (the ledger could not record the pid).
  `Spawn` does not read `JIG_SESSION`; pass the session. Tests that start workers call
  `h.WaitVerifiers()`.
- **D8 (`claim`)**: `claim` should write `start.<repo>.sha`, which `verify` reads; with none, `verify`
  falls back to the merge base with `origin/<target>`. A bare `jig verify` finds the slice of a
  session from the `claim` and `release` lines (event, `session`, `slice`) D8 writes, through locate.
- **D10 (gate reads the operator's clone)**: the gate's reuse rule is unchanged (`reusablePasses`);
  `verify` writes the lines it reads. A hand-built ticket whose slices name an env class gets a pass
  the gate reuses only when that class is the whole set the gate brings up.
- **D11 (stalls)**: the oracle fail lines carry `signature` and `attempt`; two with an equal signature
  for one slice are the repeat.
- **D3 (`here`)**: `jig here` lists the verified commits and the pending verifications itself
  (`verificationsIn`; `journal.Pending` would do the same read). The registered section adds what
  it does not show: a `verification:` block, and `sections.verify` in `--json`, for the located slice
  at the repo's HEAD, whatever its state: pending, pass, fail (with its time and summary) or error.
- **D13**: the originals of `verifyGreen`, `outputTail`, `oneLine`, `cleanHead` and the recording
  functions stay in `internal/frontier` until it deletes them; the copies here have the tests of their
  own (`record_test.go` is the frontier's recording tests against the copy).
- **`jig doctor` (D5.2)** could prune: a killed worker leaves `<jig home>/verify/<store>/<ticket>/<sha12>-<slice>`
  and git's record of it in the clone (`git worktree list`), cleared the next time the same
  (commit, slice) is verified or by `git worktree prune`; and a pending record with no live pid.

## ADR impact (for D1)

ADR 0032 can say: verification is a detached process the digester starts and the journal records, keyed
by (commit, slice); the oracle runs on a fresh detached worktree of the operator's clone, so the
operator's working tree is never touched and a commit is judged as committed; the line shapes are the
frontier's, which keeps the gate's reuse and `BuiltCommits` as they were; pending is written first, so
the work is visible before it is done; the run bound is the manifest's `timeout:`.
