## Verbs

```
jig setup   --global | --project <name> | --here   [pieces] [--harness h[,h]|all] [--tracked] [--members] [--uninstall] [--yes]  [skill names...]
jig setup   --cloud [pieces] [--harness ...]       prints a shell script, writes nothing
jig attach  [pieces] [--harness ...] [--tracked] [--members] [--uninstall] [--yes]  [skill names...]      (setup --here, in a project)
jig skills  --global | --project <name> | --here   [--helpers | --all] [--tracked] [--uninstall]  [skill names...]
jig skills install [--project] [--dest <dir>]      (hidden alias: the older form, unchanged)
jig hint    --global | --project <name> | --here   [--harness claude,codex,gemini] [--tracked] [--uninstall] [--yes]
jig hooks   --global | --project <name> | --here   [--harness h] [--tracked] [--uninstall] [--yes]     (D5.1, extended)
jig doctor  [--project <name>] [--harness h[,h]|all]
jig skill   [<name>]
```

Orders: `setup` 500, `attach` 501, `hooks` 510, `githook` 511/512, `hint` 513, `doctor` 520, `skill` 521;
`skills` keeps 210 (the legacy band) and the hidden `skills install` is 211.

**Pieces and sets.** `--skills --hooks --githook --hint` are the pieces. `--artifacts` is those four,
`--helpers` is the two helper skills, `--all` is both. Positional names are extra skills (`retro`,
`platform-sync`) and imply the skills piece for just those names. The project skill set is `here`,
`intake`, `build`, `review`, `publish`, the helpers `jig-init`, `jig-attach`. A name of the set that this
binary does not carry yet (`build`, `review`, `publish` until D8 and D10 land) is reported in the step's
detail (`not in this jig yet: ...`) and skipped; an extra that does not exist is `VALIDATION_ERROR`.

**Missing input.** Scope and pieces are never guessed. Both missing, or either: on a terminal
(`e.stdinIsTerminal`) it asks (`Where should jig be set up?` with global, here or a project name;
`What should it set up?` with artifacts, helpers or all; each with a default); with no terminal it is
`NEEDS_INPUT` (exit 2) whose help lines list the choices and an example. `attach` with no piece flags
means `--artifacts`.

**Consent.** The steps that edit a file that is the person's (hooks: a settings file; hint: a memory
file) need a yes, asked once for all of them: `--yes`, or on a terminal `This will: ... Apply? [y/N]`
(a decline writes nothing at all and says `result: declined`), or with no terminal `NEEDS_INPUT` whose
help is the command to run again with `--yes`. Skills, stubs and git hooks need none. `jig hint` asks as
`jig hooks` does.

**Output** of `setup`, `attach`, `skills` and `hint` (the label is the verb):

```
setup:
  scope: global | project <name> | here
  action: install | uninstall
  result: installed | unchanged | removed | declined
steps[N]{piece,harness,target,result,detail}:
  skills,,<dir>,installed,"4 skills: here, intake, jig-init, jig-attach; not in this jig yet: build, review, publish"
  hooks,claude,<file>,installed,<what the harness needs to read it>
  githook,,<hooks dir or clone>,installed,<core.hooksPath note, or the clone's state>
  hint,claude,<file>,installed,~82 tokens in every session
help[1]: ...
```

A step's result is `installed`, `removed`, `unchanged`, `skipped` (the githook of a folder with no
repository, a clone jig leaves alone, a stub path holding a skill of the person's) or `declined`.

## Where each piece goes

| Piece | `--global` | `--project`/`--here` (untracked, the default) | with `--tracked` |
|---|---|---|---|
| skills | full text in `~/.claude/skills/<name>/` and `~/.agents/skills/<name>/` | one stub, named `jig`, in `<dir>/.claude/skills/jig/` and `<dir>/.agents/skills/jig/`; each file in `.git/info/exclude` | the full text in `<dir>/.claude/skills/<name>/` and `<dir>/.agents/skills/<name>/`, not excluded |
| hooks | the harness's global file (below) | the harness's project file; Claude Code's is `.claude/settings.local.json`; excluded | Claude Code's `.claude/settings.json`; not excluded (the other harnesses have one project file, excluded unless tracked) |
| githook | git's global `core.hooksPath` (D5.1) | each clone in scope: covered by the global wrappers, or a block in its post-commit | the same: git hooks are never tracked |
| hint | `~/.claude/CLAUDE.md`, and `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md` for the harnesses whose directory exists | `<dir>/CLAUDE.local.md`; excluded | `<dir>/AGENTS.md`, and `<dir>/CLAUDE.md` when it exists and does not hold `@AGENTS.md` |

`<dir>` is D5.1's scope target: the folder of the nearest `jig.yaml` marker walking up (else the top of the
git work tree) for `--here`, the project's root for `--project`. `--members` repeats the project forms for each
member repository of an `orchestrator` marker (`repos[].path` under the marker); on any other marker it is
`VALIDATION_ERROR`. With no `--harness`, a project's hooks go to the harnesses its marker's
`expects.harness` lists, else Claude Code.

**The stub** (`setup.StubBody`) is a skill named `jig` whose description tells the agent to run `jig here`
and then `jig skill <name>`, with a table of the project skills (name, first sentence of the description)
and no copy of any skill. The text of a skill therefore always comes from the binary that runs, and a repo
never holds a stale one. `jig skill <name>` prints the embedded `SKILL.md` as it is, no framing; `jig
skill` alone lists them (`skills[N]{name,use it when}`).

**`--cloud`** prints a POSIX script: the `install.sh` one-liner from the README, `PATH` with
`$HOME/.local/bin`, then `jig setup --global <pieces> --yes` (default `--artifacts --helpers`; `--harness`
passes through). It takes no scope, `--uninstall`, `--tracked`, `--members` or `--yes` (`VALIDATION_ERROR`).

## Ownership: marks, not records

| What | Mark | Found again by |
|---|---|---|
| hook entry (JSON harnesses) | the command | `setup.OwnedCommand` (D5.1's regex) on `command` (`bash` for Copilot) |
| OpenCode plugin | first line `// jig-hooks-plugin: ...` | `OpenCodeShim`; an install refuses to replace a `jig.js` without it |
| skill, stub | last line `<!-- jig-skill v=<jig version> -->` | `setup.SkillStamp`; also a file byte-equal to an embedded skill (what `skills install` wrote before stamps) |
| hint | `<!-- >>> jig >>> -->` ... `<!-- <<< jig <<< -->` | `findBlockBetween` |
| exclude lines | `# >>> jig >>>` block in `.git/info/exclude` (D5.1) | `ExcludeFile`/`UnexcludeFile` |

Install over a skill directory named like one of jig's replaces it (as `skills install` always did); the
stub's name `jig` is no skill jig ships, so a `SKILL.md` there that carries no stamp is the person's and is
left (`skipped`). Uninstall removes only stamped files (or equal to an embedded text); with no name it
removes every one under the roots, including skills an older jig installed that this one no longer carries.
A hint file, plugin or hooks file that held only jig's content is deleted by the uninstall, with the
directories that were left empty up to the project folder; a person's settings file is never deleted.

## The other harnesses

Written from the vendors' documentation and unit tested against golden files
(`internal/setup/testdata/*.golden.*`); only Claude Code's is proven end to end (D7's live test). Every
entry runs `<jig> observe --harness <name>`.

| Harness | Global file | Project file | Events (vendor names) |
|---|---|---|---|
| claude | `~/.claude/settings.json` | `.claude/settings.local.json` (`.claude/settings.json` tracked) | SessionStart, UserPromptSubmit, PostToolUse `Bash`, Stop, SessionEnd |
| codex | `~/.codex/hooks.json` | `.codex/hooks.json` | SessionStart, UserPromptSubmit, PostToolUse `Bash`, Stop (no session end) |
| gemini | `~/.gemini/settings.json` key `hooks` | `.gemini/settings.json` | SessionStart, BeforeAgent, AfterTool `run_shell_command`, AfterAgent, SessionEnd; entries carry `"name": "jig"` |
| cursor | `~/.cursor/hooks.json` | `.cursor/hooks.json` | sessionStart, beforeSubmitPrompt, afterShellExecution, stop, sessionEnd; `{"version":1,"hooks":{"<e>":[{"command":...}]}}` |
| copilot | `~/.copilot/hooks/jig.json` | `.github/hooks/jig.json` | sessionStart, userPromptSubmitted, postToolUse, agentStop, sessionEnd; entry `{"type":"command","bash":...,"powershell":...,"timeoutSec":30,"comment":"jig"}` (PowerShell gets `& "<path>" ...` for a quoted program) |
| opencode | `~/.config/opencode/plugins/jig.js` | `.opencode/plugins/jig.js` | handlers `event` (session.created, session.idle, session.deleted only), `chat.message`, `tool.execute.before/after` (bash only) |

For D7's adapters: the OpenCode shim sends one JSON object per event on stdin, `{"hook":"event","cwd":
dir,"event":{"type":...,"properties":...}}`, `{"hook":"chat.message","cwd":...,"input":{...},"output":
{"parts":[...]}}` and `{"hook":"tool.execute.after","cwd":...,"input":{"tool":"bash","sessionID":...,
"callID":...},"output":{...},"command":"<shell command>"}`. The adapter maps `session.created` to
session-start, `session.idle` to stop, `session.deleted` to session-end, `chat.message` to prompt. D7's
brief names `jig observe --harness opencode` and not the payload, so this is the contract if D7 chose none.
Codex needs its hooks feature on (`codex_hooks` in `~/.codex/config.toml`, which jig does not edit); the
install output says so, and the Gemini CLI and OpenCode notes are in `Harness.Note`.

The grouped merge (`groupedFormat`) and the flat one (`flatFormat`) keep D5.1's rules for every file: one
owned entry per event, an existing one kept in place with its command brought up to date, extras dropped,
the person's keys, hooks and order untouched, the file's own indent, line ending and final newline, a file
jig cannot read an error and never written over. A file made for hooks alone (`Harness.Dedicated`: codex,
cursor, copilot, opencode) is deleted by an uninstall that leaves it with none; claude's and gemini's
settings files are the person's and stay (a project's, when jig made it, goes as D5.1 does).

## doctor

```
doctor:
  jig: <version>
  binary: <path>
  jig_home: <dir>
  scope: global | global + here | global + project <name>
pieces[N]{piece,harness,where,state,detail,cost,fix}:
notes[N]:                       (only when there are any)
help[1]:
```

`piece` is `skills` (`harness` is `claude` or `agents`: which skills directory), `helpers` (optional; not
counted as missing), `hooks`, `githook`, `hint`. `where` is the place that has it in the best shape:
`global`, `here`, `here (tracked)`, `here (stub)`, or empty when nowhere. `state` is `installed`, `stale`
(a stamp from another version, entries that run another jig, wrappers that differ), `partial` (an event
without an entry, some clones) or `missing`. `fix` is the command that adds or refreshes it, empty when
installed (`jig hooks --global --yes`, `jig githook --global`, `jig hint --global --yes`, `jig skills
--global`, with `--harness x` for another harness; the project forms when that is where the piece is).
`cost` is the tokens the skill descriptions and the hint add to every session (four bytes a token), and a
sentence for hooks and git hooks. The project checked is the working directory's (a `jig.yaml` marker or a
git repository, as `--here` finds it) unless `--project` names one. Harnesses other than Claude Code are
listed when their directory exists in the person's home (or `--harness` names them).

Notes: `hooks not seen: no hook or tool event from <h> is in the ledger yet` for a harness whose hooks are
in place and whose `Harness` appears on no ledger `hook` or `tool` line; the hooks the global wrappers do
not run in a clone (`reference-transaction`, `fsmonitor-watchman`, server-side ones: D5.1's known limit);
a binary not named `jig`; `CLAUDE_CONFIG_DIR` set; a `--project` with no folder. Doctor exits 0 and writes
nothing.

## Decisions

- **Untracked project skills are one stub**, not copies: it reads the brief's "stubs under
  `.claude/skills/jig/` and `.agents/skills/jig/`" as one `jig` skill in each directory.
- **`CLAUDE_CONFIG_DIR` is not honored** (D5.1 left it to this ticket). Writing there would send an e2e run on
  a developer machine that has it set to the real directory, and `jig skills install` never honored it.
  `jig doctor` says when it is set.
- **The hint's codex and gemini files are written when their directory exists** (or `--harness` names them),
  not always: jig would otherwise create `~/.codex` for a person who has no Codex, and doctor would then find
  a harness in use.
- **`skills install` is untouched** (all skills, no stamps, `--project` a switch, `--dest`), registered as a
  hidden verb so its own flags keep their help and parity test; the README, the install scripts and the live
  Quickstart test still use it.
- **No `--yes` on `skills` or `githook`**: they write nothing of the person's.
- **`attach` requires a marker, `setup --here` does not** (a repository with no marker works there, as D5.1's
  `--here`).

## Known limits (help text and this file)

- Claude Code ignores project hooks in a folder it does not trust and with `--bare`; Codex does not read hooks
  in an untrusted folder either. The flag usage of `setup`, `attach` and `hooks` says so, and so does the
  install output.
- A stub or skill is read when a session starts; a running session does not see it.
- The hook entries call `jig` by name or by the quoted path of the binary (D5.1's contract): a binary not named
  `jig` can set up skills and the hint but not hooks or git hooks (`BINARY_NAME`).
- The five other harnesses' file shapes and payloads are not proven against the tools.

## ADR impact (for D1)

ADR 0032 should add to D5.1's list: ownership by detection extends to skills (a stamp with the writing jig's
version), the hint (a marked block) and the OpenCode plugin (its first line); a project gets one stub that
defers to `jig skill <name>` in its untracked form and the full text only under `--tracked`; the installers
share one consent rule (the files that are the person's ask once; a caller without a terminal passes
`--yes`); `jig doctor` reads and never writes.
