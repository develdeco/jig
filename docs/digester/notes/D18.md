# D18: branch names

Branch `dg/D18`, from the `digester` tip 28860c8 (S0b, S0a, D3, D8, D10 among the
merged), then merged with b16a0ac (D2, the last digester merge). Decision 31 per
decision 7: a ticket's branch is `<id>-<slug>`, the id is the one the tracker
that names branches knows, the name binds a branch to its ticket with no claim,
and a branch a session chose for itself is recorded by its claim. No new verb.

## The name

`Store.ResolveTicketBranch(ticket, rec, target)` (and `TicketBranch`, which reads
the record first), in this order:

1. A recorded `branch:` wins, validated as before (the target branch and names git
   rejects are `TICKET_BRANCH_INVALID`). The default is **never written** to `branch:`,
   so `Ticket.Adopted()` means what it did.
2. Otherwise `<id>-<slug>`:
   - **slug**: `ticket.yaml` `slug:` when it has one, else `store.Slug(title)`.
   - **id** (`Store.branchID`): the GitHub issue number from
     `tickets/<id>/tracker/github.yaml` (`store.TrackerIDs`) when the ticket is mirrored
     **and** the project's branches are led by GitHub; else the store id.
3. A ticket with no slug to give (no title, or a title with no ASCII word) keeps
   `jig/<id>`, the name every ticket had. See the deviations.

`store.Slug(title)`: the lowercase ASCII words of the title joined by `-`, cut at a
word boundary so it is at most 40 characters. Any rune that is not an ASCII letter or
digit ends a word, except an apostrophe (straight or curly), which sits inside one
(`Don't` is `dont`). Only ASCII letters are lowercased (the Kelvin sign is not a `k`).
A first word over 40 characters is cut at 40. No ASCII word gives `""`.

**When the slug is fixed.** `jig ticket new` and `jig graduate` write `slug:` when they
mint, so editing the title later never renames the branch. A ticket minted before the
field has none: its slug follows its title on read, and `WriteTicketBranch` (what
records a branch) writes the slug the title gives at that moment into the record. Slug
is added at all four sites of `ticket.go` (the `Ticket` field, `ticketFile`,
`ReadTicketFile`, `writeTicketFile`), so no rewrite drops it (`TestTicketSlugSurvivesEveryRewrite`).
`ticket.yaml` is decoded strictly: an older jig refuses a ticket that has `slug:`
(`TICKET_RECORD_INVALID`, help: upgrade jig). `schema_version` stays 1.

**Which tracker leads.** `Store.BranchesFrom` (new exported field) holds the jig.yaml
marker's `branches: { from: <tracker> }`. Empty or `github` (any case) means GitHub's
issue number leads a mirrored ticket's branch; any other value leaves the store id to
lead it. `resolveStoreChecked` sets it from `project.Config.BranchesFrom`, which
`project.WithMarkerRepos` fills from the marker. Only a v3 store reads a marker, so a v2
store is always "unset", i.e. GitHub. `Store.BranchesLedByGitHub()` is the predicate.

**`store.TrackerIDs(ticket)`** (`trackerids.go`) reads `tickets/<id>/tracker/github.yaml`
leniently (`repo`, `issue` only; the rest is the mirror's) through the Windows-safe
`readFile`: `TrackerIDs{GitHub *GitHubIssue{Repo, Number}}`, none when the file is
absent or names no issue; an undecodable file is `TRACKER_RECORD_INVALID`.
The store cannot import the mirror, so the two keys are spelled again in `githubRecordIDs`.

## Binding

`TicketForBranch(branch)` strips one `jig/` and then tries the leads that cannot both
begin one name:

- `KEY-N` (`BranchLeadID`, unchanged): a ticket id (`how` `id`), else an alias (`alias`).
  So `jig/<old id>` branches bind through the aliases a migration leaves.
- a bare number (`BranchLeadIssue`, new: `^[1-9][0-9]*` then end or `-`): the issue
  number of a ticket's GitHub record (`how` `remote`). `102-anything` binds the ticket
  mirrored to issue 102 with no claim and no recorded branch. `102` is not `1020`; `102x`
  and `0102-x` bind nothing.
- Two tickets carrying one number (same-numbered issues of two repositories) is
  `TICKET_REMOTE_ID_COLLISION`; the ticket's own id in the name still binds.
- A ticket whose tracker record cannot be read costs only its own claim on a number (as
  `aliasClaims` does for aliases).

The issue index (`remoteLeads`) is built by a fresh scan of every ticket's record on each
numeric lookup and is **not cached**: the mirror writes those records without going
through the store, so a cache could hold a ticket back from the number its issue was just
given. `findOverlaps` calls `TicketForBranch` per local branch, so a repo with many
digit-led branches pays one scan each; there is nothing to pay for a branch that leads
with a `KEY-N` or with no number.

"Then remote key" (a tracker whose ids are `KEY-N`, like Jira's) is **not implemented**:
no tracker record gives such a key. Add the key to `remoteLeads` and ask it from the
`KEY-N` branch of `TicketForBranch` when one does.

`locate` is untouched: `how` `remote` falls into its `default` and reads as
`ticket_how: branch`, explain `ticket: JIG-1 (branch 102-fix-login)`.

## Claim records the branch

Decision 7: "`claim` on a branch naming no ticket records it." `cmd/jig/claim_branch.go`
`recordBranch`, called by `recordClaim` after the start sha and before the push (so the
record goes out with the claim):

- records `Where.Branch` with `WriteTicketBranch` when the work is on a branch, the ticket
  has no recorded branch, `TicketForBranch(branch)` binds **no** ticket (not this one, not
  another; an error counts as binding), and `CheckAdoptableBranch` accepts the name (not
  the repo's target branch, not a name git rejects);
- never replaces a recorded branch; a refused or green claim records nothing; `--release`
  and a re-claim record nothing new.

The claim output gains one help line when it recorded: `Branch X names no ticket, so it is
now T's branch (ticket.yaml branch:); ...`. The `claim` journal line is unchanged (`Branch`
is still the branch the work was on). Recording makes the ticket adopted, which is the
intent: the branch is not the ticket's by name, so it is the ticket's by record, and gate,
publish, `jig next` all name it. `recordClaim` and `printClaim` gained a `recorded` result.

## Verbs and output

| Verb | Change |
|---|---|
| `jig ticket new`, `jig graduate` | the minted `ticket.yaml` carries `slug:` |
| `jig next [T]` | `branch:` is the new name (and `git switch -c <name>` in the help) |
| `jig here`, every verb that takes the ticket from the branch | a branch led by the ticket's issue number binds |
| `jig claim` | records a non-ticket branch (above); one help line |
| `jig publish --body`, gate, `jig validate` | name the branch through `TicketBranch`; the recorded name wins (`TestPublishBodyTargetsRecordedName`) |

New error codes: `TRACKER_RECORD_INVALID` (a `github.yaml` the store cannot decode),
`TICKET_REMOTE_ID_COLLISION`. `validate` reports a broken tracker record through its
existing `TicketBranch` check.

## The issue footer

`internal/mirror/render.go`: `footer(where, branch, marker)`; `ticketFooterAt(ticket, branch)`
(`ticketFooter(ticket)` is the same with no branch). `RenderTicketBody` names the branch
beside the store id when the project's branches are **not** led by GitHub:

```
Mirrored from the jig ticket store (`JIG-1`, branch `JIG-1-fix-login`). The store is ...
```

This is decision 31's "the other trackers link the branch through the PR body and the
issue footer": GitHub finds a branch by the issue number that leads it, so an issue of a
GitHub-led project (the default) is unchanged, byte for byte. The footer of a new issue
(the body sent at create time, before the issue has a number) names no branch. A branch
that cannot be resolved (a record git rejects, a broken tracker record) leaves the footer
as it was and does not fail the render.

## Deviations from the brief

- **A ticket with no slug keeps `jig/<id>`**, instead of the bare id (`JIG-1`). Brief:
  `<branchID>-<slug>` always. With a bare id every fixture ticket (hand-built, no title)
  would change name, and every test of the other tickets that pushes `jig/JIG-1` for it and
  then publishes (`PR_HEAD_MISMATCH`) would break at the merge. Tickets minted through jig
  always have a title; the case is a hand-built store or a title with no Latin letter.
- **The issue footer is unchanged for a GitHub-led project.** Naming the branch in every
  footer rewrote every mirrored issue once and broke the bridge adoption guarantee
  (`TestSyncAdoptsBridgeRecordWithNoMutation`); see above for when it is named.
- **`claim` records the branch** though the brief's file list does not name `claim.go`:
  decision 7 says it. One hunk in `claim.go`, the logic in the new `claim_branch.go`.
- **Two fields added to shared structs**: `Store.BranchesFrom` (`store.go`) and
  `project.Config.BranchesFrom` (`project.go`, filled in `load.go`).
- `internal/migrate/refusals.go`: the warning is **kept** (`BranchWarnings`, same trigger,
  same substrings) but its text no longer says jig works the ticket on `jig/<new id>`; it
  says the ticket is the new id, jig names its branch `<new id>-<slug>`, and the old branch
  still binds through the alias.
- `skills/here` and `skills/publish` lost `jig/T-1` from their examples (`<branch>`) and say
  what binds a branch and that `jig claim` records one.
- Existing tests changed because their subject changed: `TestTicketBranchDefault` (a titled
  ticket resolves to `T-2-fix-the-thing`; an absent record still `jig/T-1`),
  `TestTicketRecordRoundTrip` (recording a branch also fixed the slug), `TestNextReadySetsAndTickets`
  (`JIG-2-second`), the two mirror tests that keyed pull requests by `jig/DEMO-1`
  (`1-first-ticket` once the issue exists; `DEMO-1-a-clean-title` for the create-time scan),
  and `TestPublishTitlesThePullRequestWithTheRecordedTitle` (records the title **before**
  gating: a title recorded after would move the ticket off the branch the gate reviewed).

## Known limits and heads-up

- **The name changes when the mirror gives the ticket its number.** A branch begun on the
  store-id name (`JIG-1-fix-login`) still binds, but the mirror then looks for pull requests
  from `102-fix-login`, so it will not place that one on the board. In a mirrored project the
  issue is created in the same command that mints the ticket (the checkpoint hook), so the
  window is short; a project that adds a tracker later, or whose first sync failed, meets it.
  Recording the branch (a claim on a branch that names no ticket does) is the cure; a
  `FindPullRequests` over several candidate names is the other.
- **Tickets of other builds with a title and a pushed `jig/<id>` branch** (a test that mints
  a ticket with `ticket new --title`, pushes `jig/<id>`, then publishes) now resolve a different
  default. The e2e suite has none; D13's ports and any later test should use the name `jig next`
  prints, or record the branch. Fixture tickets have no title and keep `jig/JIG-1`.
- Comments in `internal/frontier/frontier.go`, `internal/pool/pool.go`,
  `internal/verifydeliver/{adopt,gate}.go` still say `jig/<ticket>` where they mean the default
  branch; left alone (D13 deletes or rewrites most of them). README lines 125, 222 and 433-434
  and ARCHITECTURE lines 698, 747, 758 and 773 say the same; D1.
- The earlier full run of `./e2e` beside `./internal/frontier` and `./internal/verifydeliver`
  failed `TestPublishDeclinedPromptCommitsAndPushesStore` once (exit 1, empty output, 35 s) and
  passed alone and in two full runs of the package: load, not the change.

## ADR impact

- ADR 0013 (a ticket's branch is recorded): the default it falls back to is `<id>-<slug>`, not
  `jig/<id>`; a claim on a branch that names no ticket now records one.
- ADR 0032 (D1) should state decision 31: the id that leads (GitHub's issue number when the
  mirror has one and the project's branches are GitHub-led, else the store id), the slug (fixed at
  mint, ASCII, at most 40 characters at a word boundary), that the default is derived and never
  recorded, that binding reads the leading id or issue number, and that `jig/<id>` branches keep
  binding through aliases. ADR 0031's migration warning about `jig/<old id>` branches stays.
