# D7: `jig observe`

Branch `dg/D7`, from the `digester` tip 4e8e648 (S0b, S0a, D19, D3, D4, D5.1 and
D6 merged). One hidden hook verb whose core, `internal/observe`, takes neutral
`Event`s from per-harness adapters. It turns session start, prompt, tool call,
stop, session end and git's post-commit into session records, verifications and
context, and prints what the harness reads. The core never reads a harness's own
shape; every adapter is the only place that does.

## The verb

```
jig observe --harness <h>                       the hook payload of harness h on stdin
jig observe --event <kind> [flags]              the event from flags alone (a script, a crew)
jig observe --harness <h> --event <kind> ...    payload on stdin, the flags laid over it
```

Hidden (`verb.Spec.Hidden`), Order 900, FlagSet `observe`. Flags, all hidden with
the verb: `--harness`, `--event`, `--session`, `--agent`, `--cwd`, `--tool`,
`--command`, `--exit`, `--files` (comma separated), `--model`, `--transcript`,
`--stop-active`. A flag that is given replaces what the payload said. With
`--event` and no `--harness` the adapter is `neutral` and stdin is not read.

**It exits 0 and prints nothing whatever it is handed**: a payload that is no
payload, an unknown harness, a bad flag, an exit that is no number, a store that
will not open, a panic. Claude Code puts the stdout of a SessionStart or
UserPromptSubmit hook into the model's context and reads a non-zero exit as a
refusal (exit 2 blocks a prompt), so a hook that complains does harm. What went
wrong is one line in `<jig home>/logs/observe.log` (`<utc time> <harness> <kind>:
<message>`, started over past 512 KB, the old one kept as `observe.log.1`). When
stdin is a terminal (a person ran it) the error is also rendered on stdout with
its exit code. An event the harness sends that jig does not act on (a
`Notification`, say) is no failure and is not logged. At most 64 MB of payload is
read.

`githook post-commit` (the D5.1 runner, hidden) now builds a `post-commit` event
with `Harness: "git"` and calls `observe.Handle`. Its contract is unchanged: exit
0 always, silent on success, one line `jig githook post-commit: <message>` on
stdout for a failure (git shows it beside the commit), and the `git-commit` ledger
line it always wrote.

## The neutral field contract

An `Event` has exactly: `Harness, Kind, Session, Agent, Cwd, Tool, Command string;
Exit *int; Files []string; Model, Transcript string; StopActive bool`. Kinds:
`session-start`, `prompt`, `tool`, `stop`, `session-end`, `post-commit`. Any field
but `Kind` may be empty. An empty `Cwd` falls back to `Deps.Cwd` (the working
directory), so a hook that names no directory acts on the one it runs in. A
`post-commit` event has no session of its own (the commit is read from HEAD of
`Cwd`).

`Result` is `{Context, Message, Block string}`: text for the model, text for the
person, and a reason to refuse to stop. The neutral JSON, both what a script
sends (`event|kind`, `session`, `agent`, `cwd`, `tool`, `command`, `exit`, `files`,
`model`, `transcript`, `stop_active`, `harness`) and what jig answers
(`{"context","message","block"}`, each only when it has something to say), is the
shape of the `neutral` and `opencode` adapters.

Context for a kind with no channel for it goes to `Message` so nothing is
dropped; a Block on anything but a stop is ignored. Only Claude Code is proven
against the real program (`TestHooksLive`). The other shapes are read from each
tool's documentation and covered by unit tests on sample payloads; where a
harness is narrower (Cursor and Copilot cannot be told things after a tool call)
the note waits for the next event that can carry it.

## What each event does

Every event but `post-commit` first runs `locate.Locate(jigHome, cwd, {Session})`.
A directory in no jig project is left alone: no ledger line, no output. The store
is opened through `openLocatedStore` (schema checked); a project whose store is
not on this machine still gets its ledger lines, and nothing that needs a ticket.

| Event | Does | Output |
|---|---|---|
| session-start | `ledger.StartSession` (harness, agent, cwd, clone, ticket, slice, model, and `commit` = HEAD), a `hook` line; then `hereText` of the located directory, the blocks of `jig here` and every registered here section | Context |
| prompt | a `hook` line; a `session-touch` when the ticket or slice differs from the session's last line; the notes the session has not heard (`note-delivered`, outcome `prompt`) | Context |
| tool | if the tool ran a command and HEAD differs from the one the session's last line recorded (in the same directory): `verify.Spawn` for HEAD; a `tool` line; the notes not yet heard (outcome `tool`) | Context |
| stop | a `hook` line; the findings (below) | Message, or Block |
| session-end | a `hook` line, `ledger.EndSession`, one call to every note source (what they return is dropped), a journal `note` line per question still open | none |
| post-commit | `git-commit` ledger line (as D5.1 wrote it); then, if the directory is in a project, `verify.Spawn` of HEAD | none |

**Verifying a commit** (`verifyCommit`, shared by tool and post-commit). The slice
is the commit's `Jig-Slice` trailer if the ticket has such a slice, else the
located slice (`JIG_SLICE`, else the session's latest unreleased `claim`); neither
means nothing is verified. Before `verify.Spawn` the core looks 1 MB back in the
ledger for a `verify-spawned` line of the same commit and slice: git's hook starts
the worker inside `git commit`, the PostToolUse hook runs right after, and the
worker has not written its journal line yet, so the journal alone would let both
start one. `Spawn` stays the idempotence of last resort. The request carries the
session (the harness's, else `JIG_SESSION`) and agent.

**HEAD moved** is "HEAD is not the commit the session's newest `tool`, `hook`,
`session-start` or `session-touch` line recorded, in the same directory". A
session with no such line only starts being watched (hooks installed
mid-session). It is stateless: the ledger is the memory. A checkout of a branch
whose tip has a trailer and no verification is verified too; that is meant.

**Stop.** Findings, each with a fingerprint (`ref`):

| Finding | Ref | Blocks an unattended session |
|---|---|---|
| a verification running: `journal.Pending` newer than 2 h, or a `verify-spawned` line of the ticket newer than 10 min whose commit and slice the journal has no record of | `pending:<sha12>:<slice>` | yes |
| tracked files changed and not committed (`git --no-optional-locks status --porcelain --untracked-files=no` in the event directory) | `dirty:<hash of the list>` | yes |
| an open question | `question:<qid>` | no |
| a note from a source: enforced and not yet refused for, or not yet heard | the note's Ref | an enforced one, once |

*Interactive* (no unattended claim, no marker default): Result.Message is
`jig: <finding>` per line, never a Block. *Unattended* (the session's latest
unreleased `claim` line has `unattended: true`, or the nearest `jig.yaml` marker
has `unattended: true`): a Block when there is a blocking finding, unless
`StopActive` and none of the blocking findings is new (a `note-delivered` line of
outcome `stop-block` for the session already has its ref). The reason lists every
finding with its remedy, and each ref is recorded as `note-delivered` /
`stop-block`. So a session is refused at most once for a given fact, and a
`stop_hook_active` stop with nothing new always ends. A verification that is
still running at the end of a new turn holds the session back again.

**The queue.** The brief's "note queued for the next prompt" is the set of notes
the session has not heard: nothing is stored. A note source's note, and a
verification outcome, are delivered at the next tool call or prompt whether or
not a Stop showed them to the person first.

## Note sources (the extension point of D11 and D12)

```go
type NoteSource func(NoteCtx) ([]Note, error)
func RegisterNoteSource(name string, fn NoteSource)   // from an init(); panics on a bad or taken name
type Note struct{ Ref, Text string; Enforce bool; Source string }
type NoteCtx struct { Event Event; Where locate.Where; Store *store.Store; JigHome string
    Now, Since time.Time; Commit string; Unattended bool; Journal func() ([]journal.Line, error) }
```

A source is called at every tool, prompt, stop and session-end event of a session
whose directory is in a project and which works on a ticket in a store that is
here (`Where.Ticket` and `Store` are set). It must be quick and return the same
`Ref` for the same fact. **It may write its own records**: D11's `correction`
line and D12's `spend` line are written by the source, on the event it wants
(D12: Stop and SessionEnd), which is also how a fact is reported once. What it
returns at a session-end is not delivered. A source that errors or panics costs
only its own notes; the error reaches the log.

`Enforce` is the one switch: set, the note holds an **unattended** session back
at Stop once (D11's stall, drift and scope notes); unset, it is only told (D12's
spend, "never a kill"). The core, not the source, knows whether the session is
unattended (`NoteCtx.Unattended`). `NoteCtx.Since` is the session's start in the
ledger (zero when the ledger has no line of it yet); a fact older than that was
not made in this session. `NoteCtx.Commit` is the commit a tool call just
moved HEAD to. Delivery per session is once per `Ref`, remembered by
`note-delivered` lines, read back at most 16 MB from the end of the ledger and
stopping at the session's latest `session-start`.

Built in: `verification` (a `verified` line since the session began: advisory;
a failed oracle or a `verify-error` not followed by a later `verified` of the
slice: **enforced**; refs `verified:<sha12>:<slice>:<attempt>`,
`oracle:<sha12>:<slice>:<attempt>`, `verify-error:...`) and `answer` (an `answer`
journal line with a `ref` for a question whose `question` line names the
session and the same ref: the answer text from the question file; ref
`answer:<qid>`).

## Line shapes

Ledger lines (`journal.Line`, stamped by `env.now`):

| Event | Keys the core sets | When |
|---|---|---|
| `session-start` | `session`, `agent?`, `harness`, `cwd`, `clone`, `ticket`, `slice?`, `model?`, `commit` (HEAD) | SessionStart |
| `session-touch` | `session`, `harness`, `cwd`, `clone`, `ticket`, `slice` | a prompt on another ticket or slice |
| `session-end` | `session` | SessionEnd |
| `tool` | `session?`, `agent?`, `harness`, `tool`, `command?` (flattened, 400 bytes), `exit?`, `files?`, `commit` (HEAD, command tools only), `branch`, `ticket?`, `slice?`, `cwd` | every tool event in a project |
| `hook` | `session?`, `agent?`, `harness`, `cwd`, `ticket?`, `slice?`, `outcome` (the kind: `session-start`, `prompt`, `stop`, `session-end`), `summary?` (what Stop showed or refused for) | every event but a tool call (which writes `tool`) |
| `note-delivered` | `session`, `harness`, `ref`, `outcome` (`tool`, `prompt` or `stop-block`), `summary` (the text), `ticket`, `slice?` | a note given to the session |
| `git-commit` | `commit`, `cwd`, `branch?` and nothing else | git's post-commit |
| `verify-spawned` | written by `verify.Spawn` (D6) | a worker started |

A doctor's "hooks seen from harness H" is therefore any ledger `hook` or `tool`
line with `harness` H, which is the rule `jig doctor` (D5.2) applies.
Journal lines: one `note` per open question at session end (`slice`, `session`,
`agent?`, `harness?`, `ref` = the question id, `provenance: jig`, `summary` =
"the session ended with question q-001 still open: ...", once per session and
question; left in the store clone for the next checkpoint to push, because
SessionEnd hooks get little time and a push is a network call). The core reads
the ticket journal's `claim`, `release` (unattended), `question`, `answer`,
`oracle`, `verified`, `verify-pending`, `verify-error`.

## Decisions

- **Stateless.** Nothing is stored for a session but ledger lines. Memory is
  `ledger.ReadBackward` (16 MB window, stops at the session's latest
  `session-start`), so the cost of a hook is the distance to what it asks for,
  not the length of the ledger. A hook costs about 90 ms on this Windows host.
- **Outside a project, nothing.** The global hooks fire for every session on the
  machine; recording sessions of unrelated repositories in jig's ledger would be
  noise and a privacy leak. `Locate` says none, and the event returns at once.
- **Errors never reach stdout or the exit code** (above). `Handle` also returns
  its errors beside a partial `Result` (`errors.Join`), so a ledger line that
  could not be written does not cost the context.
- **A failed Bash command fires `PostToolUseFailure`, not `PostToolUse`** (seen
  with the real Claude Code 2.1.232). The adapter reads both as a tool event;
  the D5.1 installer registers only PostToolUse, so `git commit ... && go test`
  with a failing test is seen at the next successful tool call, or by git's hook.
  D5.2 or D1 may add the event to `ClaudeHooks()`.
- **No `model` in a SessionStart payload** of the real Claude Code; the field is
  read when present.
- **Verification outcomes are ticket facts, delivered to every session on the
  ticket that began before them**, not only to the session whose commit it was
  (git's hook has no session). The `since` rule keeps a new session from being
  handed history.
- **A running verification is also "what the ledger says was spawned"** (10
  minute window) so a Stop right after a commit sees it before the worker's first
  journal line; a worker that died is passed over after 10 minutes and a
  `verify-pending` line after 2 hours.

## ADR impact (for D1)

ADR 0032 can say: the digester sees a session through the harness's own hooks
and git's post-commit, both calling one verb that never fails the harness; a
per-harness adapter is the only code that knows a harness's payload, and the
core speaks a neutral event; the machine ledger is the only memory of the hooks
(what a session was told, where HEAD was), read back from its end; a directory
in no project is never recorded; an unattended session is held back at Stop once
per fact and never twice for the same one (`stop_hook_active`); notes reach a
session once, as context at its next tool call or prompt.
