# D15: `jig events`

Branch `dg/D15`, from the `digester` tip 877d9d4 (S0, D3, D4, D5, D6, D19
merged). One ndjson stream over the ticket journals and the machine ledger,
ordered by time, each line tagged with the file it came from, with `--follow`.
It reads and writes nothing else: no sync, no fetch, no ledger or journal line.

## Verb

```
jig events [T] [--follow] [--since <t>] [--all] [--store P] [--project N]
```

Registered in `cmd/jig/events.go`, Order 350, help row "stream the ticket
journals and the machine ledger as one time-ordered ndjson". `T` may stand
anywhere among the flags (`parseWithPositionals`); at most one.

| Flag | Meaning |
|---|---|
| `--follow` | print the stream as it is, then each line added to it, until interrupted (`e.ctx`); exit 0 |
| `--since <t>` | only lines stamped at or after `t`: an RFC 3339 timestamp, a duration back from now (`30m`, `1h30m`), or `now` (nothing already written, only what comes). A negative duration or anything else is `VALIDATION_ERROR` |
| `--all` | every store the machine map names that is on disk, and the whole ledger. Refused (`VALIDATION_ERROR`) with a ticket, `--store` or `--project` |
| `--store`, `--project` | as on every store verb |

**Scope.** Without `--all` it is the store the directory resolves to (`--store`
and `--project` as usual): with `T`, that ticket's journal; without, every
ticket's journal, listed again at every poll so a ticket made while following is
followed. `T` goes through `Store.ResolveTicket` (an alias reads as its ticket,
silently, unlike `resolveTicketArg`, which would print "X is now Y" into the
stream) and must have a folder in the store. Outside every project with
nothing to name one it is the usual "no jig store found" refusal; `--all`
works anywhere.

**Output.** One JSON object per line (`events.Envelope`, below), written one
`Write` per line with HTML escaping off, and nothing else on stdout: no help
block, no axi. Nothing on stderr. An empty stream prints nothing and exits 0.
Errors before the stream starts are the usual axi `VALIDATION_ERROR` block (exit
2). A failed write to stdout (the reader went away) ends the run with exit 1 and
no message. A journal that cannot be read fails a non-follow run whole (a short
stream is never passed off as a whole one); `--follow` rides out a poll that
fails (a sharing violation on Windows while a journal is replaced) and gives up
with the error after 40 failed polls in a row.

## The envelope

```go
type Envelope struct {
    Src   string `json:"src"`             // "journal" or "ledger" (events.SrcJournal, events.SrcLedger)
    Store string `json:"store,omitempty"` // the project name, on journal lines; empty on ledger lines
    journal.Line                          // embedded, so the line's own keys sit beside src and store
}
func (Envelope) At() (time.Time, bool)    // the ts, RFC 3339 with or without fractions
```

A ledger line has no store: the ledger is the machine's, not a store's. Nothing
in the line is rewritten (no `ticket` is filled in for a tool line); the one
loss is a ledger key `journal.Line` has no field for (`clone` on session lines,
D4's note), which the stream does not carry.

Lines are sorted by `ts` parsed as an instant (second-resolution stamps of older
jig versions and nanosecond ones mix; text order is wrong for them). A line with
no readable `ts` sorts first and is dropped by any `--since`. Ties go to journal
lines before ledger lines, then to the order the scope lists the journals (store
projects by name, tickets by key then number), then to file order. A reader may
rely on per-file append order only, never on causality between files or
machines: a union-merged journal can put a line of another machine anywhere in
the file, and `--follow` prints it when it first sees it, which is after later
lines.

## Which ledger lines (decision)

The brief does not say. A ledger line is in the stream when it is about a ticket
of the scope: it names that ticket in `ticket`, or it names none and its `session`
was last bound to a scoped ticket by an earlier ledger line (any line with both
`session` and `ticket` binds, last wins, read in file order from the start of the
ledger whatever `--since` says). So the tool lines of a session on JIG-1 are in
`jig events JIG-1` once a `session-start`, `session-touch`, `verify-spawned` or
`graph` line has put the session on JIG-1; a session that is on no ticket,
or a line with neither ticket nor session, is only in `--all`. The first lines
of a session that had no ticket yet are not retro-fitted.

`--all` is the whole ledger and every store's journals, each journal line
tagged with its project (the machine map's name). A mapping whose store is not
on disk is skipped; a store of the old layout (tickets not under `tickets/`) has
no journals to list.

## Follow

`events.Follow` polls every 250 ms (`events.PollInterval`). Each poll opens,
reads and closes every file; no handle is held between polls (`journal.Append`
renames over the journal, which Windows refuses for an open file;
`TestPollHoldsNoFileAfterwards`, `TestFollowDeliversEveryAppendOnceAndBlocksNone`).

- **Journals** are read whole: a file whose size and mtime are unchanged is
  skipped; otherwise every line is hashed (sha256, 16 bytes) and the lines whose
  hash has not been emitted that many times are the new ones. Counting copies
  keeps two identical lines as two lines. A reordered or merged file therefore
  yields only its new lines; a line that does not parse yet (half written) is
  not counted and is taken once it does. The first poll is the history, sorted;
  later polls are sorted within themselves.
- **The ledger** is read by `ledger.ReadFrom` offset, not by hash: appends only,
  so the offset is the de-duplication (the brief says hash per file; for the
  ledger that would keep a hash per tool call for the life of the process). A
  ledger that shrinks restarts from 0. A poll that cannot list the journals reads
  no ledger, so no line is lost to a wrong scope.
- Without `--since`, `--follow` prints the history first and then follows. A
  consumer that wants only new lines passes `--since now`.

## Package

`internal/events/{envelope.go,merge.go,follow.go}` plus the package comment in
`doc.go`:

- `Journal{Store, Ticket, Path}`, `Scope{Journals func() ([]Journal, error), Ledger string, AllLedger bool}`
- `Read(scope, since) ([]Envelope, error)`
- `NewReader(scope, since) *Reader`, `(*Reader).Poll() ([]Envelope, error)`: the lines not returned by an earlier Poll
- `Follow(ctx, scope, FollowOptions{Since, Interval}, emit func(Envelope) error) error`: nil when `ctx` ends, `emit`'s error when it fails

**For D16.** The TUI's `Source` can wrap `Follow` (or `NewReader` polled on its
own tick) with a `Scope` of its choosing; `cmd/jig/events.go` has the scope
builders (`storeJournals`, `journalOf`, `machineJournals`). Nothing in the
package reads the store or runs git; the journal path comes from `journal.Path`.

## Deviations from the brief

- **`journal.Path(st, ticket)`**, new exported function in a new file
  `internal/journal/path.go` (`journalPath` is unexported in `journal.go`,
  which D2 rewrites). It is the only change outside D15's own files.
- **Ledger de-duplicated by offset**, journals by hash (above).
- **`--store` and `--project`** are flags, as on the other store verbs.
- **`TestEventsFollowSeesHookVerification` drives `jig verify` itself**, because
  `jig observe` (D7) is not in the tip: the harness commits, then runs
  `jig verify` (the detached worker, the same call the hooks make). When D7
  lands, the commit alone starts the worker and the test can drop the `verify` call;
  it stands as it is. Likewise `TestEventsReadsHarnessRun` appends the `tool`
  line a PostToolUse hook would write with `ledger.Append`.
- The Write and Edit tools refused paths in this worktree; the files were
  written through the shell.

## Limits

- The first poll reads the whole ledger into memory (`ledger.ReadFrom` from 0),
  `--since` or not. A ledger of millions of tool lines makes `jig events` slow to
  start; rotation or an index by time is for whoever needs it.
- `jig events` shows what is on disk. It does not fetch another writer's branch
  (D2), so lines of other machines appear after the next checkpoint merges them.

## ADR impact (for D1)

ADR 0032 can say: the journal and the ledger are the bus and `jig events` is its
one reader; the stream is ordered by each line's own instant and promises nothing
across files; a follower never holds a file open and tells new lines from old by
content, because the journal is rewritten whole and a merge may reorder it.
