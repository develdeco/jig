# D17: `jig init`, `repos`, `share`; store.yaml and schema 3

Branch `dg/D17`, from the `digester` tip eb36b53 (S0, D3, D4, D5.1, D19
merged). Decisions 21, 23, 24, 30 and 34 of the digester chart, per decision 6
of the plan. A project is now defined by a `jig.yaml` in its repo and a
sibling store whose config is `store.yaml` (schema 3); a v2 store, with its
`project.yaml`, opens unchanged and moves up with `jig store migrate`.

## Verbs

All registered from their own file's `init()`. `init` keeps Order 100 and
`store` 230; `repos` is 400, `repos add` 401, `repos remove` 402, `repos sync`
403, `share` 404. Positionals may sit anywhere among the flags
(`parseWithPositionals`).

| Verb | Flags | Exit |
|---|---|---|
| `jig init [path\|url...]` | `--standalone`, `--orchestrator`, `--clone`, `--yes`, `--key` | 0; 2 for a refusal or when it needs a yes it cannot ask for |
| `jig repos` | none | 0; 2 outside a project |
| `jig repos add <path\|url>` | `--clone` | 0; 2 |
| `jig repos remove <name>` | none | 0; 2 |
| `jig repos sync` | `--yes` | 0; 2 |
| `jig share` | `--store-remote <url>`, `--remote <name>=<url>` (repeatable), `--create`, `--yes` | 0; 2 for a refusal or no yes; 1 for a failed push or `gh` |
| `jig store migrate` | adds `--to <n>`; `--map` now only for the v1 step | 0; 2 |

The old `init --store <path> --clone name=path` mode is retired (`jig here`
maps a clone on the spot, `jig map` places one by hand); `--clone` is now a
bool and `--store` is an unknown flag. `cloneFlag` (main.go) is gone.

**`init`** runs only at a project's root (`project.CheckInitDir`): it refuses a
folder with a `jig.yaml` ("already initialized"), one under a `jig.yaml`
("inside the jig project at ...", naming `jig repos add` and `attach --tracked
--members`), one below the top of its git repo, and a store. With neither
`--standalone` nor `--orchestrator` it reads the case off the folder
(`project.InferKind`: direct children with a `.git`, or `.gitmodules` entries,
make an orchestrator; naming repos on the command line does too) and prints a
`picked:` block (`mode`, `why`) before it writes. Output: `init:` (`mode`,
`project`, `store`, `marker`, `git` when it ran git init), for an orchestrator
`repos[N]{name,path,source,state}` (`source` is `nested`, `submodule` or
`fetched`), then help.

- Single repo: creates `<name>-tickets` beside the folder (git on `main`,
  `store.yaml`, `platform/`, `ledger.md`, `.gitignore`, `.gitattributes`, one
  commit "jig: init store" by the person), writes `jig.yaml` (`jig: "1"`,
  `project`, `kind: project`; no `store:`, no `repos:`), and maps the project.
- Orchestrator: the same, with `kind: orchestrator` and `repos:` as
  `{name, path}` entries. It must be a git repository: a plain folder gets
  `git init -b main` only with `--yes` or a yes at the prompt; with no
  terminal and no `--yes` it writes nothing and exits 2 (NEEDS_INPUT). No
  repos named = every direct child with a `.git` plus direct `.gitmodules`
  paths (`init` with no arguments is `repos sync` on an empty list). A path
  must be a direct child that is a repo; a URL is fetched into the folder named
  as `git clone` would name it: `git submodule add` plus `ignore = all` in
  `.gitmodules` (staged), or with `--clone` a plain clone, `/name/` in
  `.gitignore`, and its `remote:` in `jig.yaml` (a gitignored clone is not
  something another checkout has). `git -c protocol.file.allow=always` is
  passed for a URL that names this machine.
- Nothing is committed in the folder: `jig.yaml` (and `.gitmodules`) are the
  person's to commit. The machine map gets `{store, root, clones}` through
  `UpdateMachine` (the single repo's clone is keyed by the project name).
- Refuses a project name already mapped to another live store, an existing
  non-empty sibling store dir, and (before writing anything) a machine with no
  git identity. A failure after the store was made takes the store away again;
  it does not undo a `git init` of the folder or a repo already fetched.

**`repos`** prints `project:` (`name`, `kind`, `root`), `repos[N]{name,path,
remote,state}` (`state` is `checked out`, `not checked out here` or `missing`),
`unlisted[N]{name,path}` (nested repos the list lacks) and help. **`add`**
takes a path of any depth under the orchestrator or a URL; prints `repos_add:`;
refuses a repo the list has, a path outside, the folder itself, a non-repo.
**`remove`** takes the name out of the list and the machine map and leaves the
folder; prints `repos_remove:`. **`sync`** prints `repos_sync:` (`added`,
`removed`, `not_here`) and the `added`, `removed`, `not_here` tables when
non-empty. Rules (`project.Sync`): nested repos the list lacks are added; a
listed repo with no folder (or no `.git`) is removed; a listed submodule that is
not fetched (or a listed repo with its own `remote:`) is `not_here` and stays,
unless the person answers no at the prompt (asked only at a terminal without
`--yes`). A dropped submodule still in `.gitmodules` returns on the next sync;
the help says to `git rm` it. `add`, `remove` and `sync` refuse a single-repo
project; all four find the project by walking up for a `jig.yaml`, passing over
a `kind: member` one (`project.FindProjectMarker`).

**`share`** (decision 30): plan, confirm, then do. It needs the project's
`jig.yaml` and store. Remotes: the store's from `--store-remote` or its
existing origin; a repo's from `--remote <name>=<url>` (the project's own repo
goes by the project's name, or `.`; an orchestrator's nested repos by their
names), or created with `gh repo create <name> --private --source <dir>
--remote origin` for each repo that has none (`--create`; the store is
`<project>-tickets`). A repo that already has a different origin is refused, not
rewritten; a path given relative is made absolute against the working
directory. Without `--yes` it prints the plan as help lines and exits 2
(NEEDS_INPUT), or asks `Apply? [y/N]` at a terminal. Then: sets or creates the
remotes; writes `store: <url>` into `jig.yaml` and, for each nested repo that
`.gitmodules` does not carry, its `remote:`; commits `jig.yaml` alone ("jig:
record the project's store in jig.yaml", as the person, `git commit -- jig.yaml`
so staged work of theirs stays staged); pushes the store, each nested repo it
gave a remote, and the project's own repo last (its current branch, upstream
set when it had none). Output: `share:` (`project`, `store_remote`,
`marker_committed`), `pushed[N]{repo,branch}`, `remotes_set[N]{repo,remote}`,
`without_remote[N]{repo}` (nested repos still without one; collaborators cannot
get them) and help. A second `share` commits nothing new.

**`store migrate`** applies exactly the next step of `migrate.Steps`. `--to n`
must be the next version or it is refused ("one step at a time"); at the
current schema it says there is nothing to migrate; `--map` on a step that takes
none is refused. The v1 step is unchanged. The v2 to v3 step: see below.

## Files and formats

`store.yaml` (written by init; the migration edits the v2 node tree instead):

```yaml
schema_version: 3
keys:
    DEMO: everything in demo
trackers: []
platform: platform/
projects: [demo]
```

`gate:`, `context:`, `staircase:`, `builder_effort:` and any other key of a
v2 `project.yaml` are kept by the migration (the plan's key list omits the
last two; dropping them would lose configuration). `name` and `repos` are
the project's: `name` becomes `projects: [name]` in its slot (its comments
kept), `repos` goes.

`jig.yaml` (the S0b `Marker`): init writes `jig`, `project`, `kind`, `repos`;
share adds `store` (after `project`) and `repos[].remote`. `project.SetMarkerRepos`
and `SetMarkerStore` edit the YAML tree, so unknown keys and comments survive.

**Config completion.** `project.LoadStoreConfig(storeRoot)` reads store.yaml or
project.yaml (both present is a VALIDATION_ERROR). A v3 `Config` has `Projects`,
no `Repos`, and `Name` only when the store serves exactly one project.
`project.LoadConfig(jigHome, storeRoot, name, roots...)` completes it:
`WithMarkerRepos` fills `Name` (the marker's) and `Repos` from the marker found
at `roots`, then at the machine map's root and clones for the project. A
`kind: member` marker is skipped. Orchestrator: one `Repo` per marker repo, at
its path. Otherwise one repo, the folder, named by the marker's first repo or the
project. `Repo.Label` (new, `yaml:"name"`) carries the marker's name so
`Repo.Name()` is the same on every checkout; a repo's remote is the marker's,
else its clone's origin, else `.gitmodules`' URL, else its directory. A v3 store
whose marker cannot be found has **no `Repos`** (callers guard `len(cfg.Repos)`;
`verifydeliver.primaryRepo` no longer indexes an empty list). `cmd/jig`'s
`locateStore` (so `resolveStoreChecked`) calls `LoadConfig` with Locate's root and
repo dir; `here` and `status` call `LoadStoreConfig`. `lint
TestStoreConfigIsReadThroughTheLoader` fails on the file names as string
literals outside `internal/project`, `internal/migrate`, `internal/store/store.go`,
the fixture and the review eval.

**Versions.** `MinSchemaVersion = 2`, `CurrentSchemaVersion = 3`;
`CheckSchemaVersion` accepts both, refuses older (unless `allowOlder`) and
newer. The fixture is pinned to a local `fixtureSchemaVersion = 2`, so the suite's
stores stay v2 (the standing proof that a v2 store opens); tests of v3 make
theirs with `jig init`. `store.Open` accepts either file.

**v2 to v3 step** (`migrate/v2tov3.go`): refuses a project of several repos or
none, a project with no clone of its repo mapped (help: `jig map <repo>=<path>`),
a mapped clone that is not a directory, and a `jig.yaml` there that marks another
project. It swaps `project.yaml` for `store.yaml` in one commit by the person
("jig: migrate store to schema_version 3", after the shared clean and
level-with-origin checks) and writes `jig.yaml` into the mapped clone, uncommitted
(an existing marker is kept as it is). The marker holds `project`, `kind:
project`, `store:` only when the store's origin is a URL (not a path on this
machine), and one `repos:` entry only for what the clone does not already say: a
name other than the project's, a target other than `main`, a URL remote that is
not the clone's origin. A failed commit restores the store and removes the marker
it wrote (STORE_MIGRATE_APPLY_FAILED).

**Locate.** `isStoreDir`, `storeName`, the flag, marker, map-remote and
sibling-store steps now read both layouts (`project.IsStoreDir`,
`LoadStoreConfig`, `LoadConfig`); the resolution order is unchanged.

## Decisions

- **The v1 step is a registry entry, not a special case.** `migrate.Steps`
  maps `from` version to `Step{Plan, Check, Apply, Help, UsesMap}`;
  `NextStep(cfg, to)` picks it. Each step renders as the same `files` table.
- **`share` commits `jig.yaml`.** A fresh clone needs the file, and `share` is the
  push, so it commits that one file in the person's repo (and nothing else).
  `init` commits nothing in the folder.
- **`share` pushes the current branch** of the store, of each nested repo it gave
  a remote, and of the project's repo; the plan names the branch before asking.
  A nested repo that already has a remote is not pushed.
- **Why `repos[].remote` is written at share and at `--clone`.** A checkout does
  not have a gitignored clone, so `jig.yaml` is the only place its URL can come
  from; a submodule's URL is `.gitmodules`'.
- **`--key` works for an orchestrator too** (the store declares one key either way).
- **Names.** The single repo is named after the project unless the marker says
  otherwise; the migration writes the name only when the v2 repo's differs.

## ADR impact

ADR 0032 should say: a project is defined by `jig.yaml` at its root and a
sibling store; the store's own config (`store.yaml`: `schema_version`, `keys`,
`trackers`, `platform`, `gate`, `context`, `projects`) is what says how tickets
are written, and what describes the project (name, repos, kind) is the marker;
local until `jig share`; migrations are one step each (`migrate.Steps`) so each
is one reviewable store PR; a v2 store is a first-class citizen until its owner
migrates it. ADR 0031's "enforced on every command" for schema 2 becomes "schema
2 to the current one is accepted".
