## Verbs

```
jig hooks   --global | --project <name> | --here   [--harness claude] [--uninstall] [--yes]
jig githook --global | --project <name> | --here   [--uninstall]
jig githook post-commit                             (hidden; git runs it)
```

**Scopes.** Exactly one, always spelled out. None is `NEEDS_INPUT` (exit 2) with the three
choices as help; two is `VALIDATION_ERROR`.

- `--global`: `hooks` edits `<user home>/.claude/settings.json`; `githook` sets git's global
  `core.hooksPath`.
- `--project <name>`: a project of this machine's map (`projects.yaml`). `hooks` writes
  `<root>/.claude/settings.local.json`, where root is `MachineProject.Root`, else the one clone of a
  project with exactly one; a project with neither is `NO_PROJECT_ROOT`. `githook` takes all its clones.
  An unknown name is `VALIDATION_ERROR` listing the known ones.
- `--here`: `hooks` uses the folder of the nearest `jig.yaml` marker walking up from the working
  directory, else the top of the git work tree around it; neither is `NOT_IN_PROJECT`. `githook` uses
  the one git clone around the working directory (`NOT_IN_PROJECT` when there is none).

**`hooks` and `--yes`.** A change to a settings file needs consent. `--yes` gives it. Without `--yes`:
on a terminal (`e.stdinIsTerminal`) it prints what it would do and asks `Apply? [y/N]` (a decline is
`result: declined`, exit 0); with no terminal it writes nothing and exits 2 with `NEEDS_INPUT`, whose
help line is the command to run again with `--yes`. When there is nothing to change (already installed,
or nothing to remove) it needs no consent and says `result: unchanged`. `githook` has no `--yes`, as
in the brief.

**`hooks` output**, on stdout:

```
hooks:
  harness: claude
  scope: global            (project <name> | here)
  file: <path>
  result: installed | unchanged | removed | declined
  command: <program> observe --harness claude        (install only)
  events: SessionStart UserPromptSubmit PostToolUse Stop SessionEnd
help[1]: ...
```

`--harness` takes `claude` only for now (the default); any other value is `VALIDATION_ERROR` naming
what is supported. D5.2 adds the rest by adding to the dispatch in `cmdHooks` (one `if` on the harness
today) and `claudeSettingsPath`.

**Project and `--here` files.** The file is `.claude/settings.local.json`, the one Claude Code reads
for the person alone. Installing also has `setup.ExcludeFile` list it in the repository's
`.git/info/exclude`. An uninstall that leaves the file as `{}` (it held only jig's entries) deletes the
file, takes the exclude line out and removes the `.claude` directory if it is empty. The global file is
never deleted.

**`githook --global` output:**

```
githook:
  scope: global
  hooks_dir: <jig home>/hooks
  core.hooksPath: set | unchanged | restored | unset | left
  previous: <value as written> | none
  wrappers_written: <n>
  result: installed | unchanged | removed
```

**`githook --project` and `--here` output:** a `githook:` block (`scope`, `result`) and
`clones[n]{clone,state,detail}` with `state` one of `covered` (the clone's hooks directory is jig's
own), `block` (a block is in its post-commit, `detail` is the file), `none` (after an uninstall) or
`skipped` (`detail` is the reason). A skip is exit 0.

## The hook command contract

A command is `<program> <verb> ...` with the program being the bare word `jig` when
`lookPath("jig")` is the same file as `executable()`, else the absolute path of the running binary,
double-quoted, with forward slashes (`"C:/tools/jig.exe"`; Git Bash reads both). The Claude command is
`<program> observe --harness claude`; the git one is `<program> githook post-commit`. The binary must
be named `jig` or `jig.exe`, else the install refuses with `BINARY_NAME` (an entry it could not
recognize again would pile up), and a path with `"`, `$`, a backtick or a backslash after
`ToSlash` is refused too. Taking entries out needs no command, so any binary may uninstall.

**Ownership regex.** The design's is `^"?[^"]*jig(\.exe)?"? (observe|githook)\b`. It lets `[^"]*`
run over spaces, so `echo ran jig observe` and `npx tool --jig observe` match. The code uses

```
^(?:"(?:[^"]*[/\\])?jig(?:\.exe)?"|(?:[^\s"]*[/\\])?jig(?:\.exe)?) (?:observe|githook)\b
```

which is the same with the program held to one word: a bare `jig`, or a path whose last element is
`jig`/`jig.exe`, quoted (and then it may hold spaces) or not. Everything jig writes matches both. Use
`setup.OwnedCommand` rather than a copy of either.

## Claude Code merge

`MergeClaude(data, program)` and `UnmergeClaude(data)` work on the ordered form, so every key, every
other hook and their order stay. Per event in `ClaudeHooks()` (SessionStart, UserPromptSubmit,
PostToolUse with matcher `Bash`, Stop, SessionEnd) there is exactly one owned entry after a merge: an
existing one is kept in place and its command brought up to date, extra ones are dropped (and a group
that only they filled), a missing one is appended as a group of its own
(`{"matcher":"Bash","hooks":[{"type":"command","command":...}]}`, no matcher for the others). A second
merge returns the input bytes with `changed == false`. An unmerge removes owned entries in every event
(so an older jig's extra events go too), then the groups, the events and `hooks` itself that it
emptied, and nothing else. A file that is not a JSON object, has comments, or whose `hooks` or an
event is the wrong type is an error and is never written over.

The file keeps its indent, line ending, byte order mark and final newline; numbers keep their written
form; strings are not HTML-escaped. It is not byte-for-byte: a compact `[{...}]` is re-laid out. The
write is atomic (temp file in the same directory, rename), keeps the file's permission bits and writes
through a symlink. There is no lock sidecar: the file is the person's, and Claude Code edits it too.

## Git hooks

**Global.** `jig githook --global` writes 20 POSIX sh wrappers into `home.HooksDir(root)`
(`ClientHooks()`: every client hook except `reference-transaction` and `fsmonitor-watchman`) and sets
`git config --global core.hooksPath <dir>` through gitx. Each wrapper runs, in this order:

1. the repository's own `$(git rev-parse --git-common-dir)/hooks/<name>`, with the arguments and stdin,
   then
2. the hook of the `core.hooksPath` that was set before, from `<hooks dir>/.previous` (the value as
   written, `~/` expanded by the wrapper; a relative value resolves against the hook's working
   directory, as git resolves it), then
3. for `post-commit` only, `<program> githook post-commit`, if that program is found.

The exit code is the first failure of 1 or 2 (the second is not run after a failure; the jig step
still runs, since the commit is made). `pre-push` and `post-rewrite` get stdin on a temp file so both
hooks read it. A hook file that is not executable is skipped, except under MINGW/MSYS/CYGWIN where git
runs any file. The wrappers set `JIG_GITHOOK_WRAPPED=1` for what they run.

The previous value is the global `core.hooksPath`, else the system one (the global would shadow it);
never jig's own directory. The wrappers and `.previous` are written before the setting is switched. A
file in the hooks directory that is not a wrapper of jig's (no marker on its second line) makes the
install refuse and change nothing. Uninstall puts the setting back (`restored`, or `unset` when there
was nothing, or when the previous value is the system's), leaves a `core.hooksPath` someone set since
alone (`left`), and deletes only the wrappers it recognizes.

**Per clone.** A clone that sets `core.hooksPath` for itself is not reached by the global setting.
`InstallClone` finds the hooks directory git really uses for it and appends a block to its
`post-commit` (created, with `#!/bin/sh`, when there is none):

```
# >>> jig >>>
# Written by jig githook; jig githook --uninstall removes this block.
[ -n "${JIG_GITHOOK_WRAPPED-}" ] || { command -v <program> >/dev/null 2>&1 && <program> githook post-commit </dev/null; } || true
# <<< jig <<<
```

The guard keeps a clone under both the global wrappers and a block from recording a commit twice. A
block is not written (state `skipped`, with the reason) when `post-commit` is not a shell script (a
non-sh interpreter line or a NUL byte); when the clone's hooks directory is inside its work tree and the
file is not git-ignored (it may be tracked; D5.2's `--tracked` form is the way in); or when the
`core.hooksPath` comes from the global or system config, which every repository shares (the global
install chains it instead). An uninstall removes the block from the effective directory and from the
clone's own `.git/hooks`, and deletes a `post-commit` that held nothing else.

**`githook post-commit`** (hidden, `NoFlagSet`) appends one ledger line and exits 0 whatever happens;
a failure is one line on stdout (`jig githook post-commit: <error>`), which git shows beside the
commit. The line, with `ticket` empty because the ledger is the machine's, not a store's:

```json
{"ts":"2026-10-23T09:12:17.1830426Z","ticket":"","event":"git-commit","commit":"<sha>","branch":"main","cwd":"<work tree top>"}
```

`branch` is absent on a detached HEAD. `cwd` is the directory git ran the hook in (the work tree's top,
in the spelling the OS gives), so compare it with `gitx.SameDir`, not as a string. `ts` is `e.now()`.

## Environment seams

`gitConfig(e)` hands gitx `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM` and `GIT_CONFIG_NOSYSTEM` from
`e.getenv`, so an in-process test gives the verb a config file of its own (`envFrom` with
`GIT_CONFIG_GLOBAL`) and an e2e test uses `withGitGlobal`. `internal/setup.GitConfig.Env` is the same
for library tests. A cmd/jig test that runs an installer sets `withExecutable(<path>/jig)` and
`withLookPath` (the test binary is not named jig, and `envFrom` keeps the real `lookPath`): see
`newInstallerEnv` in `cmd/jig/hooks_test.go`.

## Deviations from the brief

- **Ownership regex** tightened, as above.
- **Extra files** beyond the brief's list: `internal/setup/{command,exclude,files}.go` (the command
  contract is shared by both pieces; the exclude block keeps `.claude/settings.local.json` out of
  `git status`, which D5.2's untracked form also needs; the file writer is shared) and
  `cmd/jig/scope.go` (the scope flags and the program part are D5.2's too). D5.2 reuses them.
- **`InspectGlobal`, `ClaudeEvents`** are not asked for: they are what `jig doctor` reads, and the
  tests needed the same reads.
- **`--yes` on a terminal-less run is required**, not optional (see above): the brief lists the flag
  without saying what it confirms.
- **`CLAUDE_CONFIG_DIR` is not honored.** The settings path is `<home>/.claude/settings.json`, like
  `skills install`'s. Honoring it would send a test run with the variable set on a developer's machine
  to the real directory; D5.2 decides it for hooks, skills and hint together.
- The Write and Edit tools refused paths in this worktree; the files were written through the shell.

## Known limits (for D5.2's doctor and help text)

- Server-side hooks (`pre-receive`, `update`, `post-receive`, `post-update`, `push-to-checkout`,
  `proc-receive`) are not wrapped: a repository that is pushed into and keeps one stops running it under
  the global `core.hooksPath`. `reference-transaction` and `fsmonitor-watchman` are left out by design.
  Doctor should warn when a clone has any of them in its own `hooks` directory.
- The wrappers name the jig binary by the path it had when they were written. `InspectGlobal(hooksDir,
  program)` lists the wrappers that differ from what this binary would write (`Stale`); rerunning
  `jig githook --global` rewrites them.
- A block is shell appended to the end of a hook: a hook that ends in `exit` or `exec` never reaches it.
- Claude Code ignores project hooks in a folder it does not trust and with `--bare`; the install output
  says so.
- **Do not install against a real settings file from a build that predates D7.** The entries call
  `jig observe`, which until D7 is an unknown command that exits 2, and exit 2 from a Claude Code
  `UserPromptSubmit` hook blocks the prompt.

## ADR impact (for D1)

ADR 0032 should record: the global `core.hooksPath` as the one mechanism for seeing every commit, with
the chain order above and `.previous`; ownership by detection (`OwnedCommand`), not by a record; the
installers' scope flags being explicit, with consent by `--yes` and no terminal meaning `NEEDS_INPUT`;
and the ledger `git-commit` line.
