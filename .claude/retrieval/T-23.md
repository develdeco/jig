## fix-1-root-test

- goal: Fix these gate findings:

cmd/jig/graduate.go:218 nothing tests the rejected-claim path claimOneChartEntry re-reads the chart for
The brief: "a rejected claim removes that commit, pulls, reads the chart again, and continues with the entries that still have no id, so a chart another clone graduated in the meantime is never graduated twice". claimOneChartEntry's whole shape - re-reading charts/<name>/tickets.yaml inside Claim's write, on every attempt - exists for that sentence, and no test drives it. The graduate tests cover the happy path, a mid-run Mint failure (TestGraduateMidRunFailureIsRecoverable) and a push that fails without a rejection (TestGraduatePushFailureRemovesTheClaim); internal/store's claim tests drive the rejection with a plain write that always mints, never a chart re-read. The seam the brief names is "`jig ticket new` and `jig graduate` run against a store whose origin is a bare repo: the ids they print and what lands on the origin", and this is the one behavior at that seam with no proof. It is deterministic to set up: clone the store's origin, graduate the chart from the second clone and push it, then drive claimOneChartEntry in the first clone without syncing - its push is rejected, its pull brings in the other clone's id, and the re-read must report done with no second ticket minted.
Risk (medium): If the re-read ever regresses to a read-once, two clones graduating one chart mint two tickets for one entry and orphan one of them - the duplicate-ticket failure this ticket set out to remove - and the suite would stay green.

internal/repohost/repohost.go:42 repohost.go is not gofmt'd, so CI's gofmt step fails
`gofmt -l .` reports internal/repohost/repohost.go: in the var block at lines 41-45, `sshRemoteRE` and `httpRemoteRE` are each one space short of gofmt's alignment against `sshURLRemoteRE`. .github/workflows/ci.yml:37-39 runs `test -z "$(gofmt -l .)" || { gofmt -l .; exit 1; }` on Linux, and lint/workflow_test.go pins that step's existence, so this branch fails CI as it stands. `gofmt -w internal/repohost/repohost.go` is the whole fix. Nothing else is unformatted, and `go vet ./...` plus `go test ./...` both pass in this worktree.
Risk (medium): No runtime effect, but the required CI check is red, so nothing on this branch merges until it is formatted.

internal/store/claim.go:113 undoClaim's `git reset --hard` is repo-wide, not scoped to the claim
The brief says a rejected push "removes the claim, the commit and the folder, without touching anything else in the store", and ADR 0017 repeats it. undoClaim runs `git reset --hard <pre>`, which restores every tracked file in the store and drops every commit after `pre`, not only the claim's own. Two consequences on a store with an origin, the only store where the undo runs: (a) an uncommitted modification to a tracked file made after Claim read `pre` is discarded - a journal.ndjson line or slice state another jig process on the same clone appended while the claim was in flight, an interleaving store.go's own comments already treat as possible ("Another process working on the same store can still slip in between"); (b) a commit another process made after `pre` and had not pushed yet goes with it. The staging half is scoped deliberately (`git add --`, never -A, per the same brief); only the undo is not. Scope the undo the same way: move HEAD back without touching the tree (reset --soft/--mixed) and restore just the paths write reported - `git restore --source=<pre>` for an edited file such as charts/<chart>/tickets.yaml, `git rm -r --cached` plus the existing `clean -fdx` for a folder that did not exist in `pre`.
Risk (medium): Silent loss of another process's uncommitted store writes, in a store the brief itself says has two sessions working it; the window is narrow and the project already tolerates this class of race, so this widens an acknowledged race rather than creating one.

internal/store/claim.go:124 a blob-only existence check makes the undo delete a directory it should restore
undoClaim chooses between `git restore` and `git rm -r --cached` with gitx.FileExistsAtRev, which reports whether a path exists "as a blob (not a tree)" and documents that "a directory lists its children rather than itself, so 'a/' or 'a' for a directory is false" (gitx.go:289-302). A reported path that is a directory already tracked at pre therefore reads as "did not exist there" and takes the removal branch: `git rm -r --cached -- <dir>` untracks every file under it, `git clean -fdx -- <dir>` then deletes them from disk, and the deletions are left staged (and, per the whole-index commit above, would ride into the next attempt's claim commit and its push). Today's two writers escape by luck - `jig ticket new` reports only a fresh folder (ticket.go:66) and graduate's second path is the blob charts/<chart>/tickets.yaml (graduate.go:252) - but Claim's contract is "every path it wrote" and its own doc names a ticket folder as such a path, so the next writer that reports an existing folder wipes it. Key the branch on whether the path exists at pre at all (`git cat-file -e <sha>:<path>`, `ls-tree -d`, or whether it is in the tree at sha), not on blob-ness.
Risk (medium): Unreachable from the two callers that exist today, which is why it is latent rather than a live defect; if reached it deletes tracked store files from disk and stages the deletion for the next push.
