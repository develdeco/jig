lint/global_state_test.go:248 The package-level-variable check counts `:=` short declarations as assignments, so an innocuous local pins a file to the debt list forever
checkScoped reports every *ast.AssignStmt whose LHS ident is in pkgDecls, without looking at assign.Tok. A short variable declaration (`x := ...`) is also an *ast.AssignStmt (Tok: token.DEFINE), so declaring a local whose name happens to match any package-level var or const in that package's non-test files is reported as "assigns to package-level <name>". This is live today, not theoretical: internal/fixture/fixture.go:445 declares `var envtoolBin string` at package level, and internal/fixture/fixture_test.go:316 declares a local `envtoolBin := filepath.Join(...)`. The lint reports that line as an offender. It is masked right now only because fixture_test.go is on debtList for real env edits too - but it means that debt entry can never be removed even after internal/fixture's diet removes every real offender, which is exactly the ratchet promise the brief asks for ("a listed file with no offender left also fails the lint, so the list only shrinks"). The same shape will hard-fail any unlisted package the moment a test declares a colliding local. Two contributing causes: pkgNonTestDecls also collects token.CONST names (line 94), which can never be assigned at all, and the check ignores local shadowing, so `var confirm func(...)` plus `confirm = x` inside a test function would be reported as well. Minimum fix: require assign.Tok == token.ASSIGN, and drop CONST from the collected names.
Risk (medium): The lint is a build gate for the whole repo: a false offender either fails CI on a correct test or forces a permanent debt entry, which defeats the shrink-only ratchet the ticket exists to establish.

- goal: Fix these gate findings:

internal/gitx/gitx.go:101 The new exact-environment path skips repoEnv stripping, the invariant gitx's package doc promises every call
runOnce's new `if exact { cmd.Env = env }` branch (lines 100-104) hands env to git verbatim, so the repoEnv filter every other path gets through inheritedEnv (lines 171-191: GIT_DIR, GIT_WORK_TREE, GIT_COMMON_DIR, GIT_INDEX_FILE, GIT_OBJECT_DIRECTORY, GIT_ALTERNATE_OBJECT_DIRECTORIES) is skipped. The package doc states that invariant without exception (lines 2-4: "Every call is argv-based, scoped to a working directory (an inherited GIT_DIR and the like are dropped, so git finds its repository from that directory)"), and repoEnv's own doc (lines 165-170) names the live cases: "A git hook exports some of them (GIT_INDEX_FILE, and GIT_DIR in a bare or server-side repository), and a user can export any of them". The only caller today is IdentityEnvWithBase, and the only value reaching it is internal/verifydeliver/identity_test.go's ambientWithoutIdentity, which drops just the six GIT_AUTHOR_*/GIT_COMMITTER_* names from os.Environ() and keeps everything else. So on a machine where the test binary inherits any repoEnv variable - tests run from a git hook, or a shell with GIT_DIR exported - the two `git var` calls resolve against that other repository instead of the mapped clone (TestPublishCommitsWithMappedCloneIdentity) or the sealed lease (TestPublishFailsIdentityRequiredAndPushesNothing), and both tests read the wrong repo's identity config. jig's own runs happen to be safe only because cmd/jig calls gitx.ClearRepoEnv() at startup (cmd/jig/main.go:27); a bare `go test ./...` inherits whatever the shell has, and no test pins this either way. Fix: filter repoEnv out of env in the exact branch too, with the same case-insensitive match inheritedEnv uses, so the invariant holds on every path regardless of what a caller passes.
Risk (medium): A git call that escapes its working-directory scope reads - and for other verbs would write - another repository; here it silently decides which identity lands on publish's commits, and the failure depends on the host's environment rather than the code.

internal/gitx/gitx.go:51 RunReplaceEnv with a nil env inherits the whole process environment, the opposite of what it and run document
os/exec treats a nil Cmd.Env as "the child uses the current process's environment", so RunReplaceEnv(dir, nil, args...) reaches `cmd.Env = env` with env == nil and inherits everything - repoEnv included, and the pinned identity the function exists to shadow. Both doc comments claim the reverse: RunReplaceEnv's "env as the call's whole process environment, instead of appended to this process's own inherited one" (lines 46-50) and run's "env is the call's whole environment, verbatim, and nothing is inherited" (lines 71-73). It is unreachable today because IdentityEnvWithBase short-circuits a nil base to IdentityEnv (lines 524-527), so no test can see it, which is exactly what makes it a trap for the next caller of an exported function whose whole point is replacement. Fix: in the exact branch use a non-nil empty slice when env is nil (`cmd.Env = []string{}`), and watch that a `var kept []string` accumulator in the repoEnv filter the finding above asks for does not reintroduce nil for an all-filtered input.
Risk (medium): Silently inheriting the environment a caller asked to replace puts the wrong identity on publish's commits or points git at another repository, and the call site reads as if the opposite happened.
