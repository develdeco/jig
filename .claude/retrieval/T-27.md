## fix-1-root-test

- goal: Fix these gate findings:

cmd/jig/store_test.go:188 The mirror sync on a migrated store is never tested, at the seam and critical path the brief names
brief.md#Seams names "A6's mirror sync against its fake GraphQL server, on a migrated store" as one of the four seams, and brief.md's critical paths name "after the migration, a sync updates each mirrored issue in place and creates none". Nothing in the change covers it: internal/mirror's tests all build a schema-2 store from scratch (newTestRemoteStore, mirror_test.go:46), and the migration tests (TestStoreMigrateApplyEndToEnd here, TestApplyMigratesAStoreEndToEnd in internal/migrate) stop at `jig status`/`jig validate` and at the records on disk. DECISIONS.md:3185 lists only the other two critical paths, so the gap is openly there. The behaviour looks right by reading - migrate moves tracker/github.yaml with the folder (apply.go moveTicket keeps it), ticketRecordPath now resolves it through st.TicketRelDir (mirror/record.go:83), and a record carries no ticket id of its own, so a moved record is found at the new path and drives an update rather than a create - but nothing pins it. cmd/jig tests already drive a fake mirror client through the env (see graduate_test.go:1259), so a migrate-then-checkpoint test here can assert the fake saw UpdateIssue for each ticket and CreateIssue for none.
Risk (medium): If the record or the path were wrong, the first sync after the real cutover would create a duplicate GitHub issue for every ticket in the store and place it on the owner's project board - visible outward and tedious to undo by hand.

internal/migrate/apply.go:19 A failure part-way through Apply leaves the store half-migrated, with an error that carries no code and no way out
Apply moves every ticket folder first, then rewrites every record, then the charts, then project.yaml, and only then commits. Any failure after the first os.Rename (a ticket.yaml ReadTicket refuses with TICKET_RECORD_INVALID, a chart write hits the stale-read guard, a Windows file lock on a rename) returns and leaves the store with folders already moved and nothing committed. The errors on that path are plain fmt.Errorf (moveTicket, apply.go:52-65) or git's/os's own error returned unchanged (apply.go:36-41, 127-130), against brief.md's constraint for every slice: "Errors are *axi.Error with a code and Help lines that say what to do next". The operator is left to work out on their own that the store must be restored (`git reset --hard` plus `git clean -fd`, safe exactly because CheckClean and CheckLevelWithOrigin ran first) before retrying. Wrapping Apply's failures in one *axi.Error with a code and that recovery line is enough; nothing about the intent changes.
Risk (medium): No data is lost (everything was committed and level with origin before Apply ran), but this is a one-shot command on the project's source of truth, and an operator who retries or pushes from a half-moved tree makes it worse.
