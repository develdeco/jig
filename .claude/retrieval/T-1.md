## fix-1-root-test

- goal: Fix these gate findings:

cmd/jig/graduate.go:126 Ids are written back only after every ticket is minted, so a failure midway duplicates tickets on a re-run
The brief requires that graduate write each new id into its entry "as soon as that ticket exists, before creating the next", so that "a failure midway leaves every created ticket recorded in the file, and a re-run continues where it stopped". The implementation mints all drafts in one tracker.Graduate call (line 116) and only then calls st.WriteChart once (line 126). tracker.Graduate itself returns `nil, err` on a mint failure (internal/tracker/tracker.go:134), discarding the ids it already minted, so the caller cannot record partial progress even if it wanted to. Concretely: a 3-entry chart where entry 2's Mint fails leaves entry 1's ticket folder, tracker/ticket.md and ticket.yaml on disk, the chart file untouched and uncommitted; the next `jig graduate` mints a *new* id for entry 1 (the local adapter picks max+1 from the store, internal/tracker/local.go:58-76), leaving an orphan ticket and a duplicate. ADR 0010 (docs/adr/0010-...md:51-55) states the opposite invariant as a decided property of the design ("after a graduate call failed partway through, creates exactly the tickets that are still missing"), so code, brief and ADR disagree. Fix: have Graduate report the ids minted so far (or accept a per-ticket callback) and write the chart entry back after each mint.
Risk (high): Silent duplicate ticket creation plus orphaned ticket folders in the store's git history; a github/command tracker (network, rate limits) makes a mid-run failure ordinary rather than exotic, and the store is jig's source of truth.

internal/tracker/local_test.go:123 "Epic slice" fixtures remain in the tracker tests
The brief's docs slice requires that "epic" remain only in CONTEXT.md's avoid list. internal/tracker/local_test.go still mints `tracker.Draft{Title: "Epic slice", ...}` at lines 123 and 238 - the one package whose Graduation.Epic field this ticket renamed to Chart. Fix: rename the fixture titles (e.g. "Chart slice").
Risk (low): Test fixture strings only; no behavior depends on them, but the ticket's stated goal was to retire the word from the tracker package.

cmd/jig/graduate.go:180 The graduate commit message uses Go slice formatting and a "jig: " prefix unlike every other store commit
`fmt.Sprintf("jig: graduate chart %s: %v", chart, createdIDs)` renders the ids with %v on a []string, producing `jig: graduate chart mychart: [T-1 T-2]`. Every other Store.Push message in the repo is `<subject>: <what>` with no "jig: " prefix and no Go-syntax values (internal/frontier/frontier.go:180, internal/verifydeliver/gate.go:502, publish.go:231). Fix: `fmt.Sprintf("chart %s: graduate %s", chart, strings.Join(createdIDs, ", "))` or similar, matching the store's existing history.
Risk (low): Cosmetic; the store history is read by humans and by `git log` greps, not parsed by jig.

ARCHITECTURE.md:65 Store-schema comment column is misaligned for the new entries
In the store schema block, `map.md` puts its `#` one column left of `tickets.yaml`'s, and `ticket.yaml`'s comment column matches neither (the block's existing convention is the `spec-input.md   # --branch --doc only` line). Fix: align the three new comments to one column.
Risk (low): Documentation formatting only.

internal/store/charts.go:220 An empty blocked_by key, and any comment attached to it, is dropped on write-back
updateChartEntryInNode removes the `blocked_by` key when the entry has no blockers. An entry written as `blocked_by:` with nothing under it (or `blocked_by: []`), often carrying a `# blockers TBD` head comment on that key, loses both the key and the comment the first time graduate writes an id into the file. The brief promises the write-back "keeps the file's comments, entry order and every other field". Fix: leave the existing key untouched when the caller has no blockers to write.
Risk (low): Loses a placeholder key and its comment, no ticket data; only bites a chart file that was drafted with empty blocker slots.

cmd/jig/graduate.go:186 The results table prints only created entries, never a row per entry with "existing"
The brief requires "one row per entry (position, id, title, and `created` or `existing`)". The rows loop iterates `toCreate` only, so entries that already had an id get no row and the string "existing" appears nowhere in the command. On a partially graduated chart the operator (or a session parsing the axi table) sees only the new tickets and cannot tell the chart's full shape from the output; on a fully graduated chart (line 166-177) the output is a KV block with no rows at all. Fix: build rows over every entry, tagging each `created` or `existing`, and print the table in both branches.
Risk (low): Output-only, no store or tracker state is wrong; but the table is the agent-facing contract for what a chart contains after graduation, so a session reading it gets an incomplete picture.

internal/tracker/tracker.go:170 resolveBlockedBy silently writes an unresolved "#k" placeholder into ticket.yaml
resolveBlockedBy passes any Ref it cannot resolve through unchanged (line 170), "treated as an existing tracker id". For a "#k" that is out of range, or that names a sibling not yet minted (a forward reference), the literal string "#2" therefore reaches Mint as a blocker and, worse, is written into the store as `ticket: "#2"` by the WriteTicketDeps call at line 145. ticket.yaml is defined by the brief as "Every entry names a ticket id", so this corrupts the one file that is the source of a ticket's blockers after graduation. Today only cmd/jig/graduate.go calls Graduate and its pre-validation (resolveChartEntryRefs) rejects forward refs, so the hole is unreachable from the CLI - but Graduate is an exported package API whose doc comment promises resolution, and the failure mode is a silently malformed store file rather than an error. Fix: return an error from Graduate when a "#k" ref cannot be resolved to a minted id.
Risk (medium): Unreachable from today's only caller, so no live bug; if it is ever reached it writes an invalid ticket id into the store's dependency file, which later commands (and `jig validate`) treat as a missing ticket.

internal/store/charts.go:131 WriteChart truncates the file to the caller's entry count, discarding anything added since the unlocked read
WriteChart locks, re-reads the file and then overwrites it from the caller's `entries` slice, ending with `ticketsNode.Content = ticketsNode.Content[:len(entries)]`. The locked re-read is used only to recover comments, never as the authoritative content - unlike AppendSlices (internal/store/slices.go:58-96), which merges into what it read under the lock. Because ReadChart takes no lock, any entry a human (or another jig) appends to charts/<name>/tickets.yaml between cmdGraduate's ReadChart (graduate.go:54) and WriteChart (graduate.go:126) is silently deleted; with a github tracker that window is the whole minting run. The brief's constraint for these files is "locked reads and writes (store.Lock)". Minimal objective fix: stop truncating (update and append only), and refuse the write when the locked re-read does not have the entry count the caller based its edit on.
Risk (medium): Silent loss of hand-written chart entries with no error and no trace except the store's git history; needs a concurrent edit to trigger, which is plausible since the chart file is exactly the file a human is editing while graduating.

cmd/jig/graduate.go:363 A cross-chart ref's chart name is never validated, so "../..#1" reads YAML outside charts/
cmdGraduate validates the chart name it gets on the command line (validateChartName: no path separator, not "." or ".."), but the chart name inside a `blocked_by` ref gets no such check: parseRef hands whatever precedes "#" straight to readOtherChart -> st.ReadChart -> filepath.Join(s.Root, "charts", name, "tickets.yaml") (internal/store/charts.go:257). `ref: "../../secrets#1"` therefore reads and parses a YAML file outside the store, and if that file happens to have a `tickets:` list with ids, those ids are accepted as blockers and written into a new ticket's ticket.yaml. The same rule the brief states for the command argument ("one plain directory name") should hold for a ref's chart name, and ChartEntry ids elsewhere go through checkTicketID. Fix: run validateChartName on refChart before reading, and report a bad chart name through refErr.
Risk (medium): Input is an operator-authored file, so this is a foot-gun rather than an attack path; still, jig reads and half-trusts a file outside the store it was pointed at, and the resulting blockers land in the store.

cmd/jig/graduate.go:365 Any error reading another chart is reported as "no charts/<x>/tickets.yaml"
The `default` branch discards readOtherChart's error and always says the chart "has no charts/<x>/tickets.yaml". A referenced chart whose tickets.yaml exists but does not parse (or is unreadable) is reported as missing, sending the operator to create a file that is already there instead of to the YAML error. Fix: include the underlying error, or distinguish os.IsNotExist from a parse failure.
Risk (low): Wrong diagnosis only; the run is refused either way, so nothing is created on a false message.

graduate_test.go covers the deps slice (refs, ticket.yaml, advisories) but nothing from the tracer slice's own list: an invalid chart name (".", "..", a path separator - the guard that also keeps refs like "../x#1" from escaping charts/, see the traversal finding), a chart whose charts/<chart>/tickets.yaml does not exist, an entry without a title, an entry whose id the store has no folder for, two entries with the same id, the single Store.Push at the end and its message, and the one-row-per-entry table. cmd/jig/graduate.go:166 A chart with no entries reports "fully graduated" and "All entries in this chart already have ids"
A tickets.yaml that parses but has no entries (empty file, or `tickets:` with nothing under it) yields nil entries, so toCreate is empty and the command exits 0 claiming the chart is fully graduated and that all its entries already have ids - both false for a chart with zero entries. WriteChart would have refused the same file ("tickets key not found in chart file"), so the two halves of the store API disagree about whether such a file is usable. Fix: refuse a chart with no entries with a VALIDATION_ERROR naming charts/<chart>/tickets.yaml, or say "no entries" instead of "fully graduated".
Risk (low): Misleading success message on an empty input; nothing is written and nothing is lost, but the operator is told the handover is done when no ticket exists.
