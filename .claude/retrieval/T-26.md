## fix-1-root-test

- goal: Fix these gate findings:

internal/store/resolve.go:48 Every resolve rescans the store root and re-reads every ticket.yaml
aliasClaims runs TicketIDs (one ReadDir) plus one ReadTicket per ticket in the store, and nothing memoizes the result, so each ResolveTicket call costs O(N) file reads. The callers invoke it per ref, not once per run: cmd/jig/validate.go:267 resolves once per blocked_by entry and cmd/jig/validate.go:349 once per edge of the cycle DFS; internal/mirror/links.go:236 resolves once per blocker while linking, and internal/mirror/render.go:195 resolves each blocker again when rendering the "Waits for" line - and that sync runs from inside every command (A6's checkpoint hook). For N tickets each carrying one blocker that is on the order of N squared ticket.yaml reads per sync: roughly 900 for jig's own store today, roughly 40,000 at 200 tickets, on a path every command runs. Resolving the claims map once per sync and once per validate run and threading it through (or caching it on Store for the life of one call) keeps the behaviour identical and makes the cost linear.
Risk (medium): Correctness is unaffected, but the cost sits on the checkpoint sync every command performs and grows with the square of the store's size, so it degrades silently as stores grow and L3/L4 add tickets.
