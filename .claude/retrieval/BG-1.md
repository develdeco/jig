## lean-body

## fix-4-root-test

- goal: Fix these gate findings:

internal/verifydeliver/render.go:396 An info-string fence line reads as a closing fence, so a published body can still end inside a code block
fenceScanner.fenced closes a block on any fence line of the same character and at least the same length (`case marker == f.marker && run >= f.run`), including one that carries an info string. cmark-gfm, what GitHub renders a pull request body with, allows an info string only on an opening fence: a "```sh" line inside a "```" block is that block's own content and the block stays open. Probed against this tree (go test -overlay, package-internal, no repo file changed): closeOpenFence("Shape:\n\n```md\n## Intent\n```sh") returns its input unchanged - jig reads the block as closed and appends nothing, GitHub reads it as open, and ## What changed, ## Verification and the findings count line render as the inside of that code block. That is exactly the failure closeOpenFence was added for this round (prior r3-f1), reached by a different fence syntax. firstBriefSection goes wrong the same way: for "## Intent\n\n```md\nexample\n```sh\n\n## Plan\n..." it returns "```md\nexample\n```sh" - the Intent stops at "## Plan" because the scanner believes the fence closed, and the section it hands on carries a fence GitHub never sees closed. demoteHeadings loses its own stated promise too ("A heading inside a fenced code block is left alone - it is a code sample's own text"): every "## " line after the mistaken close gets a "#" inserted, rewriting the sample the reviewer came to read. The remedy is the third CommonMark rule the scanner's doc comment leaves out of its two: while a block is open, a fence line closes it only when nothing but spaces follows the run.
Risk (medium): The failure is silent and defeats the body's central promise - two of the three sections a reviewer opens the pull request for become code-block text with no error, warning or test failure - so a review can be signed off without ever seeing what changed or how it was verified. The trigger is narrow (a text whose intended closing fence carries an info string), which is why this is medium and not high.

The edit that inserted "outside a fenced code" / "block" into this bullet rewrapped only the lines it touched, so the paragraph now reads "... - never a fixed \"skip" / "line 0\" - and normalizes" / "CRLF first, the same as `store.BriefSectionHashes`, ...": line 1921 breaks after four words while every other line in the file fills to roughly 74 columns.
