## fix-1-root-test-1

- goal: Fix these gate findings:

cmd/jig/main.go:239 The checkpoint hook throws the whole SyncReport away, so a checkpoint's sync prints nothing it is required to print
resolveStore wires the hook as `_, err := mirror.Sync(...)`, discarding the report, and no command sets store.Warn, so the hook's only visible output is a stderr warning on failure (store.go:43-53). brief.md#Ownership and drift requires "Drift lines print in the output of the command whose checkpoint found them"; brief.md#Publish safety requires a skipped item to be named with its line number and line; brief.md#Links requires an unlinked blocker to be printed, and brief.md#Adoption a recreated issue. None of these reach the user from a checkpoint sync today - only `jig trackers sync` prints anything, and the brief's "and in jig trackers sync's" makes that the second place, not the only one. Rendering the report (at least Drift, Skipped, Created/Recreated and NotLinked) through the command's own writer, and setting Store.Warn so the failure warning lands in the command's structured output rather than bare stderr, is what the brief asks for.
Risk (medium): No store or GitHub state is wrong, but an operator gets no signal that a checkpoint's sync skipped a ticket on a publish-safety hit or overwrote a hand edit, which is the whole reporting contract of the feature.

cmd/jig/trackers_test.go:142 TestTicketNewSucceedsDespiteTrackerSyncFailure can reach api.github.com with the developer's own gh token
The test relies on the checkpoint sync failing because the machine has no usable gh ("most likely GH_NOT_INSTALLED, or a real gh with no token"). On a machine where gh is installed and authenticated - the normal state for anyone working on this repo - Deps.client() builds the real GraphQLClient against https://api.github.com/graphql with that token (mirror.go:295-304) and the sync sends a repository lookup for example/tracking to github.com. brief.md's test constraints say "GitHub is a fake GraphQL server (httptest) the client is pointed at; no test reaches github.com", and the assertion itself becomes machine-dependent (it passes either way today only because the lookup happens to fail). The hook wired in resolveStore (main.go:239) offers no seam for a cmd test to inject a client or endpoint; giving it one (or asserting this seam at the mirror level, where Deps.Client already exists) keeps the test hermetic.
Risk (medium): A test in the suite makes an authenticated outbound request to github.com on a developer's machine, which the ticket's testing rules forbid, and its pass depends on local gh state rather than on the code.

internal/mirror/board.go:122 The board step re-places every item and rewrites both fields on every sync, so an up-to-date store still mutates GitHub
placeBoardItems calls client.PlaceItem unconditionally for every item with a record (and for every open or merged pull request, board.go:160), and PlaceItem always sends addProjectV2ItemById plus both updateProjectV2ItemFieldValue mutations (client.go:937-953). It already reads the item's current Status and Store ID back through ItemFieldValues when rec.Item is set (board.go:106), so it has everything needed to skip when the current values already equal the ones it would write. brief.md#Seams's first critical path is "adopting the bridge's records: a store whose records match GitHub syncs with no mutation", and ADR 0030 restates it; the suite narrows it to "no title, body, state, or link mutation" (drift_test.go:59-96 asserts only those), and board_test.go:131 documents the opposite behaviour as intended. On top of the critical path, three mutations per item per checkpoint is what makes the missing mutation pacing (above) bite.
Risk (medium): A stated critical path of the ticket is not met, and the redundant mutations are the bulk of the sync's write traffic on every checkpoint of every store.

internal/mirror/github/client.go:186 The client has neither the one-mutation-per-second pacing nor the 4-attempt retry the brief requires
brief.md#The GitHub client: "One mutation per second, as GitHub asks of clients that create content. A request that fails with a server error or a rate limit is retried with backoff, 4 attempts in all. (defaulted, as the bridge)". GraphQLClient.do posts once and returns the first failure; there is no throttle, no backoff and no attempt counter anywhere in the package (no Sleep, no retry loop, no limiter). A first sync of a real store issues a createIssue per ticket and chart plus updateIssue, link and 2 field-value mutations each, unpaced, which is exactly the shape GitHub answers with a secondary rate limit - and because a checkpoint sync is best-effort, the failure surfaces only as a warning and the next checkpoint repeats it.
Risk (medium): Not wrong per call, but on any store larger than the test fixtures the first sync is likely to be rate-limited and abandoned mid-way, leaving issues created with footer-only bodies until a later sync happens to get through.

internal/mirror/links.go:151 Parent and blocked-by link drift is neither reported nor restored
jig owns an issue's parent and blocked-by links (brief.md#Ownership and drift, and the footer every issue carries says the sync overwrites edits to them). linkParent returns early whenever the record's synced.links.parent already names the chart's issue, and linkBlockedBy skips any blocker whose node id is already in synced.links.blocked_by - both decided from the record alone. github.IssueState.ParentID and BlockedByIDs are fetched (client.go:468-477) and threaded through curByWhat but never read for a ticket, so: a parent link removed on GitHub stays removed, with no drift line and no restore; a blocked-by link removed on GitHub likewise; and a blocked-by link added on GitHub is never removed (there is no removeBlockedBy in the Client interface at all, though the brief lists the mutation as proven). Only the chart side is handled - an extra sub-issue is removed as drift (links.go:112-124). The comparison for both directions is available from the data already in hand.
Risk (medium): Two of the six fields jig claims to own drift permanently once edited on GitHub, silently, which contradicts the ownership promise printed in every issue footer.

## fix-1-root-test-2

- goal: Fix these gate findings:

internal/mirror/mirror.go:187 Publish safety never scans a real issue body, and never scans an issue that already has a record
ScanTitleAndBody is called only inside Sync's create loop (mirror.go:164 dry run, :187 live). The text it is handed there comes from item.render (mirror.go:335), which returns the title plus the footer alone - by design, since step 3 creates the issue with only the marker as its body. The store's actual text (the ticket's description, its brief.md, a chart's map.md) is rendered later, in updateIssues (update.go:131-152), and written to GitHub by client.UpdateIssue (update.go:204) with no scan at all. Two consequences: (1) a publish-safety hit anywhere in a body is never detected, on a public issue repo, on create or on update - the scan is effectively title-only; (2) every ticket or chart that already has a record (which includes every record adopted from the bridge, and every item from its second sync onward) is never scanned again, so brief.md#Publish safety's "every title and body is scanned before it is written" and "a hit skips every write for that ticket or chart, so GitHub keeps what it had" do not hold for the update path. TestSyncSkipsAPublishSafetyHit and TestSyncDryRunReportsAPublishSafetyHit both only exercise a title hit on an item with no record, so the gap is invisible in the suite. The fix is to render the full title and body, scan them when the repo is public (and unconditionally in a dry run), and skip that one item's update, link and board writes on a hit - the same skip the create path already does.
Risk (high): This is the one guard against secrets, client names and home paths in store text reaching a public issue repo, and the path that carries that text (the body) is unguarded. A published body cannot be unpublished on GitHub.

internal/mirror/mirror.go:215 --dry-run previews creations only, so the cutover's "0 changes and no drift" check cannot fail
Sync returns right after the create loop in a dry run, before updateIssues, linkParentsAndBlockers and placeBoardItems. brief.md#jig trackers sync says "--dry-run reads everything, prints what it would change", and brief.md#Cutover makes that the operator's gate: a dry run of the branch's build is compared against the bridge's own dry run, and after the swap "jig trackers sync --dry-run must report 0 changes and no drift". As implemented a dry run reports 0 changes for any store whose items all have records, however far GitHub's titles, bodies, states, links and board fields have drifted from the store - so the cutover check passes vacuously. A dry run can read GitHub (FetchIssue, PullRequestsByHead, ItemFieldValues, and a project lookup) and report Updated/Drift/LinkedParents/Placed without issuing a mutation; it only has to withhold the writes. Note that the dry-run create preview also renders only the footer body, so no dry run previews a body change at all.
Risk (medium): The operator-facing verification step for a one-shot, irreversible cutover reports success without having checked anything past issue creation.

internal/mirror/mirror.go:130 MIRROR_REPO_CHANGED is not implemented: a record naming another issue repo is silently used
brief.md#The trackers entry: "When a record names another issue repo than the entry's repo:, the sync refuses with MIRROR_REPO_CHANGED, help: moving issues to a new repo is T-30." Nothing in the change compares a record's `repo` with cfg.GitHub.Repo - the code is not in mirror.go, update.go, board.go or links.go, and the code string appears nowhere in the tree. What happens instead: items with records keep being updated in the old repo (FetchIssue/UpdateIssue work off node ids, update.go:157-204, and a recreation re-creates in rec.Repo, update.go:160-165), while items without records get issues in the new one, so the board silently splits across two repos with no refusal and - inside a checkpoint - no error the user sees.
Risk (medium): A named refusal with a named code is missing, and its absence lets a store quietly end up mirrored into two repos, which T-30 then has to untangle.

internal/mirror/mirror.go:33 The 2-minute bound is per GitHub call, not per sync, so a checkpoint can block far longer with no warning
syncTimeout is applied by building a fresh context.WithTimeout around each individual call (mirror.go:178, :193, update.go:119, :156, :203, links.go:155, board.go:70, :105, :122, ...). brief.md#Syncing at every checkpoint says "A sync inside a command stops after 2 minutes, with a warning", and ADR 0030 repeats "a bounded sync (2 minutes)". With one context per call, a store with N items can spend N x 2 minutes inside a command before the hook gives up, and nothing reports that the sync was cut short by time rather than by an error. One context created once per Sync and passed down gives the documented behaviour (and makes the deadline the thing that produces the warning).
Risk (medium): A slow or hanging GitHub makes every jig command that checkpoints hang well past the documented bound, and the user has no way to tell a slow sync from a hung command.

internal/mirror/github/client.go:236 One mutation per second and a 2-minute whole-sync bound cannot both hold for a first sync of any sizeable store
Both rules are now implemented as the brief states them, and they collide. Raising the bound, pacing only content-creating mutations, or exempting `jig trackers sync` from the bound are all defensible; which one is the human's call.
Risk (medium): Every command on a store with a sync backlog pauses for the full 2 minutes and reports a timeout warning, which reads as jig hanging; nothing is corrupted and the backlog does converge.
The human's decision: Owner decision: keep the 2-minute bound for the sync that runs inside a command, but jig trackers sync runs until it is done (no whole-sync bound).     var (
        fenceRE      = regexp.MustCompile("^\\s*(```|~~~)")
        blockStartRE = regexp.MustCompile(`^\s*(([-*+]|\d+[.)])\s|#{1,6}\s|\||>|<|(-{3,}|\*{3,}|_{3,})\s*$)`)
        listItemRE   = regexp.MustCompile(`^\s*([-*+]|\d+[.)])\s`)
    )

    // unwrap joins the hard-wrapped lines of each paragraph and list item.
    // GitHub renders every newline in an issue body as a line break, so store
    // text wrapped at 72 columns would break mid-sentence. Fenced and indented
    // code, headings, tables, quotes, HTML and rules keep their lines.
    func unwrap(md string) string {
        var out []string
        inFence, verbatim, joinable := false, false, false
        for _, line := range strings.Split(md, "\n") {
            trimmed := strings.TrimSpace(line)
            switch {
            case fenceRE.MatchString(line):
                inFence = !inFence
                out, joinable = append(out, line), false
            case inFence:
                out = append(out, line)
            case trimmed == "":
                out, joinable, verbatim = append(out, line), false, false
            case verbatim:
                out = append(out, line)
            case blockStartRE.MatchString(line) || !joinable:
                // An indented block after a blank line that is not a list item
                // is code: keep its lines as they are.
                verbatim = !joinable && len(line)-len(strings.TrimLeft(line, " ")) >= 4 && !listItemRE.MatchString(line) && len(out) > 0 && strings.TrimSpace(out[len(out)-1]) == ""
                out = append(out, line)
                joinable = !verbatim && (listItemRE.MatchString(line) || !blockStartRE.MatchString(line))
            default:
                prev := out[len(out)-1]
                if strings.HasSuffix(prev, "  ") || strings.HasSuffix(prev, `\`) {
                    out = append(out, line) // an explicit line break
                    continue
                }
                out[len(out)-1] = prev + " " + trimmed
            }
        }
        return strings.Join(out, "\n")
    }
